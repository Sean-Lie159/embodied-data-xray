## 1. 问题（已核实代码）

### 1.1 findings 只增不减，每轮全量重渲

`RunContext.findings` 是**累积列表**：

```39:39:app/agent/context.py
    findings: list = field(default_factory=list)
```

每轮 `ChatTurn` 都带**截止本轮的最新全量**：

```293:293:app/services/chat_service.py
            findings=list(self.context.findings),
```

于是 `render_charts()` 把**历史上所有图表**平铺重渲：

```135:161:app/ui/components.py
    charts = [f for f in findings if f.get("type") == "chart"]
    ...
    for i, f in enumerate(charts):
        ...
        st.image(str(path), use_container_width=True)
        ...
        st.divider()
```

### 1.2 具体退化形态

**第一，多轮后退化为流水账。** 分析 5 轮后，`render_findings_and_report()` 输出
一长条扁平 bullet：

```171:175:app/ui/components.py
    for f in findings:
        ftype = f.get("type", "?")
        tool = f.get("tool", "?")
        summary = f.get("summary") or f.get("description") or ""
        st.markdown(f"- **[{ftype}]** {tool}: {summary}")
```

`[chart]` / `[stat]` / `[report]` 混在一列，最新结果在**最下方**（要往下翻）。

**第二，图表全宽铺开，信息密度极低。** `use_container_width=True` 使每张图占满
右栏宽度；`multi_stream_overlay` 叠 26 条流时，全宽反而看不清，且 19 张图顺序
铺开导致滚动极长（实拍 `outputs/` 已有 19 png）。

**第三，左右栏无锚点。** 对话里说"已生成轨迹图"，用户需在右栏手动找是哪张；
`tool_activity` 面板也看不到对应缩略图。

**第四，report 与 chart 的语义不同却同层。** 报告是"可下载产物"，图表是"可查看
证据"，统计是"数字结论"——三者混排降低了"我现在该看什么"的判断效率。

## 2. 设计（只改渲染，不改数据）

**核心约束（总纲第 6 节约定 2）**：finding 的字段名与语义**完全不动**
（`type` / `tool` / `file_path` / `title` / `description` / `summary` / `plot_spec` /
`section_counts` / `metric` 等）。本次只改**呈现方式**。允许**新增可选字段**，
老 finding 缺该字段时必须降级正常显示。

### 2.1 图表区（tab_charts）

| 改动 | 设计 |
|---|---|
| 倒序 | `charts` 反序渲染（最新在最上）——`findings` 天然按产生顺序 append，`list(reversed(charts))` 即可 |
| 缩略图网格 | 用 `st.columns(2)` 两列网格；每格 `st.image(..., use_container_width=True)` 缩小尺寸 |
| 点击放大 | 每个缩略图配一个按钮/`st.button`，置 `st.session_state["zoom_chart"] = index`，用 `@st.dialog("图表")` 全屏显示原图 + `plot_spec` 明细 |
| 本轮新增高亮 | 该图表若属于"本轮新增"（见 2.4 增量判定），标题前加 `🆕`/`新` 标记 |
| 类型/表名可见 | 缩略图下方 caption 显示 `chart_type` 与 `table_name`（已在 finding 中） |

**`@st.dialog` 可用性**：Streamlit ≥1.35 提供。需确认 `requirements.txt` 版本
（实现时核对；若低于 1.35 则降级为 `st.expander` 内放大）。

### 2.2 Findings 区（tab_findings）

按 `type` 分组，各成折叠块：

```
统计结论（compute_stats）         [展开]
质检结果（inspect/sync/sanity）   [展开]   ← 目前质检结果也在 findings 里
图表清单（plot_chart）            [展开]
报告（generate_report）           [下载按钮组]
```

- 组内倒序（最新在上）；
- 每条显示 `[tool] summary`，`summary` 缺失回退 `description`（**保持现有回退逻辑**）；
- 报告区保留现有下载按钮（`components.py:178-190` 逻辑不动，仅位置调整）；
- 空组不渲染（不显示空折叠块，防噪声）。

**为什么按 type 而非按 tool 分组**：type 是稳定的小集合
（chart/stat/report/…），tool 会随工具增加而膨胀；且用户心智是"我要看图/看数字/
看报告"，而非"我要看 plot_chart 的输出"。

### 2.3 排序与"最新优先"的统一原则

全右栏统一 **倒序**（最新在上）。原因：多轮分析的注意力在**最近一轮**，
而非第一轮；这也与对话区"新消息在底部"的方向相反但合理——对话是时间流（从上到下
阅读），右栏是"当前成果清单"（关注最新）。

### 2.4 本轮新增的判定（不进 findings 结构）

**不改** `RunContext.findings`（避免影响 `generate_report` 汇总与所有工具）。
用**会话侧快照对比**判定增量：

```python
# streamlit_app.py / components 调用方：
prev_n = _stt.get("findings_seen", 0)      # 上次渲染到的 findings 条数
new_flags = [i >= prev_n for i in range(len(findings))]   # 后 len-prev_n 条为新增
_stt["findings_seen"] = len(findings)
```

- 首轮：`prev_n=0` → 全部标记为新增？
  **不**：首轮全部是新的，全标 🆕 反而噪声。规则改为"仅当 `prev_n > 0` 时标记
  新增"（即从第二轮起才显示 🆕），首轮不标；
- 会话切换：`findings_seen` 随会话存（在 session dict 内，天然隔离）。

> 为什么不用"给 finding 加 turn_index"：那要改工具代码（3 个工具 + 报告），
> 违反"只改渲染"的约束，且引入老 finding 兼容问题。快照对比零侵入。

### 2.5 与第 4 项（数据集状态面板）的边界

- 第 2 项：**产物与结论**的呈现（图表/统计/报告）；
- 第 4 项：**当前数据集状态**的呈现（能力标签、流清单、语义确认画像、单位告警）。

两者不重叠：第 4 项新增的是 `tab_overview` 的深化，第 2 项改的是
`tab_charts` + `tab_findings`。

## 4. 测试计划

**UI（AppTest）**
- 无 findings：图表区与 findings 区都显示引导信息，不崩；
- 有 3 条 chart + 1 条 report：图表区渲染 3 个缩略图；findings 按 type 分组后
  各组内容正确；报告下载按钮存在；
- **倒序断言**：两张图（标题 A 先、B 后）→ 渲染顺序为 B、A；
- `findings_seen` 首轮不标新增、次轮新增项被标记。

**结构（静态断言，沿用 `test_streamlit_app.py` 先例）**
- `render_charts` 中 `st.image` 不再是"每次循环无缩进地全宽直出"（防回归到旧形态）。

**人工验收**
- 生成 3 张以上图表后：右栏可两列浏览、点击可放大、最新在最上、旧图不干扰。

## 5. 风险

| 风险 | 应对 |
|---|---|
| `@st.dialog` 在旧版 Streamlit 不存在 | 实现前核对版本；不可用则降级 expander（写进实现说明） |

| 分组后的空组噪声 | 空组不渲染 |
