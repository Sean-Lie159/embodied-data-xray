# 多表并列机制设计（方案 C 的替代路径）

> 状态：**设计草案，待用户确认**（遵循 AGENTS.md §3.4「先文档后代码」）
> 关联：`docs/技术债.md` 第 5 条（多表并列机制，方案 C 暂缓）、
> `docs/表访问与跨表运算改造设计.md` §5（方案 C 的暂缓理由与触发条件）、
> `docs/ARCHITECTURE.md` §3.3（多表支持与主表语义）
> 起草日期：2026-09-21
>
> **一句话结论**：不取消「主表」，而是把「隐含默认」改为「显式提名 + 双向确认」——
> 用约 1/3 的改造成本，消灭技术债所列的全部三处不便，且把「歧义为零」这一目标
> 落在真正缺口的环节（取表）而非最贵的环节（存表）。

## 1. 问题重述与触发条件核对

### 1.1 技术债原文所列三处不便

（引自 `docs/技术债.md:84-89`）

1. **主表自动猜，猜错由用户承担**：判据是「行×列最大」，但用户关心的表
   （末端位置、关节角、触觉）往往不是最大的那张；
2. **「换数据集」与「换表」是两套机制**（前者走 `load_dataset` 替换 `context.df`，
   后者走 `table` 参数不替换），语义并存易混淆；
3. **多表同口径分析不可行**：无法「同时对三张以上表做同口径处理」。

### 1.2 触发条件核对（2026-09-21 实地勘察）

技术债给出的触发条件是：出现「需要同时对三张以上表做同口径分析」的真实需求，
**或**方案 A+B 实施后仍频繁出现「表选错 / 找不到表」的反馈。

**核对结论：触发条件尚未满足。** 依据：

- **数据侧有 ≥3 张表的例子，但均为测试夹具**：`data/tobii_ego/`（9 张 csv）、
  `data/acceptance/combined_demo/`（3 张 csv：`tasks.csv` + `ft/ft.csv` +
  `imu/imu.csv`）、`data/acceptance/mixed/`（3 张 csv）。
- **反馈侧无一手证据**：`docs/使用日志.md` 全文 13 行，**没有任何**「表选错 /
  找不到表 / 想同时看多张表」的记录。该文件中最接近的是「对话多开，一个 ui
  分析多个数据」（多数据集诉求，已由多会话实现）。
- **一手痛点只存于设计文档转述**：`docs/表访问与跨表运算改造设计.md:24`
  （agent 读 `state/end/position` 失败后要求用户导出 CSV）与 `:65-69`
  （「实际末端 vs 指令末端相差多少」无工具支持）。
- **A+B 已落地且未观察到新反馈**：表名四写法容错、主表透明化
  （`meta.main_table.selection.candidates`）、`compare_table_columns` 均已实施
  （见 `docs/表访问与跨表运算改造设计.md:7-16`）。

**因此本设计的定位是「预备方案」**：把架构级改动拆成可独立验收的台阶，
避免将来触发条件满足时仓促动手，也避免现在就用最贵的方案解决一个尚未发生的问题。

## 2. 现状事实（改造成本的真实边界）

> 本节所有事实来自 2026-09-21 的全仓只读勘察，均附「文件:行号」证据。

### 2.1 写入面极窄

全仓库**只有 2 处**写 `context.df`，且都在 `app/tools/load_dataset.py`：

| 位置 | 用途 |
|---|---|
| `app/tools/load_dataset.py:2301` | 目录型加载：写入选出的主表 |
| `app/tools/load_dataset.py:2588` | 单文件加载：写入读出的 df（覆盖式） |

**没有任何工具反向写回主表**。这一点对本设计极为有利：取消或改造「主表」语义
不会牵出隐藏的状态回写链。

### 2.2 读取面分三档（改造成本的真实分布）

| 档位 | 工具 | 改造成本 |
|---|---|---|
| **已有 `table` 参数** | `profile_data`（`profile_data.py:19`）、`compute_stats`（`compute_stats.py:206`）、`plot_chart`（`plot_chart.py:194`）、`segment_actions`（`segment_actions.py:889`）、`check_sensor_sanity`（`check_sensor_sanity.py:467`） | 低（已具备按名取表能力） |
| **无 `table` 参数、内容全读主表** | **`check_dataset_quality`**：`check_dataset_quality.py:921` `df = context.df`，该 df 是 L1 门禁（NaN/Inf、时间戳单调、丢帧、fps、episode 边界）与 L2/L3 诊断的**唯一数据源** | **高** |
| **完全不读 `context.df` 内容** | `inspect_streams`、`check_temporal_sync`、`align_container_streams`、`compare_datasets` | 零（只读 `meta.streams` / `capabilities`） |

另有一处隐蔽耦合：`plot_chart.py:764-765` 的 `multi_stream_overlay` 在无流时
**直接读 `context.df` 兜底**并硬编码标题「主表」（`plot_chart.py:772`）。

**结论：真正需要改的只有 1 个工具（`check_dataset_quality`）+ 1 处隐蔽兜底。**

### 2.3 最大缺口在「取表」环节，不在「存表」环节

三处证据：

1. `_data_access.resolve_table_name`（`app/tools/_data_access.py:577`）在匹配失败时
   只返回 **3 个示例**（`_data_access.py:766` `examples = usable[:3]`），
   **没有「列出全部可用表」的正规入口**。模型据此无从判断「是真的没有这张表，
   还是我写法不对」。
2. 5 个带 `table` 参数的工具，docstring 一律写「缺省=主表」，把选择责任推给
   LLM 的隐含推断（如 `profile_data.py:25-26`、`plot_chart.py:212`）。
3. **SYSTEM_PROMPT 中没有任何一条关于「当前表 / 如何换表」的纪律条款**：
   `app/agent/agent.py:126-129` 的条目 5 讲的是「当前**数据集**」（换数据集会替换），
   表级选择完全依赖工具 docstring。
4. **UI 侧同样空白**：`app/ui/components.py:455` 明确「只做展示，不提供语义编辑
   入口」，全仓库搜索无任何选表控件。

**这与 LangChain `Issue #294` 暴露的是同一个坑**：列表阶段只给裸表名，
模型靠名字猜、猜错后拿到 schema 才发现，必须重来。业界主流对策是
**两段式：先枚举（表名 + 一行摘要）→ 再按名取**，且枚举信息不足会直接失效。

### 2.4 一个必须顺手修的独立缺陷

`app/agent/agent.py:264-289` 的 `_TOOL_DROPPABLE` **缺少 `compare_table_columns`
条目**，导致该工具走通用截断路径（`agent.py:315` 取到空元组、`agent.py:323`
调用 `enforce_output_limit`），其 `samples` / `result` 无法结构化降级——超预算时
会被整体硬截断，而非按优先级丢弃次要明细。与本设计无关，但同属表访问层，
应一并补齐（见 §6 阶段 5）。

## 3. 方案取舍

| 方案 | 做法 | 优点 | 致命代价 |
|---|---|---|---|
| **C-1 全并列** | 删除 `context.df` / `dataset_id` 的单数语义，改为 `context.tables: dict[str, DataFrame]`，所有工具 `table` 变**必填** | 语义最干净，「对等处理」最彻底 | ① 13 个无 `table` 参数的工具全要加参数；② 38 处 `context.df` 读取点全改；③ 4 个测试夹具的构造函数签名全改；④ `check_dataset_quality` 需重构成「逐表质检」并新增跨表汇总口径；⑤ SYSTEM_PROMPT 需大幅重写；⑥ **LLM 侧风险最大**：`table` 必填意味着模型每次都得精确猜表名，空手调用会硬失败，比「猜错但有默认」更糟 |
| **C-2 默认提名** | 保留 `context.df` 与「缺省=主表」，新增 `list_tables` 工具（全表清单 + 规模 + 语义线索 + 是否当前缺省）、`set_default_table` 工具（显式切换缺省表）、UI 选表控件；`check_dataset_quality` 增 `table` 参数；SYSTEM_PROMPT 增表纪律 | **零语义破坏**，改造成本约 1/3；直接消灭「主表猜错由用户承担」与「换表机制不可见」两处不便；模型先 `list_tables` 再取表，**歧义为零** | 「单一主表」概念仍在——但已从「隐含默认」变为「显式提名 + 可枚举候选」，这是业界公认的合格形态 |
| **C-3 常驻全表** | `load_dataset` 把全部小表驻留内存，`resolve_table_name` 缺省时按问题关键词选择 | 减少 IO | 违背 `AGENTS.md` §5「上下文节俭」；多表驻留放大内存；**缺省选择引入 LLM 判断**，违反「确定性计算优先」原则 |

### 3.1 采纳 C-2 的理由

C-1 用「最贵的架构改动」换取了 C-2 同样能达成的「歧义为零」。而 C-1 最重的那部分
（`context.tables` 字典 + 全工具必填 `table`）恰恰是**唯一无法通过小步交付验证**
的部分——一旦改错，13 个工具同时失效，无法按 AGENTS.md §3.5「小步交付」原则
逐工具回归。

C-2 则把收益集中在真正缺口的环节。**现状的失败模式从来不是「存不下多张表」**
（`meta.streams` 早就登记了全部表，`resolve_table_name` 早就支持按名读取），
**而是「模型不知道有哪些表、不知道当前是哪张、换表没有确定性入口」**——
这三件事全在「取表」侧，与「存表」的数据结构无关。

## 4. 方案 C-2 详细设计

### 4.1 新增 `list_tables` 工具

> 定位：给模型一个**确定性的、可枚举的**表清单入口，替代「靠 docstring 暗示
> 缺省是主表」的隐式约定。

**返回结构（每条目的字段）**：

| 字段 | 说明 |
|---|---|
| `table_name` | 规范名，**可直接传给 `table` 参数** |
| `rows` / `cols` | 规模（供模型判断「这是明细表还是汇总表」） |
| `kind` | 语义类别（`actions` / `joint_state` / `imu` / `wrench` / …） |
| `semantic_label` | 中文语义标签（来自流登记表） |
| `label_confidence` | 标签置信度（`low` / `medium` / `high`） |
| `is_default` | 是否为当前缺省表（**必填，是消除歧义的核心字段**） |

另含汇总字段：`n_tables`、`default_table`、`dataset`。

**实现纪律**：

1. **命名口径必须复用唯一生成点** `inspect_streams._usable_table_name`
   （`app/tools/inspect_streams.py:31-56`）——它已实现「有子流 → `stem::sub`
   不含扩展名」「无子流 → 纯文件名」的规则。**不得另写一套**，否则
   `list_tables` 给的 `table_name` 与 `resolve_table_name` 的接受集不一致，
   会重演 2026-09-20「清单与容错自相矛盾」的事故（`docs/表访问与跨表运算改造设计.md:35-43`）。
2. **体积护栏内建**：表数超阈值时按 `rows × cols` 降序遍历并截断，
   同时置 `truncated=True` + `truncation_note`（对齐 SYSTEM_PROMPT 条目 11
   的截断纪律，`agent.py:143-146`）。
3. **只读 `meta.streams`，不读表内容**（零 IO 成本，与 `inspect_streams` 同档）。
4. `_TOOL_DROPPABLE` 登记可丢字段（如 `tables` 明细列表），保 `n_tables` /
   `default_table` 等结论字段。

**为什么这是第一步**：它在**不触碰任何既有语义**的前提下，把「模型不知道有哪些表」
这一最实际的缺口补掉——零回归风险，可独立验收。

### 4.2 `resolve_table_name` 补三处

1. **匹配失败时返回完整候选清单**：除现有 3 个示例外，新增
   `available_tables: list[str]`（受体积上限约束）与 `default_table: str`，
   使模型能据清单自我纠正，而非直接放弃。现状只给 3 个示例
   （`_data_access.py:766`），模型无从判断「是不是真没有」。

2. **错误 `user_message` 明确写出当前缺省表**：消除「不知道当前在用哪张」的困惑。
   文案同时保留既有的「表名形如 `<文件stem>::<节点>`，不含扩展名」格式说明
   （`_data_access.py:768-771`）——该说明是 2026-09-20 事故的直接修复，不得回退。

3. **匹配语义保持既有纪律**：**不做模糊 / 子串猜表**（防误命中，
   `docs/表访问与跨表运算改造设计.md:83-84`）。子串匹配仅在既有的
   `streams` 过滤参数中保留。

### 4.3 新增「切换缺省表」能力

**接口**：`set_default_table_impl(context, table: str) -> dict`

**行为**：

1. 先经 `resolve_table_name` 校验（**必须真的能读出来**，而非只在登记表里存在）
   ——表不存在或读取失败时返回结构化错误，**不静默回退主表**（静默回退是最坏
   的失败模式：模型以为换成功了，实际上还在分析旧表）；
2. 成功后更新 `context.df` 与 `meta.main_table.selected`，并同步
   `meta.main_table.selection.reason` 标注为「用户显式提名」（与「行×列最大」
   的自动判据区分开，保持来源可追溯）；
3. 返回 `previous` 与 `current` 两个表名，供如实告知用户；
4. **切换只改「缺省」，不改「并集」**：所有非缺省表仍经 `resolve_table_name`
   按名读取，不做任何替换（沿用 `docs/ARCHITECTURE.md:112-124` 的既有语义）。

**持久化**：建议跟随 `profile_store` 的既有范式
（`outputs/by_dataset/<净名>/profile.json`，带 `user_confirmed` 来源标记，
`app/tools/profile_store.py`），使「用户提名的表」跨会话生效。这样加载完成后
agent 只需读取 `meta.main_table`，**无需每次询问用户想分析哪张表**——
这正是「猜错由用户承担」的反面：不是让选择更聪明，而是让选择可记忆。

**边界（不做的事）**：不让缺省表选择依赖 LLM 判断。判据只有两个——
确定性的「行×列最大」（自动），或用户的显式提名。**LLM 不得自行「推断用户想要哪张表」
并直接切换**（违反 `AGENTS.md` §3.4「LLM 假设不得替代工具验证」）。

### 4.4 `check_dataset_quality` 增 `table` 参数

当前它无参数、内容全读主表（`check_dataset_quality.py:921`），是**唯一无法对
非主表做质检**的分析工具。补 `table` 参数并在返回的 `measurements` 中标注
**实际检查对象表名**。

**必须保持的既有行为**：无主表时（`df is None/empty`，`check_dataset_quality.py:927`）
把 `main_table` 标 `skip` 并列入 `not_audited`（`:929-934`），**不得改为报错**——
纯媒体数据集「无有效主表」是合法状态。

这是多表并列最实在的一处补全：真实场景中「末尾表的位置数据是否合理」
与「主时钟表的时间戳是否单调」需要分别质检，而现在只能质检后者。

### 4.5 UI 选表入口

在数据集状态面板（`app/ui/components.py:428-448` 的 `_render_main_table` 所在区，
调用点 `components.py:504-507`）增加表选择控件：

- 列出全部表（表名 + 规模 + 语义标签）；
- 用户点选后，经 `add_context_note`（`app/services/chat_service.py:291`）
  投递「用户已把缺省表切换为 X」的事件便签；
- 便签机制与既有 `data_loader_panel.py:47-52` 的加载便签**完全同构**。

**为什么必须投递便签**：否则会出现「用户已换表但模型不知情」的脱节——
这正是 2026-09-07 面板事件缺陷（`chat_service.py:294-299` 的 docstring 记载）
的同类风险：工具层状态更新了，模型认知没更新。

**分层纪律**：`components.py:455` 的「只做展示，不提供语义编辑入口」注释需相应
更新，但**不得把写操作引入 UI 层**——落盘仍走 `services` / 工具层
（`AGENTS.md` §3「分层纪律」）。

### 4.6 提示词与文案

**SYSTEM_PROMPT 新增一条表纪律**（编号接在现有 18 条之后），要点：

1. 涉及表的分析必须**显式说明表名**；不确定有哪些表时**先调 `list_tables`**
   确认，不要凭文件名猜测（与条目 9「假设标注纪律」同构）；
2. 引用统计结果时注明**表名 + 数据集**（与条目 5 的数据集标注同构，
   `agent.py:126-129`）；
3. **不得在未确认时假设缺省表就是用户想分析的表**；当用户的问题涉及
   非缺省表时，先 `list_tables` 找到对应表名再传 `table` 参数；
4. 切换缺省表属**用户决策**，须经用户明确同意后才调 `set_default_table`，
   并如实转述 `previous` / `current`。

**文案统一**：面向用户的措辞把「主表」改为「当前缺省表」或「默认表」，
减少「主表意味着最重要」的误导。

## 5. 与方案 C（技术债原文）的差异说明

| 维度 | 方案 C（技术债原文） | 本方案 C-2 |
|---|---|---|
| 主表概念 | **取消**，「多表并列对等处理」 | **保留**，但从「隐含默认」变为「显式提名 + 可枚举候选」 |
| `context.df` | 删除，改 `context.tables: dict` | 保留，语义不变（仍是「缺省表」） |
| 工具 `table` 参数 | 全部工具必填 | 保持可选（缺省=缺省表），另有 1 个工具补上该参数 |
| 歧义消除手段 | 靠「无默认」强制显式 | 靠「可枚举清单 + 当前缺省标注」消除歧义 |
| 改动面 | 13 个工具 + 38 处读取点 + 测试夹具 | 1 个新工具 + 1 个新能力 + 1 个工具补参数 + UI 控件 |
| 可否小步验收 | 否（一次全改） | 是（5 个独立台阶） |

**关键判断**：方案 C 原文的暂缓理由（`docs/技术债.md:92-94`）指出「会让每个工具
都要处理『多张表』的歧义（缺省分析哪张？统计口径如何合并？UI 如何展示？）」。
本方案的价值在于：**这三个问题都不需要通过「取消主表」来解决**——
「缺省分析哪张」由显式提名 + `is_default` 字段回答；「统计口径如何合并」本就不该
由工具层自动合并（`compare_table_columns` 已提供按对齐键的显式逐行运算，
且 `docs/表访问与跨表运算改造设计.md:161-169` 已确立「不对齐就不算」纪律）；
「UI 如何展示」由控件 + 便签回答。

## 6. 实施顺序与验收

| 阶段 | 内容 | 验收 | 风险 |
|---|---|---|---|
| 1 | `list_tables` 工具 + `_TOOL_DROPPABLE` 登记 | 表清单与 `inspect_streams.table_name` **完全一致**；超阈值截断并如实声明 | 低 |
| 2 | `resolve_table_name` 返回完整候选 + 缺省表标注 | `table_not_found` 时模型能据 `available_tables` 自行纠正 | 低 |
| 3 | `set_default_table_impl` + UI 选表控件 + 事件便签 | 切换后 `context.df` 与 `meta.main_table` 同步；模型从便签得知切换 | 中（涉及状态写入） |
| 4 | `check_dataset_quality` 增 `table` 参数 | 能对非缺省表出质检结论，且返回注明检查对象；无主表时仍标 `skip` | 中 |
| 5 | 补 `compare_table_columns` 的 `_TOOL_DROPPABLE` 条目 | 与 `tests/test_output_guard.py::test_droppable_table_covers_all_tools` 的覆盖守护一致 | **极低（独立修复）** |
| 6 | 提示词与文案统一 | 无「主表」歧义措辞残留 | 低 |

**每阶段完成后跑全量回归，零回归是硬要求**（沿用
`docs/表访问与跨表运算改造设计.md:196` 的既有纪律）。

### 6.1 实施结果

**阶段 5 已完成**（commit `98918ac`）。实施中发现原覆盖测试只校验 8 个历史工具、
而注册工具已增至 19 个——中间新增的全部漏配而测试不报。已改为从 `_ALL_TOOLS`
动态取名单守护，新增工具漏配会直接失败。

**阶段 1 已完成**。新增 `app/tools/list_tables.py`，注册进 `_ALL_TOOLS`（UI 与 CLI
各 20 个工具，`tests/test_tool_registry_consistency.py` 守护同步）。实施中实测
发现**两处本设计未预见的事实**，均已修正并加回归测试：

1. **`meta["main_table"]["name"]` 不是可靠的表名。** 两条加载路径的 meta 形态不同：
   目录型是 `{name: "state.csv", selection: {selected, candidates:[{name,nrows,ncols}]}}`
   （`name` 可直接用作表名）；单文件型是 `{name: "state/joint", candidates:[{table_name,
   rows,cols}]}`——`name` 是**裸节点路径，不能用作表名**，可用名在
   `candidates[*].table_name`。若直接读 `name`，HDF5/MCAP 场景下 `is_default`
   **恒为 False**，恰恰是最需要它的场景（几十个节点分不清当前是哪张）。
   现已统一从 candidates 反查可用名。
2. **规模字段的来源也随路径而变**：流登记项的 `n_rows`/`n_cols` 只在容器子流上
   存在，独立文件流恒为 `None`，规模权威在 candidates（两处位置不同，已合并取用）。
   未修正前模型看到的全是 `rows: None`，本工具"给出规模"的核心价值归零。

另注意 `tasks.csv` 这类 2 行表会被 `EMPTY_STREAM_MAX_ROWS=2`（`_sniffing.py:59`）
判为 `status="empty"`。本工具**仍在清单中列出**它但标 `usable=False`——用户需要
知道该文件存在，只是不适合统计。

阶段 1 新增测试 `tests/test_list_tables.py`（14 项，含真实 HDF5 单文件加载的
端到端回归）。全量回归 **1230 passed / 1 skipped**，零回归。

**阶段 2 已完成**。`resolve_table_name` 的错误路径与缺省表名解析全面加固，实施中
**又发现一处同源的既有缺陷**（比设计预想的更严重，故一并修复）：

3. **`resolve_table_name(context, None)` 返回的 `table_name` 也是裸节点名。**
   该函数缺省路径直接读 `meta["main_table"]["name"]`（`_data_access.py:624` 原实现），
   于是 h5/mcap 数据集下返回 `"state/joint"` 这个**无法回用**的假表名——而它会被
   写进 `profile_data` / `compute_stats` / `plot_chart` 等每一个工具的结果标注里，
   扩散给模型和用户。这是与缺陷 1 同源、但**影响面更大**的一处：缺陷 1 只污染
   `list_tables` 的展示，缺陷 3 污染所有分析结论的"分析的是哪张表"标注。

   修复方式：抽出**唯一权威实现** `_data_access.resolve_default_table_name()`，
   由它统一处理"目录型读 `selection.selected`、单文件型从 candidates 反查
   `table_name`"的分支；`list_tables` 与 `resolve_table_name` 都改为调用它，
   **彻底消除两处口径分叉的可能**（口径分叉会导致"清单说 A、实际分析 B"的静默
   错位，比报错更危险）。同时抽出 `main_table_candidates()` 统一候选位置差异。

   错误路径也按设计增强：表不存在时除原有 3 个示例（`available_examples`，
   保留向后兼容）外，新增 `available_tables`（**完整可用清单**，上限
   `_MAX_AVAILABLE_TABLES=60`，超限截断并如实声明总数）、`default_table`，
   `user_message` 明确指出"若想分析主表，不传 table 参数即可（当前缺省表是 X）"
   并提示可用 `list_tables`。**纪律不变：仍不做模糊/子串猜表**——给清单是为了让
   模型自我纠正，不是替它做匹配（子串能命中的写法必须仍然失败）。

   另修正候选清单口径：视频不再列入 `available_tables`（与 `n_table_streams`
   一致），同一 path 重复登记时去重。

阶段 2 新增测试 `tests/test_resolve_table_candidates.py`（14 项，含"缺省表名必须
可回用"的闭环断言与"不做模糊匹配"的纪律回归）。全量回归
**1244 passed / 1 skipped**，零回归。

**跨表对齐的既有防护不得削弱**：`compare_table_columns` 的「按组内序号配对、
重复模式不一致时如实拒绝」（`app/tools/compare_table_columns.py:99-128`）
是 2026-09-20 笛卡尔积事故（实测 28270 行变 56540 行）的直接修复，
可考虑进一步引入 pandas 官方的 `merge(validate=...)` 作为显式前置校验，
但**不得移除现有防护**。

## 7. 发起建议

鉴于触发条件尚未满足（§1.2），建议：

1. **按技术债既有结论继续暂缓方案 C**，本设计作为已评审的预备方案归档；
2. **立即执行阶段 5**：补 `compare_table_columns` 的 `_TOOL_DROPPABLE` 条目
   ——零风险的独立缺陷修复，与方案 C 的决策无关；
3. **择机执行阶段 1**：`list_tables` 工具能在不触碰任何语义的前提下，
   把「模型不知道有哪些表」这一最实际的缺口补掉；
4. **阶段 2–4 待真实需求出现再启动**——例如同一次对话里明确要求
   「对两张以上表分别做质检」或「换到某张表再分析」。

## 8. 明确不做的事（边界）

- 不引入 `context.tables` 全并列表，不让工具 `table` 参数变必填
  （方案 C-1 的核心，收益不足以抵偿 13 个工具的连锁改动）；
- 不做模糊表名匹配（防误命中）；
- 不做单位自动换算；
- 不做「差值是否合格」的判定（阈值属验收标准，不在工具职责内）；
- 不让缺省表选择依赖 LLM 判断；
- 不在 UI 层引入写操作（落盘仍走 services / 工具层）；
- 不移除 `compare_table_columns` 的既有一致性防护。

## 9. 调研参照（业界做法）

| 参照 | 关键结论 | 对本设计的影响 |
|---|---|---|
| LangChain `SQLDatabaseToolkit` | 工具描述**硬编码**「先 `list_tables` 确认表存在，再取 schema」的调用约束——**提示层约束而非代码层容错** | 支持「两段式：先枚举后取」；本设计进一步把它落为**工具**（`list_tables`），而非仅靠 docstring 提醒 |
| langchain-community `Issue #294`（2025-02-07） | `sql_db_list_tables` 只返回**裸表名**，模型靠名字猜错表，拿到 schema 才发现必须重来 | **直接支撑 §4.1 的设计**：枚举阶段必须给「表名 + 规模 + 语义标签」，不能只给裸名 |
| LlamaIndex Text-to-SQL Guide | 表数超上下文时用向量检索 top-k 剪枝 | 本项目表数量级（数十条流）远低于需检索剪枝的规模，故仅用阈值截断，不引入检索 |
| OpenAI Function Calling 指南 | 单次工具不宜超过 20 个；10–20 个时模型选对工具的能力明显下降；参数用 enum / 清晰命名避免歧义；**遇到歧义应主动澄清而非臆测** | 本项目现有 19 个工具**已逼近 20 的上限**——新增工具需谨慎（本设计只加 2 个工具，其中 1 个是切换能力）。这也是**反对方案 C-1（会显著增加参数复杂度）**的一条外部依据 |
| MCP 规范（resources vs tools） | resources 是**应用驱动**、必须可枚举（`resources/list`），且集合 MUST NOT 随连接变化；tools 是**模型驱动** | 支持「候选清单应是稳定的可枚举对象」，而非隐含默认 |
| pandas 官方合并文档 | many-to-many 键合并产生**笛卡尔积**，官方明确警告可能内存溢出；提供 `validate=` 参数在合并前校验键唯一性 | 印证 `compare_table_columns` 现有防护的正确性；建议考虑补 `validate=` 作为显式前置校验 |
