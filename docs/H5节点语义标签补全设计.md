# H5 节点语义标签补全设计（state/* 与 extrinsic 外参）

> 状态：**已实施**（2026-09-21 用户确认 A+B 一起修；全量测试 1201 passed / 1 skipped）
> 上游文档：`docs/H5节点形态接纳设计.md`（该文档解决"节点是否登记"，
> 本文档解决"登记后的 kind/语义标签是否正确"）
>
> **实测结果**：`unknown` 49 → 20，且剩余 20 条**全部是 `status="empty"` 的
> 合法空流**，非空的未分类流为 **0 条**。新增 kind：`joint_state`(11)、
> `status`(5)、`effort`(3)、`wrench`(1)、`calibration`(5)。

## 1. 问题陈述

修复帧内标量时间戳（上次）后，真实数据集 `2655849` 的流登记表暴露出
**语义标签**层面的两个缺口。实测 106 条流的 kind 分布：

```
{timestamp_index: 16, unknown: 49, actions: 8, video: 8, log: 24, pose: 1}
```

先排除**不是缺陷**的部分，避免误修：

- **`log` 24 条**：`camera_dlb.INFO`、`dds_record.INFO` 上的运行日志，被正确
  解析为「1,263 行 × 5 列，时间列 `time_of_day_us`」，标签「运行日志（含时间与
  消息）」准确。**不动**。
- **`unknown` 里的 20 条空流**：`*_manifest.json`、`intrinsic_*.json`、
  `struct_chassis.json` 等，行数 ≤ 2，被如实判为「未使用/空流」。**不动**。

真正的问题是 `unknown` 里的 **29 条"真未知"**，分两个缺陷。

### 1.1 缺陷 A：24 条 h5 `state/*` 遥测流全部误报"未知"（严重）

```
state/joint/position    14135 行 × 14 列   → 未知
state/waist/effort      14135 行 ×  5 列   → 未知
state/end/wrench        14135 行 × 12 列   → 未知
state/end/errcode       14135 行 ×  1 列   → 未知
state/head/mode         …                  → 未知
（共 24 条，全部是 14135 帧的真实遥测）
```

**根因**（已复现）：`_classify_h5_node` 的位姿分支判据是

```python
if "pose" in path_l or any("quat" in f for f in fl):
```

但帧布局下这些节点是**裸 ndarray**，`_classify_h5_leaf` 为其返回
`fields=[]`，故 `any("quat" in f for f in fl)` **恒为 False**；而
`state/joint/position` 的路径又不含 `pose`。两者皆不成立 → 落到 `unknown`。

实测复现：

```
_classify_h5_node([], 'state/joint/position')  -> ('unknown', '未知（无法分类）')
_classify_h5_node([], 'state/end/orientation') -> ('unknown', '未知（无法分类）')
_classify_h5_node(['position_0','quat_w'], 'state/end/orientation') -> ('pose', '位姿流')
```

**一致性反证**：同一份数据的 `action/joint/position` 被正确识别为动作流
（路径含 `action`，命中最前一条分支），而 `state/joint/position` 落空。
同类数据一半识别、一半不识别，属明确逻辑漏洞。

**连带损失**：`wrench`（力/力矩）、`effort`（关节力矩）、`mode`/`errcode`
（控制器状态码）这些**语义重要**的流全部无法被用户与模型区分。

### 1.2 缺陷 B：5 条 `extrinsic_*.json` 相机外参未识别（次要）

```
extrinsic_end_T_hand_left_rgbd_aligned.json
extrinsic_end_T_*_rgbd_aligned.json                       （共 5 条）
```

命名中的 `end_T_hand_left_rgbd_aligned` 是"末端 → 相机"的变换矩阵，
语义明确为**相机外参标定**。工具 evidence 自承"判不出，未做硬猜"。

**根因**：这 5 个文件走的是 ``_sniffing.classify_table_stream``（**独立表格
文件路径，不是 h5 节点路径**——首次修复时误在 `_classify_h5_node` 里加规则，
实测无效才发现走错了函数）。`classify_table_stream` 只认列名词典与内容指纹，
而这 5 个文件是变换矩阵数组、没有"列名"可言 → 两个层级都无从下手 → unknown。

**实测修正的重要事实**（与初判不同）：真实 `extrinsic_*.json` 并非小文件——
它是 **4.1 MB / 14135 行的 list**（逐帧变换矩阵，与 h5 帧数一致），
`read_table_nrows` 正确返回 14135，**非空**。而真实 `intrinsic_*.json` 是
**192 字节的单 dict（0 行）**，落在空流阈值内。

故实际行为是：5 条 `extrinsic` → `calibration`（非空），
14 条 `intrinsic` → 保持"未使用/空流"。后者符合本设计 §2.2 的"空流优先"
决定——给 0 行文件贴"相机内参"会夸大其可用性。

## 2. 设计

### 2.1 缺陷 A：为 `state/*` 补路径判据

在 `_classify_h5_node` 中新增 `state/*` 的**路径优先判定**，不再依赖恒为空的
`fields`。按叶子名归类（词表见实现）：

| 叶子名特征 | kind | 语义标签 |
|---|---|---|
| `pose` / `orientation` / `arm_position` / 含 `position` 且路径含 `end` | `pose` | 位姿流 |
| `wrench` / `force` / `torque` | `force` | 力/力矩流 |
| `effort` / `current` / `motor_current` | `effort` | 关节力矩/电流流 |
| `mode` / `errcode` / `status` / `state_code` | `status` | 控制器状态流 |
| `position` / `qpos` / `velocity` / `qvel` / `acceleration` | `joint_state` | 关节状态流 |

**关键约束**：判定顺序必须在 `action` 分支**之后**（`action/*` 已有正确标签，
不得被 `state` 规则抢走），且在 `timestamp_index` 分支**之前**或之后需保证
互斥（`state/` 路径已被 timestamp 分支的路径白名单显式排除）。

**诚实性约束**：这些标签是基于路径的**语义假设**（`label_confidence` 保持
`medium`），按 `AGENTS.md` §3.4「LLM 假设不得替代工具验证」，标签仅用于让
用户/模型看懂清单，**不代表该流已被验证**，更不得用于数值计算。此约束写入
`label_evidence` 文案。

### 2.2 缺陷 B：`extrinsic_*` 归入标定

扩展 `calibration` 分支的判据，除 `calibration` 外同时接受
`extrinsic` / `intrinsic` / `_T_`（变换矩阵命名惯例）。标签区分：

- 含 `extrinsic` 或 `_T_` → 「相机外参（变换矩阵）」
- 含 `intrinsic` → 「相机内参」
- 其余 → 「标定数据」

**边界**：`intrinsic_*.json` 当前被判为空流（20 条空流之一）——本设计**不改**
空流判定，只改语义标签。即：空流仍标"未使用/空流"，但若它同时是标定文件，
`semantic_label` 采用标定标签（优先级高于空流占位）——**待实现时确认**，
若冲突则保持空流标签不变（更保守，避免给空文件贴有意义的标签）。

> 实施决定：**保持空流标签优先**。空流的 `semantic_label` 是"未使用/空流"，
> 其 `label_evidence` 已如实说明行数。给 0 行文件贴"相机内参"会夸大其可用性。
> 故 B 只对**非空**的 `extrinsic_*` 生效。

## 6. 实施中发现的遗留缺口（**未修**，另案）

修复过程中通过真实数据实测发现一个**与 A/B 同类但独立**的缺口，此处如实登记：

**27 条 action/state 流无法与主时钟建立帧↔时间映射。**

实测 `align_container_streams` 对 aligned_joints.h5 的结果：

```
n_with_timestamp: 7 / 40
main_timestamp           status=ok            span=471.14s
action/joint/position    status=no_timestamp
state/end/pose           status=no_timestamp
state/joint/position     status=no_timestamp
（其余 26 条 action/state 同为 no_timestamp）
```

这 27 条流与 `main_timestamp` **共享同一 14135 帧**（`frame_index` 逐帧对应），
在事实上是可时间对齐的，但工具报 `no_timestamp`，理由是"子流无时间戳字段"。

**为何本次不修**：这不是标签问题，而是**读取层缺少"帧号 → 主时钟"的映射
机制**——需要让 `_H5Reader.timestamp()` 在帧布局容器里，当子流自身无时间戳列
时回退到同容器的 `main_timestamp`（按 `frame_index` 连接）。这涉及：
① 帧布局上下文如何传递到 reader；② 回退的适用边界（仅当帧数严格一致时）；
③ 是否要在返回里标注"时间轴来自容器主时钟而非该流自身"（诚实性要求）。
改动面明显大于 A/B，且属**新功能而非缺陷修复**，按 `AGENTS.md` §3.4 应先立
设计文档。建议单独立项，不要与本次语义标签混在一个改动里。

**当前后果**：用户问"h5 内部各子流对齐如何"时，只能得到 7 条时间戳流的
对齐结果，27 条 action/state 流的帧↔时间关系仍不可得。上次会话中 agent
回答"h5 内部只能靠帧索引对齐"这句，在**这个具体层面**仍然是事实。
