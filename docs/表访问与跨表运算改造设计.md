# 表访问与跨表运算改造设计

> 状态：**已实施**（2026-09-20 起草并落地；用户确认"问题1直接修，问题2做 A+B，C 列技术债"）
> 背景：UMI / 2655849 数据集实测中暴露的两类问题。本文只覆盖已确认要做的范围；
> 架构级的"多表并列"方案列入技术债，见第 5 节。
>
> **实施结果**（详见 `docs/行为测试.md` 对应章节）：
> - 表名容错：四种写法（仅节点名 / stem::节点 / 带扩展名 / 完整路径）全部可用；
>   错误提示给出真实可用示例；`inspect_streams` 补 `table_name` 字段。
> - 主表口径：h5 单文件主表从 **(2, 4) 修正为 (14135, 15)**，与流登记表同口径。
> - 主表透明化：`meta.main_table` 增 `candidates` 与 `alternative_hint`。
> - 跨表运算：新增 `compare_table_columns`（diff / distance / ratio）。
> - **实施中发现并修复一个额外缺陷**：对齐键可能**不是唯一键**（如 `frame_index`
>   每帧重复 2 次表示左右两侧），直接 merge 会产生**笛卡尔积**（实测 28270 行
>   变 56540 行），统计建立在错误配对上。现改为按**组内序号**配对，并在两侧
>   重复模式不一致时如实拒绝。

## 1. 问题陈述（实测复现）

### 1.1 问题一：h5 子流"读不出来"——实为表名格式陷阱

真实对话中 agent 尝试读取 `aligned_joints.h5` 的 `state/end/position`（末端位置）
后回答"工具读不出来"，并转向要求用户导出 CSV。实测该节点**完全可读**（28270 行），
失败原因是表名写法：

| 写法 | 结果 |
|---|---|
| `state/end/position`（仅节点名） | ✅ 成功 |
| `aligned_joints::state/end/position` | ✅ 成功 |
| `aligned_joints.h5::state/end/position` | ❌ `table_not_found` |
| `C:\...\aligned_joints.h5::state/end/position` | ❌ `table_not_found` |

**根因是"清单与容错自相矛盾"**：

1. 错误提示说"请用流登记表 / inspect_streams 的表名清单"；
2. 但 `inspect_streams` 的 `table_streams[].source` 是**完整绝对路径**
   （`C:\...\aligned_joints.h5::state/end/position`），且没有 `table_name` 字段；
3. agent 照清单抄 → 必然失败；错误提示又**未给可用表名示例、未说明不能带扩展名**
   → agent 反复试错 → 得出"工具不具备该能力"的错误结论。

**这是"能力可达但被表述掩盖"的缺陷**，与真实能力缺失是两回事。

### 1.2 问题二：主表机制的三类问题

**（a）真实 bug：h5 单文件加载的主表只有 1 帧数据**

实测：加载 `aligned_joints.h5` 后 `context.df.shape == (2, 4)`，主表节点为
`0/action/end/orientation`——**14135 帧中的第 0 帧**。

根因：选主表的 `_load_hdf5_native` 走**旧的全量遍历路径**，未使用后来为
"每帧一组"布局实现的 `_merge_frame_layout`；它看到的行数是**单帧行数**，
而流登记表已是**合并后行数**。两处口径不一致。

后果：基于主表的统计 / 绘图只覆盖 1 帧；`profile_data` 缺省调用返回
"2 行 × 4 列"，与 `inspect_streams` 报的 28270 行矛盾。

**（b）主表是自动猜的，猜错由用户承担**

主表按"行×列最大"选择，但该判据不知道用户意图。用户关心的（末端位置、
关节角、触觉）往往不是最大的那张表。当前须每次显式传 `table`，而 agent
未必知道该传什么，也无从得知"为什么选了这张"。

**（c）跨表运算能力缺失**

"实际末端 vs 指令末端相差多少"这类问题需要**同时读两张表 + 逐行运算**，
但 `profile_data` / `compute_stats` 都只做**单表单列聚合**，无任何工具支持
两表对齐后的行级运算。这不是配置问题，是能力缺口。

## 2. 方案一：表名容错与提示自洽（对应问题一）

### 2.1 表名解析容错

在 `resolve_table_name` 的匹配环节放宽（**只放宽候选生成，不改变匹配语义**）：

- 对 `"<file>::<sub>"` 形式的输入，若 `file` 部分带扩展名（`.h5`/`.hdf5`/`.mcap`），
  用 **stem** 再匹配一次；
- 若 `file` 部分是**绝对/相对路径**，用其 **name 的 stem** 再匹配一次。

匹配优先级：原始字符串精确匹配 → stem 派生匹配。**不做模糊/子串猜表**
（避免误命中；子串匹配仅在既有 `streams` 过滤参数中保留）。

### 2.2 错误提示给出可直接使用的示例

`table_not_found` 的 `user_message` 增加：

- **3 个真实可用的表名示例**（取自当前数据集的流登记表，用实际可用的 `table_name` 格式）；
- 一句格式说明："表名形如 `<文件stem>::<节点>`，**不含扩展名**"；
- 保留"用 inspect_streams 查看完整清单"的指引。

### 2.3 `inspect_streams` 补 `table_name` 字段

`table_streams` / `video_streams` 等条目新增 `table_name`（**可直接传给 `table`
参数的规范名**），与既有 `source`（完整路径，供溯源）并存。

**为什么两个字段都要**：`source` 面向"这个流来自哪个文件"的溯源需求；
`table_name` 面向"我要读它"的调用需求。此前只有 `source`，导致 agent 拿溯源
字段去当调用参数——这是本次缺陷的直接诱因。

## 3. 方案二 A：主表口径修复与选择透明化（对应问题二 a/b）

### 3.1 修主表口径不一致

`_load_hdf5_native` 改为**复用** `_list_hdf5_native_nodes`（已含帧布局合并），
使"选主表的行数口径"与"流登记表口径"一致。

- 修后主表应是 `action/joint/position`（14135 × 14）这类真实规模节点；
- `h5_structure` 元信息同步使用合并后的行数，消除与流登记表的矛盾。

### 3.2 主表选择透明化

`load_dataset` 返回与 `meta.main_table` 增加：

- `selected`：选中的表名（已有）；
- `reason`：为什么选它（已有，保留）；
- **`candidates`**：按同一判据排名的前 N 个候选（表名 + 规模），
  供 agent 判断"用户想要的表是否在候选中"；
- **`alternative_hint`**：一句提示——"如需分析其他表，用 `table` 参数指定
  （表名见候选清单或 inspect_streams 的 `table_name`）"。

**边界（不做的事）**：不改变"自动选一张主表"这一机制，也不让主表选择依赖
LLM 判断——判据仍是确定性的（行×列）。透明化的目的是让 agent 与用户**看得见**
选择结果与备选，而不是让选择更"聪明"。

## 4. 方案二 B：新增跨表逐行运算工具（对应问题二 c）

### 4.1 工具定位

新增工具 `compare_table_columns`：

> 按**对齐键**（缺省 `frame_index`）将两张表对齐，对指定列做**逐行运算**，
> 产出差异统计与分布。

直接回答"实际末端与指令末端差多少""两条流的某个通道是否一致"这类问题。

### 4.2 参数设计

| 参数 | 说明 |
|---|---|
| `table_a` / `table_b` | 两张表名（走 `resolve_table_name`，支持 2.1 的全部写法） |
| `columns_a` / `columns_b` | 各表参与运算的列（**按顺序对应**，可省略取同名交集） |
| `op` | 运算类型：`diff`（逐元素差）/ `distance`（欧氏距离，需 2–3 列）/ `corr`（相关系数） |
| `on` | 对齐键列名（缺省 `frame_index`；无该列时报结构化错误并给出可用列） |

### 4.3 返回内容

- 对齐情况：对齐后行数、两表各自行数、**未匹配行数**（不静默丢弃）；
- 差异统计：均值 / 中位 / 最大 / 最小 / 标准差 / 分位数；
- **分布形态**：分位直方（decile）——"均值 5 cm"与"全部约 5 cm"和
  "大部分 0、少数 30 cm"是完全不同的结论，必须能区分；
- 样例行（前若干条，含两侧原值与差值），供核对；
- `user_message`：一句话结论 + 注明对齐键与参与列。

### 4.4 纪律（与项目既有约定一致）

- **单位不猜**：只做"同单位下的数值差"；两侧单位若可判定且不同，
  报结构化错误而非自行换算（换算需用户确认）；
- **不对齐就不算**：对齐键缺失 / 行数不匹配时如实报"无法对齐"，
  不做位置对齐（位置对齐会产出看似合理实则无意义的数字）；
- **未匹配不静默丢弃**：两侧行数不等时必须报出差值；
- **不做推断**：工具只产出数值统计，不判断"这个差值是否合格"
  （合格阈值属验收标准，不在工具职责内）。

## 5. 列入技术债：多表并列机制（方案 C，暂缓）

**方案 C（不在本次范围）**：取消"单一主表"概念，改为多表并列对等处理。

- **暂缓理由**：会让每个工具都要处理"多张表"的歧义（缺省分析哪张？
  统计口径如何合并？UI 如何展示？），影响面覆盖 `context.df` 语义、
  全部工具的缺省行为与 UI；在没有明确的跨表分析需求清单前，
  改动成本与收益不成正比。
- **触发条件**：出现"需要同时对三张以上表做同口径分析"的真实需求，
  或 A+B 实施后仍频繁出现"表选错/找不到表"的反馈。
- 详见 `docs/技术债.md`。

## 7. 不做的事（明确边界）

- 不做模糊表名匹配（防误命中）
- 不改"自动选一张主表"的机制
- 不做单位自动换算
- 不做"差值是否合格"的判定
- 不引入多表并列（列入技术债）
