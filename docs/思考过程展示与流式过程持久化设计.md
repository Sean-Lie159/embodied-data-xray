## 1. 需求（owner 原话转写）

1. **流式过程历史应当保留而非覆盖**——目前流式过程中"工具播报 + 正文增量"
   共用一个 `placeholder`，后者会**覆盖**前者的显示（`streamlit_app.py:_run_agent_turn`：
   工具播报写 `placeholder.markdown(...)`，随后正文 delta 又写同一个 placeholder）；
2. **思考过程也要保留**，且涵盖两个阶段：**思考进行中**与**给出输出结果后**；
3. **可用小箭头隐藏/展开**；
4. **独立框 + 滑动约束显示范围**（思考内容可能很长，需固定高度内滚动）；
5. **小字体现思考过程**，与正文**视觉区分**。

---

## 2. 关键可行性实证（2026-09-14 实测，已完成）

需求 2 能否实现，取决于**网关是否回传思考过程**。此前项目从未验证过这一点
（`docs/流式输出设计.md` 6 节甚至保守地写"不承诺思考 token 可见"）。故本次先做实测：

**探针结果**（真实调用，同一基准链路）：

```
event_types: {'raw_response_event': 35, 'run_item_stream_event': 2,
              'agent_updated_stream_event': 1}
reasoning_event_types: ['response.reasoning_summary_part.added',
                        'response.reasoning_summary_part.done',
                        'response.reasoning_summary_text.delta']
=> REASONING IS AVAILABLE
```

第二个探针（同一问题）取了文本样本：

| 项 | 实测值 |
|---|---|
| 思考摘要长度 | **631 字符**（分段输出，有 `part.added`/`part.done` 边界） |
| 正文长度 | 207 字符 |
| 思考摘要形态 | **可读的英文推理文本**（非加密/非空） |
| 输出方式 | `reasoning_summary_text.delta` 增量流 |

**结论：思考过程可以完整流式获取**——需求 2、3、4、5 全部可落地。

> **重要修正**：`docs/流式输出设计.md` 6 节"风险"表中原写
> "首字延迟未改善（思考阶段无输出）…本设计不承诺思考 token 可见（网关不透传）"。
> 该判断**现已被实测推翻**：网关**回传思考摘要**（是 summary 而非原始
> chain-of-thought token，故仍不可见"逐 token 级"思考，但**摘要文本可见**）。
> 本设计实施后应在该文档修正此条。

### 2.1 三个必须说清的边界

1. **拿到的是"思考摘要"（reasoning summary），不是原始思考 token。**
   摘要由模型侧生成，631 字符是真实样本；它**不等于**完整推理过程，可能省略细节。
   展示时应措辞为"思考摘要/推理摘要"而非"完整思考链"，避免误导。
2. **摘要不保证每轮都有。** 实测该轮有；但若网关/模型不产出 summary，
   事件序列中不会出现 reasoning 类型——UI 必须**优雅降级**（无摘要则不显示该区块，
   而不是显示空框）。这是硬性要求，见第 5 节。
3. **摘要语言与正文一致（英文）**，本项目正文也是英文语境下的中文回答——
   思考摘要实测为英文（模型内部推理语言），这是正常的，不需要翻译。

## 3. 现状问题定位（已核实代码）

### 3.1 流式过程被覆盖（需求 1 的根因）

```python
# streamlit_app.py::_run_agent_turn（现状）
placeholder = st.empty()
for chunk in service.reply_stream(prompt):
    if chunk.kind == "tool":
        placeholder.markdown(f"_{chunk.text}…_")     # 写 placeholder
    elif chunk.kind == "delta":
        acc += chunk.text
        placeholder.markdown(acc + STREAM_CURSOR)   # **覆盖**上面的工具播报
```

**同一个 `placeholder` 被反复整体覆写**，所以：
- 工具播报只在"下一次正文 delta 到来前"可见，正文一开始就被冲掉；
- 过程结束后 `placeholder.markdown(turn.reply)` 最终只剩正文——
  **中间过程（调了哪些工具、按什么顺序）在界面上完全消失**，
  只剩 `render_tool_activity` 折叠块里的一行摘要。

即：**不是"历史被丢弃"，而是"过程从未被持久保存"**——只有一个不断被覆写的格子。

### 3.2 思考过程当前被完全忽略

`stream_turn` 只识别两类事件：

```python
if etype == "raw_response_event":
    ... if "output_text" in str(dtype):   # 只取正文
elif etype == "run_item_stream_event":
    ... if _is_tool_call_item(item):      # 只取工具
```

`response.reasoning_summary_text.delta` **落在两个分支之外，被静默丢弃**。

## 4. 设计：过程时间线（Timeline）

### 4.1 核心思路：把"过程"变成有结构的记录，而非一个会被覆写的格子

**数据层**：在 `ChatTurn` 上新增**结构化过程记录**（不是纯文本），
让 UI 能分层渲染（思考小字 / 工具播报 / 正文）。

```python
@dataclass
class StreamEvent:
    """流式过程中的一条记录（供 UI 分层渲染与持久展示）。"""
    kind: str      # "reasoning" | "tool"
    text: str      # reasoning 的摘要增量文本 / tool 的功能描述
    tool_name: str = ""
```

`ChatTurn` 新增字段（**新增可选字段，零回归**）：

```python
steps: list[StreamEvent] = field(default_factory=list)   # 过程时间线（持久）
reasoning: str = ""                                       # 思考摘要全文（便于测试/导出）
```

**为什么不复用现有 `tool_activity` 字符串**：`tool_activity` 是
"调用工具: A → 调用工具: B" 的单行摘要（来自 `run_result`），
无法承载"思考摘要 + 工具 + 时序"的结构，也无法分层渲染。故新增 `steps`，
`tool_activity` **保留不动**（有测试依赖，且信息互补）。

### 4.2 事件采集（`app/agent/agent.py::stream_turn`）

新增对 reasoning 事件的识别与事件吐出的扩展：

```python
# reasoning 摘要增量（新增分支）
if "reasoning_summary_text" in str(dtype) and isinstance(delta, str) and delta:
    reasoning_acc += delta
    yield TurnEvent(kind="reasoning", text=delta)
```

`TurnEvent.kind` 扩展取值：`"delta" | "tool" | "reasoning" | "done"`。
`done` 事件携带 `reasoning` 全文与 `steps` 列表。

**关键设计：`part.added`/`part.done` 的处理。**
实测事件序列含 `reasoning_summary_part.added` / `.done`。
`part.added` 通常标志"新一段思考开始"——**用于插入段落分隔符**（`\n\n`），
使长摘要分段可读，而不是一大坨文本。这是"可读性"的关键细节。

### 4.3 流式过程中的实时渲染（需求 1 + 5）

用**多个独立占位符**替代单一 placeholder，让过程与正文**并存**而不互相覆盖：

```python
with st.chat_message("assistant"):
    # 1) 过程区（思考 + 工具播报）：独立容器，边生成边长
    with st.container(border=True):
        steps_box = st.empty()       # 累积渲染过程时间线
        # 2) 正文区：独立占位符（不再与过程共用）
    body_box = st.empty()
```

- 过程区**累积**渲染（不覆写）：每次 `reasoning`/`tool` 事件都**追加**到
  `steps` 列表后整体重渲（Streamlit 模式下这是实现"历史保留"的标准做法）；
- 正文区独立，只渲染正文增量。

### 4.4 思考过程的历史形态（需求 2/3/4/5 —— 核心）

过程结束后，`steps` 随 `ChatTurn` **写入 `messages`**（`_record_turn` 已把
turn 存入消息），因此**历史轮次也能回看**（此前只有当前轮有过程）。

渲染组件（新增 `app/ui/components.py::render_reasoning_and_steps`）：

```
┌─ 思考摘要 ▸ ──────────────────────────────┐   ← st.expander（小箭头折叠/展开）
│  The user wants a one-sentence answer...  │   ← 小字（st.caption 或 <small>）
│  Sampling rate refers to how many data    │   ← 独立框内滚动
│  points are recorded per unit of time...  │      (max_height ≈ 200px)
│  ─────────────────────────────────────    │
│  ▸ 正在检查时间同步                        │   ← 工具播报（同区，功能语言）
└───────────────────────────────────────────┘
```

**逐项对应需求**：

| 需求 | 实现 |
|---|---|
| 历史保留、不覆盖 | `steps` 存入 `ChatTurn.steps` → 随 `messages` 持久；每轮累计渲染 |
| 思考中 + 输出后都在 | 流式时实时追加渲染；结束后作为历史轮次重新渲染同一组件 |
| 小箭头隐藏/展开 | `st.expander("思考摘要", expanded=False)`（默认收起，需要时展开） |
| 独立框 + 滑动约束 | `st.container(border=True)` 包住 + `st.container(height=200)`（固定高度内滚动） |
| 小字区分 | 思考用 `st.caption`（Streamlit 的次要文本样式，字号小、颜色淡）；正文仍 `st.markdown` |

**默认收起还是展开（需 owner 定，见第 8 节）**：
默认收起（`expanded=False`）符合"思考过程不喧宾夺主"；但需求说"思考过程中"
也要能看到——可折中为：**流式进行中默认展开**（让人看到在思考），
**历史轮次默认收起**（回顾时按需展开）。

### 4.5 独立框的滚动约束实现细节

**已核实 API（本环境 Streamlit 1.61.1）**：
`st.container(border=True, height=200, autoscroll=True)` ——
`height` 为固定高度时容器内部滚动；
`autoscroll=True` 使**新增内容时自动贴底**
（官方语义：仅在固定高度容器生效；默认 `None` 时"固定高度且含
`st.chat_message` 才自动贴底"）。

**`autoscroll=True` 对本需求正好**：思考摘要是持续增长的流，
用户需要看到**最新**的思考内容而非开头——这与"正文区默认贴底"是同类需求。
**这是思考框必须显式设 `autoscroll=True` 的原因**（默认值在非 chat_message
容器上不会自动贴底）。

**风险：嵌套滚动可能产生"滚动陷阱"。**
`streamlit_app.py` 的 `_inject_scroll_css()` 已把 `.block-container`
设为 `overflow: hidden` 并给聊天容器固定高度。**嵌套滚动容器**（聊天区滚动
+ 思考框滚动）需在真实浏览器验证不出现"滚轮卡在子容器、无法滚到外层"的问题。

**风险应对（第 9 节详述）**：先真机验证；若出现滚动陷阱，
降级方案为——**不用 `st.container(height=N)`，改用 expander 自身折叠**
（点击小箭头即看全文，不做内部滚动）。这是"功能等价、交互略简"的稳妥退路。

> 附：`st.expander` 支持 `icon` 参数（本环境已核实）——思考框可加图标
> 以符合 `docs/UI视觉优化设计.md` 的图标约定（如 `brain`/`sparkles`），
> 但**必须只用一处**（图标总量受控，见该文档 3.4）。

## 5. 优雅降级（硬性要求）

**思考摘要不保证存在**（见 2.1 边界 2）。规则：

| 情况 | 行为 |
|---|---|
| 该轮有 reasoning 事件 | 正常显示"思考摘要"折叠框 |
| 该轮无 reasoning 事件 | **不显示该区块**（不显示空框、不显示"（无思考）"） |
| 只有工具播报无思考 | 过程区只显示工具播报（仍保留，满足需求 1 的过程保留） |
| 流式中途失败 | 已收到的思考与工具播报**保留**（与 `docs/流式输出设计.md` 3.4 "保留已输出正文"一致） |
| 历史轮次（旧数据无 `steps`） | `ChatTurn.steps` 缺省空列表 → 不渲染过程区（**向后兼容**） |

> 最后一行是关键兼容点：**此前已产生的会话消息没有 `steps` 字段**，
> 组件必须容忍缺失（`getattr(turn, "steps", []) or []`），不得报错。

## 7. 测试计划

**单元（`stream_turn`，用假事件流）**
- reasoning 增量事件被识别并 yield `kind="reasoning"`；
- `done` 事件携带 `reasoning` 全文（等于各 delta 拼接）；
- `part.added` 插入分段符（断言段间有 `\n\n`）；
- **无 reasoning 事件时**：`reasoning` 为空串、`steps` 不含 reasoning 项（降级）；
- 中途失败：已收到的 reasoning/tool **保留在 steps 中**（**回归关键**）。

**单元（`ChatTurn` 兼容）**
- 旧结构（无 `steps`）不报错（`getattr` 降级）；
- `reply_stream` 的 final 块 turn 含 `steps`/`reasoning`；
- `steps` 顺序正确（reasoning 与 tool 按发生顺序交错）。

**UI（AppTest）**
- 有 reasoning：渲染出"思考摘要"expander，默认收起；
- 无 reasoning：**不渲染**该 expander（断言不存在），不崩；
- 历史轮次（turn.steps 为空）：不渲染过程区，不崩；
- 工具播报在**过程区**、正文在**独立区**（断言两者不再共用同一容器——
  静态断言 `_run_agent_turn` 不再只有一个 placeholder）。

**行为（`docs/行为测试.md` 追加终身回归）**
- 背景：此前流式过程共用一个 placeholder，工具播报被正文覆盖、过程不持久；
  思考过程（实测可得，摘要 631 字符）此前被静默丢弃；
- 期望：过程（思考摘要 + 工具播报）在**当前轮与历史轮**均可见、可折叠、
  固定高度内滚动、小字区分；无摘要时优雅降级。

**人工验收**
- 真实长任务：观察思考摘要是否实时增长、结束后是否仍可回看；
- **滚动验证（重点）**：思考框内部滚动是否与外层聊天滚动冲突（见 4.5 风险）；
- 深色模式下思考小字的可读性（沿用 `docs/UI视觉优化设计.md` 的验收）。

## 9. 风险

| 风险 | 应对 |
|---|---|
| **嵌套滚动导致"滚动陷阱"**（最需实测） | 4.5 降级方案：仅 expander 折叠；实现后必须真机验证 |
| 思考摘要很长（实测 631 字符，长任务可能数千） | 固定高度 + 内部滚动；expander 默认收起 |
| 摘要非每轮都有 → 空框误导 | 第 5 节硬性降级规则（无则整块不渲染） |
| 旧会话消息无 `steps` 字段 | `getattr` 缺省降级（第 5 节末行） |
| 每次事件全量重渲过程区导致性能下降 | 思考增量高频（35 raw 事件/轮）；重渲成本需实测；若明显卡顿则改为节流（每 N 字符或每 100ms 重渲一次） |
| 展示思考摘要引发"信息过载" | 默认收起 + 小字 + 独立框（不干扰正文阅读） |
| 用户把"摘要"误认为"完整思考链" | 文案用"思考摘要"，文档 2.1 明确说明是 summary 非原始 CoT |
