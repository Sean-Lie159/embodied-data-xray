# 流式渲染节流与执行中断恢复设计

> 版本：v0.2（三个层次均已实施，含两处非预期发现）
> 关联文件：`AGENTS.md`（行为准则）、`docs/流式输出设计.md`（流式总设计）、
> `docs/思考过程展示与流式过程持久化设计.md`（过程区设计）
> 状态：**已实施并验证**（2026-09-22）。全量测试 1383 通过 / 1 跳过。
>
> 触发背景（真实事故，2026-09-22）：用户在单轮提问里要求 4 项分析
> （加载 + 时间对齐 + 指尖自洽性 + 120Hz 质检 + 左右手对称性），
> 前端**卡死约 196 秒后整轮内容丢失**，刷新后对话只剩用户提问、助手回复为空。
> 用户最初怀疑"是不是一次问太多了"——方向对，但**归因不是任务量**。
>
> **实施记录**：
> - ✅ 层次一 节流（commit `b7a78da`）：时间 + 字符双阈值，渲染次数与思考速度解耦；
> - ✅ 层次二 渲染上限（同 commit）：尾部截断 + 如实标注省略；
> - ✅ 层次三 中断恢复（同 commit 临时兜底 → `1326470` 转为正式实现）：
>   `StopException` 专项识别 + 可操作建议 + **内容不再丢失**；
> - ✅ 附带发现并修复两处独立缺陷（`1326470`）：
>   - **入参 `null` 字面量**：模型把 JSON 的 `null` 传成字符串 `"null"`，
>     工具拿它去匹配文件名（必然失败）→ 返回 `baseline_no_match` →
>     模型误以为参数无效而**重试整轮**（正是本次事故中"三次重试"的来源之一）。
>     修复：在工具调用的**唯一经过点**（`guard_tools`）统一归一并删除空值键，
>     覆盖全部 14 个工具的 31 个可选参数（逐个改必然遗漏）。
>   - **流式线程崩溃致永久阻塞**：`_run` 顶层异常（`new_event_loop` /
>     `run_until_complete` 自身崩溃）此前会被静默吞掉且**不投 `_DONE`**
>     → 消费端永久阻塞在 `q.get()`。修复：`_run` 补投 `(异常, _DONE)` +
>     `q.get(timeout=30)` 检测线程已死后主动收尾。
> - ✅ 另一独立缺陷（同 commit）：**主题字号缺单位**——`.streamlit/config.toml`
>   的 `headingFontSizes` 用了整数，Streamlit 该字段要求**带单位字符串**，
>   导致启动报 `TypeError: bad argument type for built-in operation`、
>   **标题层级完全未生效**。注意 `headingFontWeights` 相反，要求**整数**
>   （Streamlit 源码明确），两者易混。

## 1. 事故根因（基于实测日志，非推测）

诊断埋点捕获的原始证据：

```
[STREAM-DIAG 196.44s] 消费循环退出；线程存活=True（join 超时 5s）
  | state={'pump_started': True, 'pump_finished': False, 'pump_exc': None,
           'items': 8501, 'last_kind': 'reasoning', 'done_put': False,
           'got_done': False}

[UI-DIAG 196.44s] _run_agent_turn 流式循环异常：StopException:
  File "streamlit_app.py", line 196, in _run_agent_turn
    with process_placeholder.container():
  ...
  File "streamlit/runtime/scriptrunner/script_runner.py", line 509
    raise StopException()
```

**三条关键事实**：

1. **后台线程工作正常**：`items=8501`、`pump_exc=None`、`last_kind='reasoning'`
   ——它一直在产出事件，**没有死、没有异常**；
2. **异常发生在 UI 渲染层**：`StopException` 由 Streamlit 的
   `_maybe_handle_execution_control_request()` 抛出，语义是"脚本被要求停止，
   不要再渲染"；
3. **196.44 秒**：脚本跑了近 200 秒才被中断。

**因果链**：

```
reasoning 事件逐 token 到达（8501 个事件中绝大多数是它）
        ↓
对**每一个** reasoning 增量执行：
    with process_placeholder.container():      # 新建容器
        render_reasoning_and_steps(live_steps) # 重渲染**整个**时间线
        ↓
live_steps 持续增长 × 重渲染次数持续增长 = 平方级开销
        ↓
脚本运行 196 秒仍未结束
        ↓
Streamlit 执行控制介入 → 抛 StopException
        ↓
脚本中断 → `_record_turn` 从未执行
        ↓
assistant 消息从未写入 messages → 刷新后内容丢失
```

**为什么"拆成 4 次提问"就正常**：思考量急剧下降 → reasoning 事件数少几个
数量级 → 不触发 200 秒级的渲染开销。**任务多不是原因，"思考链长 → UI 逐
token 重渲染"才是原因。**

**补充证据**：事故当时实测进程 CPU 20 秒仅涨 0.13 秒、内存/线程数不变
——说明进程**已空闲**（脚本已中断），而非"仍在计算"。

## 2. 三个层次的问题

### 层次一：UI 逐 token 重渲染（**性能缺陷，最严重**）

**现状**（`streamlit_app.py:193-202`）：每个 reasoning/tool 增量都触发
`process_placeholder.container()` + 全量 `render_reasoning_and_steps`。

**注意**：`docs/思考过程展示与流式过程持久化设计.md` 与 `agent._append_step`
已实现"**相邻同类片段合并**"（避免每 token 一条 step）。但那是**服务端采集
层**的合并——**UI 侧仍然对每个增量触发一次全量重渲染**。设计意图未落到 UI。

### 层次二：过程区渲染无规模上限

即使节流后，若单轮 reasoning 极长，`live_steps` 拼接出的文本仍会非常大，
`st.caption` 渲染长文本同样有成本。需要"只渲染尾部 N 条"或按字符截断。

### 层次三：执行中断导致整轮丢失（**可用性缺陷**）

`StopException`（以及任何 UI 层异常）发生时：
- `_run_agent_turn` 抛异常 → 主循环中断 → **`_record_turn` 从未执行**；
- 结果：assistant 消息**从未写入 `messages`**，刷新后整轮内容丢失；
- 更糟的是**没有任何提示**（Streamlit 的 `StopException` 属控制流异常，
  不显示红框），用户完全不知道发生了什么。

**这违反项目「诚实降级」原则**（`AGENTS.md` §5）。

## 3. 设计

### 3.1 层次一：时间+字符双阈值节流（已实施）

**策略**：reasoning/tool 增量先累积到缓冲，满足以下**任一**条件才重渲染：

- 距上次渲染超过 `_PROCESS_RENDER_INTERVAL_S`（默认 **0.4 秒**）；
- 或累积字符数超过 `_PROCESS_RENDER_MIN_CHARS`（默认 **120 字符**）。

**为什么用"时间 + 字符"双阈值**：

- 纯时间阈值：思考速度慢时会显得卡顿（0.4 秒才更新一次）；
- 纯字符阈值：思考速度快时会频繁触发；
- 两者任一满足即渲染，兼顾"响应感"与"渲染次数上限"。

**效果估算**：事故中 8501 个事件、196 秒。按 0.4 秒节流 → 最多渲染
约 **490 次**（而非 8501 次），且每次渲染的**触发频率与思考速度解耦**。

**收尾必须强制渲染**：流式结束后无条件渲染一次，保证最终内容完整
（节流只影响中间过程，不影响最终状态）。

**实施位置**：`streamlit_app.py` 的 `_run_agent_turn`。

### 3.2 层次二：过程区渲染上限（已实施）

`render_reasoning_and_steps` 增加**尾部截断**：`live_steps` 超过
`_PROCESS_RENDER_MAX_STEPS`（默认 **40** 条）时，只渲染最后 40 条，
并在开头加一行说明"（已省略前 N 条过程）"。

**为什么保留尾部**：用户关心的是"**当前**在做什么"，早期步骤的价值随时间
递减；且 upsert 渲染的是同一块区域，保留尾部更符合"跟着思考走"的预期。

**注意**：这只影响**流式中的实时渲染**。**持久化到 `messages` 的 steps
不截断**——历史轮次展开时仍能看到完整过程（若同时应用上限，需在渲染层
而非存储层截断，本设计即如此）。

### 3.3 层次三：中断恢复（临时兜底已实施，正式实现待办）

**已实施的临时兜底**（本次事故定位时加入，**应转为正式实现**）：

- `_run_agent_turn` 捕获异常 → 打印诊断 → 重新抛出；
- 主循环捕获 → 构造一个 `completed=False` 的失败 `ChatTurn`
  → **仍然调用 `_record_turn`** → 内容不丢、可见、可重试。

**正式实现应包含**（待办）：

1. **识别 `StopException`** 为"本轮被中断"（而非普通异常），
   在 UI 上明确显示"本轮因执行时间过长被中断，建议拆分提问或缩小范围"；
2. **给用户可操作建议**：`StopException` 的根因是任务量过大，
   提示应具体（如"本次含 4 项分析，建议每轮聚焦 1 项"）；
3. **诊断埋点转为可选日志**（受配置开关控制，默认关闭），
   避免长期在 stderr 打印噪声。

### 3.4 为什么不在服务端"限制思考量"

一个自然的想法是"既然思考太长，就限制 reasoning 输出"。**本设计不采用**，
理由：

- 思考链长度由任务复杂度决定，**截断思考会降低答案质量**（尤其涉及多步
  推理的分析任务）；
- 项目已有 `REASONING_EFFORT` 配置供用户按需调整（`high`/`low`/`off`），
  这是**正路**；
- 问题的本质是**UI 渲染效率**，不是思考量本身——不该用"少思考"来绕过
  "渲染慢"。

## 5. 验收标准

1. **不再出现 200 秒级卡死**：同一提问（4 项分析）下，UI 渲染次数与
   思考速度解耦；
2. **中断不再丢内容**：即使中途异常，assistant 消息仍写入 `messages`，
   刷新后可见（带"本轮未完成"标记 + 重试入口）；
3. **正常场景零回归**：短推理轮次的渲染行为与体感不变；
4. **全量测试通过**：既有 1330 项不回退。

## 6. 明确不做（防止过度设计）

| 方案 | 否决理由 |
|---|---|
| 服务端截断 reasoning 输出 | 降低答案质量；已有 `REASONING_EFFORT` 供用户控制 |
| 把过程区改成"只在收尾时渲染" | 失去"思考可见"的核心价值（`docs/流式输出设计.md` 的诉求） |
| 持久化 steps 时也截断 | 历史轮次应能回看完整过程；截断只在渲染层做 |
| 引入 asyncio 直连 Streamlit（去掉线程桥） | 改动面过大，需重写服务层异步接口；当前线程桥本身工作正常 |
