### 1.2 缺口盘点

**第一，语义确认画像不可见。** 系统在 2026-08/09 建立了完整的语义确认闭环：
`propose_stream_semantics`（工具验证）→ 用户确认 → `confirm=True` 落盘到画像
（`profile_store.save_dataset_profile`）→ 重载时 `apply_profile_overrides` 把
`label_source="user_confirmed"` 应用到流登记表（`profile_store.py:245-249`）。

但面板里**完全看不到**：哪些流已确认、确认成什么语义、哪些仍是 unknown。
SYSTEM_PROMPT 纪律 12 要求 agent 引用这些标签时说明"来自持久化确认画像"——
如果面板能直接列出，用户就不必每次都靠对话追问。

**第二，`unclassified_hint` 不可见。** `inspect_streams` 在
`n_streams >= 5 and classified < n_streams` 时产出
`unclassified_hint`（`inspect_streams.py:618-623`），催 agent 主动引导批量确认。
但这是**模型侧**的提示，**用户侧**面板没有任何"当前 N/M 条流未分类"的直观信息。

**第三，单位告警（`unit_warnings`）、时钟形态矛盾（`clock_artifact_suspected`）
不可见。** `docs/技术债.md` 第 4 条详细记录了"单位链路事故"（纳秒被当秒、
`duration_s≈5.28e10` 误导模型），修复后这些告警出现在**工具返回**里，
但 UI 面板不展示——用户只在 agent 转述时才间接知道。

**第四，视频 fps 与流清单的关联已做但不够。** `video_fps_by_file` 已传入
（`chat_service.py:335-339`），面板表格用它显示"xx fps（视频）"——这块做得对，
保留。

## 2. 设计

### 2.1 面板结构

`tab_overview` 从"能力标签 + 流清单"扩展为**五段式**（有数据才渲染对应段）：

```
数据集：<dataset_id>            推测类型：Ego（置信 0.7）
─────────────────────────────────────────────
[1] 能力标签        IMU ✓（6 轴）/ 视频 ✓ / 力 ✓ / 标定 ✗ / 状态动作 ✓
[2] 语义确认进度     13/26 条流已分类 · 13 条未分类  ⚠️ 建议批量确认
                    └ [展开] 已确认清单（来自持久化画像）
[3] 数据质量告警     ⚠️ 2 条流单位未知（不参与跨流对齐）
                    ⚠️ 1 条流疑似时钟形态矛盾（容器时间 vs 传感器时间）
[4] 流清单           表格：流 / 角色 / 采样率 / 语义标签 / 来源
[5] 数据概况         行数 / 列数 / 缺失（若有）
```

### 2.2 各段的数据来源（全部走现有接口，不新增工具）

| 段 | 数据来源 | 说明 |
|---|---|---|
| [1] 能力标签 | `dataset_summary()["capabilities"]` | **现有逻辑不动** |
| [2] 语义确认进度 | `context.meta["streams"]` 聚合：`kind not in (None,"unknown")` 计数 + `label_source == "user_confirmed"` 计数 | 与 `inspect_streams` 同口径（`inspect_streams.py:612`），**须一致**，否则 UI 说"已分类"而工具说"未分类" |
| [3] 质量告警 | `context.meta` 中的 `unit_warnings` / `clock_artifact_suspected`；若无则从 **画像/最新工具返回缓存** 取 | 见 2.3 的数据获取难点 |
| [4] 流清单 | `dataset_summary()["streams"]` | 增列"语义标签"与"来源(rules/fingerprint/user_confirmed)" |
| [5] 数据概况 | `context.meta["main_table"]`（`load_dataset` 已写入行/列数） | 若 `rows_total != rows_loaded` 须显示截断提示 |

### 2.3 数据获取的难点与解法（本项最需要想清楚的地方）

**[2] 与 [3] 的数据在工具返回里，不在 `RunContext.meta` 中**（`unit_warnings`
与 `clock_artifact_suspected` 是 `inspect_streams` / `check_temporal_sync` 的
返回字段，工具未回写 meta）。

三种解法：

**解法 A（推荐）：让 `inspect_streams` 缓存关键状态到 `meta`**

在 `inspect_streams` 产出 `unclassified_hint` / `clock_artifact_suspected` 时，
同时写回：

```python
context.meta["qc_state"] = {
    "unclassified_hint": unclassified_hint,
    "clock_artifact_suspected": [流名清单],
    "unit_warnings": [流名清单],
    "checked_at": <时间戳>,
}
```

- 优点：UI 有稳定数据源，且与工具**同一次计算**的结果一致（不会 UI 与工具口径打架）；
- 代价：**需要改工具代码**（`inspect_streams.py`），比"只改 UI"重；
- 零回归做法：新增 key 不影响任何现有消费方；`meta` 是每会话独立的，
  多会话天然隔离。

**解法 B：UI 侧自行计算**

UI 直接从 `streams` 推算"已分类/未分类"，不依赖工具：

- 优点：零工具改动；
- 缺点：**只有 [2] 能做**（[3] 的单位告警需要实际读数据才能判，UI 不做数据分析，
  否则违反"UI 不做业务计算"的分层纪律）；且口径与工具可能不一致。

**解法 C：不显示 [3]**

只做 [2]（UI 自算）+ [4] 的语义标签列。

**决策建议**：**[2] 用解法 B（UI 自算，零工具改动），[3] 用解法 A（工具回写 meta）**。
理由：[2] 的判据（`kind`/`label_source`）在 `meta["streams"]` 里已经齐全，
UI 读一下就能算，没必要动工具；[3] 必须由工具产生（单位判定需读数据），
硬要让 UI 算就是重复实现且破坏分层。

> 若 owner 希望**本次完全不改工具**，则降级为：只做 [2] + [4]，[3] 留待后续。
> 此时本项退化为"纯 UI 改动"，风险最低。

### 2.4 语义确认清单（[2] 的展开内容）

展开后按"来源"分两组：

```
已确认（来自持久化画像，跨会话生效）：
  imu_glove.csv        → IMU（imu, 6 轴）         [user_confirmed]
  tf.jsonl             → 坐标变换（tf）            [user_confirmed]
自动识别：
  force_sensor.csv     → 力/力矩（force）          [dictionary]
未分类：
  mystery_a.jsonl      → unknown                   —
```

来源取值映射（`profile_store` 已定义常量）：
`user_confirmed` → "用户确认"，`content_fingerprint` → "内容指纹"，
`dictionary` → "词典"。

**重要**：此段须标注"来自持久化确认画像（跨会话生效），非模型记忆"——
与 SYSTEM_PROMPT 纪律 12 的表述一致，避免用户误以为 agent "记得"。

## 4. 测试计划

**单元**
- `dataset_summary()` 返回的 streams 含 `semantic_label` / `label_source` / `kind`；
- 语义计数与 `inspect_streams` 口径一致（用同一份 `meta` 造数据，断言两个入口
  算出的"已分类数"相同）——**这是防"UI 与工具打架"的关键用例**；
- 【若采纳解法 A】`inspect_streams` 调用后 `meta["qc_state"]` 存在且字段齐全；
  未调用该工具时面板降级为不渲染 [3] 段（不报错）。

**UI（AppTest）**
- 未加载数据集：显示引导，不崩；
- 加载数据集后：五段（或降级版）渲染不崩；流清单表含"来源"列；
- 有 `unit_warnings`（构造 meta）时告警段出现；无则整段不出现。

**人工验收**
- 加载含 26 条流的 MCAP 数据集：面板显示 13/26 已分类 + 未分类提示；
  展开可见 user_confirmed 清单；单位告警若存在则可见。

## 5. 风险

| 风险 | 应对 |
|---|---|
| UI 自算"已分类数"与 `inspect_streams` 口径不一致 | 2.2 明确同口径判据 + 第 4 节专门用例 |
| 采纳解法 A 需改工具，触碰工具层 | 只**新增** meta key，不改任何现有返回字段；`meta` 每会话独立 |
| `unit_warnings` 只在调用过 `check_temporal_sync` 后才有 | 面板降级：无数据不渲染该段（不误导为"无告警"）——**措辞须区分"未检查"与"无问题"** |
| 语义清单过长（26 条）挤爆面板 | 用 `st.expander` 折叠 + 表格；超 20 条时分页或只显示摘要 |

> 最后一条要强调：**"未检查"与"检查通过"必须用不同措辞**（如"尚未执行
> 时间同步检查" vs "已检查，无单位告警"）——否则用户会误以为"没问题"，
> 这与项目"诚实降级"纪律一致。
