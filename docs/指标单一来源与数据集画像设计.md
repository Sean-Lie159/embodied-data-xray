# 第一部分（A）：指标单一来源（metrics 物化）

## A.1 问题陈述（实测证据）

用户在真实数据上观察到**三条互相矛盾的信息**：

| 用户看到的位置 | 显示 | 实际来源 |
|---|---|---|
| 流明细表（报告） | 采样率 **未知** | `meta["streams"][*]["measured_rate"]` 为 None |
| 时间同步检查 | 实测 **120.007 Hz** | `check_temporal_sync` 自己现读时间戳列重算 |
| 质检「采样率声明合法性」 | **skip**（未声明 fps） | 只读 `fps` 列与 LeRobot `meta/info.json` |
| 时间同步「标称率核对」 | **skipped**（未配置） | `nominal_rate_hz` 字段**永远为 None** |

同一份数据、同一个事实（采样率），四个位置给出四种说法。用户判断
「agent 各工具之间信息不通」——**这个判断是正确的**。

## A.2 全面排查结果（基于代码，非印象）

### A.2.1 采样率：7 处独立实现

| # | 位置 | 算法/来源 | 是否复用缓存 |
|---|---|---|---|
| 1 | `load_dataset._measure_rate_hz` (l.1519) | `infer_unit(ts)`（**不传列名！**）→ `to_ns` → `1e9/mean(diff)` | **写入者** |
| 2 | `inspect_streams`（读缓存） | 读 `meta["streams"][*]["measured_rate"]` | 读取者 |
| 3 | `check_temporal_sync` | 自读时间列，走 `timestamp_units` 正规入口（带列名） | **否** |
| 4 | `check_dataset_quality._check_fps` (l.493) | `1.0 / median_step`——**对原始数值取差分倒数，无单位归一化** | **否** |
| 5 | `generate_report`（流明细表，l.91） | 读 `measured_rate.sample_rate_hz` | 读取者 |
| 6 | `align_container_streams` | 自算 | **否**（待确认具体行号） |
| 7 | `compare_datasets` | 自算 | **否**（待确认具体行号） |

### A.2.2 三处具体缺陷（均已定位到行）

**缺陷 A2-1：`_measure_rate_hz` 漏传列名，丢失单位线索。**

```python
# load_dataset.py:1539
unit = infer_unit(ts)["unit"]          # ← 未传 col_name
```

而 `timestamp_units.infer_unit` 的**列名后缀是最高优先级的单位线索**
（`_ns`/`_us`/`_ms` 是强信号）。不传列名即退化为纯量级推断，对
`timestamp_ns` 这类列会失准或直接返回 unknown → `_measure_rate_hz` 返回
None → 流明细显示「未知」。
**而 `check_temporal_sync` 传了列名**，所以它能算出 120.007Hz。
**这就是「同一个数据集两个采样率」的直接原因。**

**缺陷 A2-2：`check_dataset_quality._check_fps` 做无量纲差分。**

```python
# check_dataset_quality.py:491-495 附近
median_step = float(np.median(diffs))
measured = 1.0 / median_step            # ← 对原始数值取倒数
```

对纳秒时间戳（间隔 8,333,100）会得出 `1.2e-7` 这种无意义值。
当前因「无声明 fps」而 skip 才没暴露；**一旦数据补上 `fps` 列，它会报出
荒谬的实测值并误判「偏差超 10%」**。这是潜伏缺陷。

**缺陷 A2-3：`nominal_rate_hz` 字段只有读、没有写。**

全代码库仅 `check_temporal_sync._nominal_rate` (l.189) 读它，
**零处写入**。因此该字段恒为 None，`nominal_check` 必然 skipped。
而 `session.json` 里的 `nominal_hz: 120` 只被登记为配置文件的
`config_keys`（键名清单），**从未流入任何采样率计算**。

### A.2.3 其他"同一事实多处实现"（同类问题）

| 事实 | 处数 | 是否统一入口 |
|---|---|---|
| 时间戳单位量级推断 | 2 套阈值 | **否**：`timestamp_units` 用 1e15/1e11/1e8；`_sniffing` 自建 1e17/1e14/1e11 |
| 时间列识别 | ≥ 4 处 | **否**：各工具自写候选清单 |
| episode 列识别 | ≥ 4 处 | **否**：`_data_access` / `compute_stats` / `annotation_store` / `segment_actions` 各一份 |
| 列名匹配 | ≥ 6 处 | **否**：各工具自写 `_find_col` |
| 视频帧率 | 2 处 | **否**：`meta.video_meta[*].fps` 与 `meta.streams[*].measured_rate` 并存 |

**结论**：这不是 3 个工具的局部问题，而是 **`RunContext.meta` 被当作"可写可不写的备忘录"，而非"唯一事实来源"** 的系统性缺陷。

## A.3 根因分析：为什么"共享 state"没起作用

机制本身是有的——`openai-agents` SDK 文档明确：

> context 对象不会发送给 LLM，它纯粹是一个本地对象；在
> `RunContextWrapper` 中持有，供所有工具访问。

`RunContext.meta` 就是这个共享容器。问题在于：

1. **SDK 只提供管道，不提供任何强制机制**——是否复用完全靠工具代码自觉；
2. **同一个 key 有多个写入者**（#1 与 `inspect_streams` 都写
   `measured_rate`，算法不同），**谁后跑谁覆盖**，这是"结果分歧"的直接来源；
3. **没有 provenance**——读到的值不知道是"实测"还是"声明"还是"猜的"；
4. **没有单一写入口**——每个工具都能自己算一遍，且**算了也不回写**。

## A.4 设计目标与非目标

**目标**：

1. 同一事实**只有一个权威值**，且**结构上无法产生第二个**；
2. 每个指标带**来源标记**（provenance），可区分实测/声明/推断；
3. 「标称值」与「实测值」**不互相覆盖**，而是**并存且可比较**；
4. 一致性判定用**容差**，不要求相等；
5. 新增指标时**有守护测试**强制走统一入口。

**非目标**（明确不做，避免过度设计）：

- 不做通用的 KV 存储或黑board 框架——本项目是**单进程本地工具**，
  不需要分布式共享状态；
- 不引入外部依赖（Redis/DB/消息队列）；
- 不重构 `RunContext` 的注入方式（`Runner.run(context=)` 保持不变）。

## A.5 核心设计：metrics 单一物化区

### A.5.1 数据结构

在 `RunContext.meta` 下新增**唯一的 metrics 区**：

```python
meta["metrics"] = {
    "streams": {
        "<stream_key>": {            # stream_key = 规范化的流标识
            "sample_rate_hz": {      # ← 实测值（唯一权威，供计算使用）
                "value": 120.007,
                "provenance": "measured",
                "source": "timestamp_diffs",
                "evidence": "相邻时间戳差分的均值倒数（已归一化为纳秒）",
                "measured_at": "2026-09-21T16:40:00Z",
            },
            "nominal_rate_hz": {     # ← 标称值（不作权威，仅供比较）
                "value": 120.0,
                "provenance": "declared",
                "source": "session.json:nominal_hz",
                "evidence": "配置文件声明的标称采样率",
            },
            "tolerance_ratio": 0.05, # ← 一致性判定容差
        }
    },
    "dataset": {
        "nominal_hz": {...},          # 数据集级标称（若有多流声明的交集）
    },
}
```

**关键设计决定（最重要）**：**标称值与实测值是两个不同的 key，不竞争**。

这直接回答用户的疑问——120 与 120.007 **不是"两个来源的冲突"**，而是
「设计目标」与「实际表现」的正常关系。若把它们塞进同一个 key 用"权威链"
选一个，反而会**永久丢失**"标称 120 但实际只有 100"这种真正该报警的情况。
**标称值必须保留，它的价值就在于可被对比。**

### A.5.2 唯一写入口

新增模块 `app/tools/metrics_store.py`（**唯一允许写 `meta["metrics"]` 的地方**）：

```python
def materialize_stream_metrics(context: RunContext, *, force: bool = False) -> dict:
    """物化全部流的采样率指标（**唯一写入口**）。

    幂等：已物化且未 force 时直接返回，不重算——这是"单一来源"的保障。

    Returns:
        {"streams": {stream_key: {...}}, "n_measured": int, "n_declared": int}
    """

def get_measured_rate_hz(context: RunContext, stream_key: str) -> dict | None:
    """读某流的实测采样率（**所有工具的唯一读取入口**）。

    Returns:
        {"value": float, "provenance": "measured", "source": str, ...}
        或 None（未物化/无法测量）。
    """

def get_nominal_rate_hz(context: RunContext, stream_key: str) -> dict | None:
    """读某流的标称采样率（供一致性比较，**不用于计算**）。"""

def compare_rate(measured: dict | None, nominal: dict | None,
                 tolerance_ratio: float) -> dict:
    """比较实测与标称是否一致（容差判定，**不要求相等**）。

    判定：|measured - nominal| / nominal <= tolerance_ratio → "consistent"。

    Returns:
        {"consistent": bool|None, "deviation_ratio": float,
         "tolerance_ratio": float, "explain": str}
        ——任一侧缺失时 consistent=None（**如实说"无法比较"，不猜**）。
    """
```

### A.5.3 统一算法链（消除 A2-1 / A2-2）

```
时间列（含列名后缀线索）→ timestamp_units.infer_unit(col_name=...) 
                        → self_correct_unit（采样率合理性自纠）
                        → to_ns
                        → 差分 → 取稳健统计量（中位数，抗离群）
                        → 1e9 / median_diff_ns = measured_hz
```

**必须传 `col_name`**（修 A2-1），且**先归一化再算**（修 A2-2）。
`check_dataset_quality._check_fps` 与 `check_temporal_sync` 全部改为
**读 `metrics_store.get_measured_rate_hz`**，不再自己算。

### A.5.4 标称值来源链（修 A2-3）

按优先级收集**声明值**（**只写 `nominal_rate_hz`，不覆盖实测**）：

| 优先级 | 来源 | provenance | 说明 |
|---|---|---|---|
| 1 | 平台配置文件（如 `session.json` 的 `nominal_hz`） | `declared` | 本次缺失的正是这一环 |
| 2 | 数据列 `fps` / `frame_rate` / `rate_hz` | `declared` | 既有行为 |
| 3 | LeRobot `meta/info.json: fps` | `declared` | 既有行为 |
| 4 | 视频元数据 `meta.video_meta[*].fps` | `declared` | 既有行为 |

**配置文件识别规则**：`meta["streams"]` 中 `status == "config"` 的流（见
`docs/ARCHITECTURE.md` §3.3.0 的修复），其 `config` 字段里含
`nominal_hz` / `sample_rate_hz` / `hz` / `fps` 等键时，作为数据集级标称值。
**注意**：该识别必须**保守**——仅当键名明确表达"采样率"语义时才取用，
不做模糊匹配（避免把无关数字当采样率）。

### A.5.5 一致性判定：容差而非相等（回答用户疑问）

用户明确担心："120.007 vs 120 实际可以认为二者一致"。**设计采纳**：

- 判定式：`deviation_ratio = |measured - nominal| / nominal`；
- `deviation_ratio <= tolerance_ratio` → **一致**（consistent）；
- 默认容差 **0.05（5%）**，可配置（`settings.metrics_rate_tolerance_ratio`）。

**容差取 5% 的依据**（外部调研）：
- Soda 的 `percent_threshold` 默认 **0.05**；
- Great Expectations 亦以百分比设阈；
- 本项目现有硬编码为 **10%**（`check_dataset_quality.py:496`），
  本设计统一为 5% 并移入配置。

本数据实测偏差 `|120.007-120|/120 = 0.0058%`，**远小于 5% → 判为一致**，
符合直觉。

**呈现纪律**：即使判为一致，报告仍应**同时给出两个数字**
（"实测 120.007 Hz，声明 120 Hz，偏差 0.006%，一致"）——
不能只报"一致"而隐去数值，否则用户无法判断偏差方向与量级。

## A.7 明确不做的方案（记录否决理由）

| 方案 | 否决理由 |
|---|---|
| **用户初提的"权威链"（实测 > 声明 > 列 > meta）** | 会让标称值被实测覆盖，**永久丢失**"声明 120 实际 100"的告警能力；且"权威链"把两个语义不同的量（目标 vs 表现）塞进一个 key，是概念错误。改为**两个 key 并存 + 容差比较**。 |
| 引入外部 KV/DB 做共享状态 | 单进程本地工具，无必要；且违反「本地运行、不引入额外依赖」 |
| 让每个工具自己去读 `meta` 缓存（靠自律） | **这正是当前失效的原因**——SDK 不强制，自律必然被绕过。改为**单一写入口 + AST 守护测试** |
| 全量重构 `RunContext` | 改动面过大、收益不匹配；保留现有注入方式，只加 metrics 区 |

# 第二部分（B）：数据集画像确认（能力标签与类型）

## B.1 问题陈述（实测证据）

用户提问："报告中很多是我们已经知道、你也分析过、做过语义确认的，**为什么还是 unknown**？"

排查确认两个独立缺陷：

**缺陷 B1-1：模态矩阵是硬编码六项，漏掉了本数据的核心模态。**

```python
# generate_report.py:108-115
rows = [
    ("视频流", caps.get("has_video_streams")),
    ("IMU", caps.get("has_imu")),
    ("力/力矩", caps.get("has_force")),
    ("标定", caps.get("has_calibration")),
    ("状态/动作", caps.get("has_actions")),
    ("语言标注", caps.get("has_language")),
]
```

`capabilities` 实际有 **10 个键**（`_sniffing.py:2238-2249`）：
`has_video_streams`、`has_audio`、`has_imu`、`imu_axes`、`has_force`、
`has_calibration`、`has_actions`、`has_hand_tracking`、`has_pose`、
`dataset_format`。

**矩阵漏了 `has_pose`、`has_audio`、`has_hand_tracking`、`imu_axes`、
`dataset_format`**——而这份手套数据的核心能力**恰恰是 `has_pose=True`**。
结果报告呈现"IMU ✗ / 力 ✗ / 标定 ✗"，**唯独没有"位姿"这一行**，
用户看到的是"一堆没有"，关键模态反而消失。

**缺陷 B1-2：`guessed_type` 算完即固定，无用户确认通道。**

```python
# _sniffing.py:2251-2264（硬编码 if-else 链）
guessed_type = "unknown"; conf = 0.0
if dataset_format == "lerobot":          → "LeRobot", 0.8
elif has_video and imu_present and pose_present:  → "Ego", 0.7
elif has_video and (imu_present or pose_present): → "Ego", 0.5
elif imu_present and pose_present:       → "遥操/动捕", 0.5
elif actions_present:                    → "状态/动作数据", 0.6
elif imu_present:                        → "IMU 数据", 0.6
# 都不是 → 保持 unknown / 0.0
```

本数据 `has_pose=True` 但**无 IMU、无动作列、无视频** → **一个分支都不命中**
→ `unknown` + 置信度 `0.0`。

**关键**：该值在 `load_dataset` 时算一次写入 `meta`，**此后永不更新**。
而流层面的 `semantic_label` **有** `label_source` 字段
（`inspect_streams.py:641`，取值 `user_confirmed` / `content_fingerprint` /
`dictionary`）——说明"用户确认覆盖自动识别"机制**只做在流层面，
数据集类型层面完全没有确认通道**。用户"确认过了"是事实，但**确认的是流，
类型那层无处可写**。

## B.2 设计目标

1. 模态矩阵**从能力标签动态生成**，新增标签自动跟上，不再漏项；
2. 数据集类型支持**用户确认覆盖**，跨会话生效，来源可溯源；
3. 报告在 `unknown` 时**主动提示**"可确认后固定类型"，而非静默呈现 unknown；
4. 有**守护测试**防止将来新增能力标签时漏配中文名。

## B.3 设计内容

### B.3.1 能力标签注册表（+ 守护测试）

新增 `_CAPABILITY_META`（位置：`app/tools/_sniffing.py` 或
`app/tools/capability_meta.py`）：

```python
_CAPABILITY_META: dict[str, dict[str, Any]] = {
    "has_video_streams": {"label": "视频流", "what": "含摄像头视频"},
    "has_audio":         {"label": "音频", "what": "含麦克风/音频轨"},
    "has_imu":           {"label": "IMU", "what": "含惯性测量单元（加速度/角速度）"},
    "imu_axes":          {"label": "IMU 轴向", "what": "IMU 的通道轴向", "is_detail": True},
    "has_force":         {"label": "力/力矩", "what": "含力或力矩传感"},
    "has_calibration":   {"label": "标定", "what": "含标定/内外参文件"},
    "has_actions":       {"label": "状态/动作", "what": "含可作为动作的学习信号"},
    "has_hand_tracking": {"label": "手部追踪", "what": "含手部/手指关节追踪"},
    "has_pose":          {"label": "位姿", "what": "含空间位姿（位置或朝向）"},
    "dataset_format":    {"label": "数据集格式", "what": "匹配到的公开格式", "is_detail": True},
}
```

**生成规则**：矩阵 = 遍历 `capabilities` 的键，按注册表取中文名；
`is_detail=True` 的项不作为独立矩阵行（而是附注）。
**未注册的键**：以原键名呈现并**标记 `未登记`**——不隐藏、不猜中文名。

**守护测试**：`test_every_capability_has_chinese_label`——遍历
`capabilities` 的所有键，断言都在 `_CAPABILITY_META` 中（与第一部分质检
的 `_RULE_META` 守护同构）。

### B.3.2 数据集画像（dataset profile）与确认通道

沿用既有的「画像文件 + 来源标记」范式（`app/tools/profile_store.py`
已为**流的语义**实现，此处扩展到**数据集级**）。

**画像文件**：`outputs/by_dataset/<净名>/dataset_profile.json`

```json
{
  "dataset_type": {
    "value": "手套位姿追踪数据",
    "source": "user_confirmed",
    "confirmed_at": "2026-09-21T17:00:00Z",
    "auto_detected": "unknown",
    "note": "用户确认：Forsense-G7 双手手套采集，左右前臂不采集"
  },
  "expected_missing": {
    "tips_trajectory.csv": ["*forearm_pos_*", "*forearm_quat_*"],
    "source": "user_confirmed",
    "note": "左右前臂在本采集中本就无传感器，属预期缺失"
  },
  "capabilities_override": {},
  "content_fingerprint": "<数据集内容指纹，用于校验画像仍适用>"
}
```

**`expected_missing` 的必要性（来自本次实测）**：用户明确说"左右前臂在这个
数据采集中是没有的，因此属于正常"。但当前**无处记录这一事实**，导致
`tips_trajectory.csv` 的质检永远报 `fail`（14 个 forearm 字段 100% 空），
用户每轮都要口头解释一遍。

**设计**：质检的 `nan_inf` 规则读取画像的 `expected_missing`，
**匹配到的列从缺失率判定中排除**，并在结果中如实标注
「N 个字段为空但属**已确认的预期缺失**（依据：用户于 X 时确认）」——
**不隐藏、不静默**，而是**区分"意外缺失"与"预期缺失"**。

### B.3.3 报告呈现

- `guessed_type == "unknown"` 时，报告显式写：
  「未匹配到已知格式。**如需固定类型，可确认后写入数据集画像**（跨会话生效）」；
- 有画像时，显示「类型：<已确认值>（来源：用户确认于 <时间>）」，
  并保留 `auto_detected` 供对照；
- 模态矩阵附注 `dataset_format`「数据集格式」一行。

# 附录：外部调研依据（用于设计决策）

## A. 关于"共享状态"的架构模式

- **Deequ（AWS）**：**Analyzer（计算指标）与 Check（断言）严格分离**。
  Analyzer 先跑、物化 metrics 行，Check 只读指标绝不重算。本项目
  `metrics_store` 的设计直接借鉴此模式。
- **LangGraph**：用 `TypedDict`/Pydantic 声明 state，**Reducer** 负责
  多来源写同一 key 时的合并——这正是"权威链"应有的位置（作为**一个
  reducer 函数**，而非散落各处的 if-else）。官方记录了一致性陷阱：子图
  有独立 checkpoint 命名空间，父图可能看不到子图更新。
- **Blackboard 架构**（arXiv:2507.01701，2025-07）：所有 agent 只通过
  黑板通信、无直接接触，从而**移除各自独立记忆**以保证一致性；并设有
  **conflict-resolver** 角色检测黑板矛盾——即"发现两个工具结果不一致"
  的机制。

## B. 关于容差判定

- Soda：`percent_threshold` 默认 **0.05**（5%）；
- Great Expectations：按百分比设阈；
- **本设计采用 5%**，取代现有硬编码的 10%。

## C. 明确未找到公开出处的项

以下未查到权威出处，故**未**作为设计依据，仅作默认值处理：

- "实测值 vs 声明值"比较的统一行业惯例（无统一标准，故设计为可配置）；
- 采样率偏差的具体行业容差数值（故取 Soda/GX 的通用百分比惯例）。
