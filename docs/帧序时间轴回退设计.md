# 帧序时间轴回退设计（子流无时间戳列时回退到容器主时钟）

> 状态：**已实施**（2026-09-21；全量测试 1214 passed / 1 skipped）
> 前序文档：`docs/H5节点形态接纳设计.md`（节点是否登记）、
> `docs/H5节点语义标签补全设计.md`（标签是否正确，其 §6 登记了本缺口）
>
> **实测结果**（真实数据集 `2655849` / `aligned_joints.h5`）：
> `n_with_timestamp` 7（自带）、`n_by_container_clock` **27**（回退）、
> `container_master_clock = main_timestamp`；6 条保持 `no_timestamp`
> （其中 4 条是每帧多行的 `(2,4)` 布局，frame_index 重复 → 严格校验拒绝）。

## 1. 问题陈述

修复"帧内标量时间戳漏登记"后，`main_timestamp` 已能被读到时，暴露出下一个缺口。

**实测**（真实数据集 `2655849` / `aligned_joints.h5`）：

```
align_container_streams(container="aligned_joints.h5")
  n_with_timestamp: 7 / 40
  main_timestamp           status=ok             span=471.14s  rate≈30.0Hz
  timestamp/camera/*       status=ok             (6 路)
  action/joint/position    status=no_timestamp   ← 帧数 14135，与主时钟同帧
  state/end/pose           status=no_timestamp   ← 帧数 14135，与主时钟同帧
  state/joint/position     status=no_timestamp   ← 帧数 14135，与主时钟同帧
  （其余 24 条 action/state 同为 no_timestamp）
```

`reason` 一律是"该子流无时间戳字段（或读取失败）"。

**事实**：这 27 条 action/state 流与 `main_timestamp` **共享同一 14135 帧**
（`frame_index` 0…14134 逐帧对应）。它们在事实上**是可时间对齐的**——
第 i 帧的动作/状态数据，就发生在 `main_timestamp` 的第 i 个时刻。

**后果**：用户问"h5 内部各子流对齐如何"，只能得到 7 条时间戳流的结果；
27 条真实遥测流的"帧 ↔ 时间"关系不可得。上次会话中 agent 回答
"h5 内部只能靠帧索引对齐，不存在时间对齐概念"，在**这个层面仍然是事实**。

## 2. 为什么不能简单地"给这些流补一列时间戳"

要警惕一个错误做法：既然 `main_timestamp` 有 14135 个值、这些流也有 14135 行，
那就把它们横向拼接。**这是错的**，因为：

1. **帧数一致 ≠ 逐帧对应**。帧数相同可能是巧合同长；真正保证对应的是
   `frame_index` 列（0…14134 且无重复无缺口）。必须**显式校验 frame_index**，
   而不是靠行数相等。
2. **会改变流的语义**。把主时钟"写进"某条子流，会让用户以为该流自带时间戳。
   实际上时间轴来自**容器的共享主时钟**，不是该流自身的属性。二者在数据
   溯源上必须区分——否则用户拿这份数据做训练时，会误以为每个传感器都独立
   打了时间戳。
3. **不得扩展到异构情况**。若某流的帧数与主时钟不同（真实数据集里
   `txt` 侧 14140~14142 行 vs h5 14135 帧），绝不能"截断/补齐后硬对齐"。

故本设计要求：**回退必须显式、必须可溯源、必须校验、不得静默**。

## 3. 设计

### 3.1 回退的触发条件（四个条件同时满足才回退）

1. 该子流**自身**确实没有可用时间戳列（现有逻辑判定为 `no_timestamp`）；
2. 该子流所在容器内**存在**一个可用的主时钟节点（`main_timestamp` 等，
   即 `timestamp_index` 类且能被读出）；
3. 该子流带 `frame_index` 列，且主时钟的行数 == 该流的行数 ==
   `frame_index` 的唯一值个数（**严格一致**，不做截断/补齐）；
4. `frame_index` 为 0…N-1 的连续整数（无重复、无缺口、无乱序）。

任一不满足 → **不回退**，保持 `no_timestamp` 并如实说明原因。

### 3.2 主时钟节点的选取

容器内可能有多个候选（`main_timestamp` + 6 路 `timestamp/camera/*`）。
选取规则（确定性，不猜）：

1. 节点名精确等于 `main_timestamp` → **优先**（语义最明确，就是主时钟）；
2. 否则取路径含 `timestamp` 且**不含 `camera`** 的 `timestamp_index` 节点；
3. 否则取行数最大的 `timestamp_index` 节点；
4. 多个并列时按节点名字典序取首（保证可复现）。

选取结果**必须**写进返回，让用户知道时间轴取自哪个节点。

### 3.3 可溯源标注（诚实性核心要求）

按 `AGENTS.md` §3.4「LLM 假设不得替代工具验证」，回退结果必须让用户/模型
明确知道"这条时间轴不是该流自身携带的"。设计三处标注：

- `rows[]` 增加 `time_source` 字段：
  - `"stream"` —— 该流自带时间戳列（原有情形）；
  - `"container_master"` —— **回退**，时间轴来自容器主时钟；
  - `"none"` —— 确实无时间轴。
- 回退行同时带 `time_source_node`（如 `"main_timestamp"`）与
  `time_source_basis`（如 `"frame_index 逐帧对应，14135 帧严格一致"`）。
- `user_message` 汇总时**显式说明**回退了几条、依据是什么，如：
  "另有 27 条子流自身无时间戳列，但经 `frame_index` 与容器主时钟
  `main_timestamp` 逐帧严格一致（14135 帧），已按容器主时钟给出对齐；
  这些流的时间轴来自容器主时钟、非自身携带。"

**不得**把回退结果混入 `n_with_timestamp` 而不加区分——需拆分为
`n_with_timestamp`（自身有时间戳）与 `n_by_container_clock`（回退得到）。

### 3.4 不做的事（边界）

- **不改 `read_stream(want="timestamp")` 的返回语义**。该调用点被
  `check_temporal_sync` 等多处复用，静默回退会污染其它工具的结论。回退只在
  `align_container_streams` 的容器上下文里生效（那里已知容器内全部子流）。
- **不为 txt/csv 目录型数据做同类回退**。那些是独立文件、无容器概念、
  也没有共享主时钟的确定性依据。
- **不跨容器回退**（h5 的子流不得回退到别的容器的主时钟）。
- **不修改任何数据文件**，只在工具返回里提供对齐视图。

## 4. 影响面

| 工具 | 变化 |
|---|---|
| `align_container_streams` | 27 条 action/state 从 `no_timestamp` 变为可对齐（标注 `time_source="container_master"`）；新增 `n_by_container_clock` |
| `check_temporal_sync` | **不变**（走 `read_stream`，不经本回退） |
| `load_dataset` / `inspect_streams` | **不变** |
| 主表 / 数值 | **完全不变**（只增加对齐视图，不写入数据） |

## 5. 测试计划

1. **回退生效**：帧布局 h5（14135 帧，含 `main_timestamp` + 无时间戳的
   `state/joint/position`），断言 state 流拿到主时钟、`time_source` 标注正确。
2. **严格一致校验**：构造"帧数一致但 frame_index 不连续/有重复"的数据，
   断言**不回退**（防"巧合同长"误对齐）。
3. **帧数不一致不回退**：sub 流帧数 ≠ 主时钟行数时保持 `no_timestamp`。
4. **无主时钟不回退**：容器内无 `timestamp_index` 节点时保持原行为。
5. **相机流不受影响**：6 路 `timestamp/camera/*` 仍用自身时间戳
   （`time_source="stream"`），不被主时钟覆盖。
6. **可复现性**：多候选主时钟时选取结果稳定。
7. **端到端**：真实形态数据集上 `n_by_container_clock == 2`（27 条中的部分）
   且 `n_with_timestamp == 7` 不变。

## 6. 待确认

1. **回退是否默认开启**？（推荐：默认开启但必须带 `time_source` 标注——
   否则用户拿不到这个显然可得的信息；标注已保证诚实性。）
2. **`n_with_timestamp` 是否包含回退行**？（推荐：**不包含**，另设
   `n_by_container_clock`，避免用户误以为 27 条流自身都有时间戳。）

两点均已按推荐实现（默认开启 + 拆开计数）。实施中另发现两个必须记录的坑：

### 6.1 主时钟被回退流"抢占"（实施中实测发现并修复）

初版实现后，`master` 报成了 **`action/joint/position`** 而非 `main_timestamp`。
根因：主时钟选取规则是"跨度最大者"，而回退流的**时间轴是从主时钟借来的**，
与 `main_timestamp` 同跨度；`max()` 遇平局按字典序，`action/...` 排在
`main_timestamp` 之前 → 数据流"赢"了。

这在本工具里是**语义错误**（master 应为时钟节点本身，不是借了时间轴的数据流）。
修复：把回退流（`time_source="container_master"`）排除在 master 候选之外，
仅在**没有任何自带时间戳的流**时才回退到用 `ok_rows` 选。
若有测试不覆盖此点，很容易漏过。

### 6.2 每帧多行的 `(2,4)` 流按严格校验被拒（有意行为）

真实数据集里 6 条流保持 `no_timestamp`，其中 4 条是 `(2,4)` 双手机布局
（`action/end/orientation`、`state/end/orientation`、`state/end/arm_orientation`、
`action/end/position`）——它们每帧产生 **2 行**，故 `frame_index` 会**重复**
（14135 个帧号 / 28270 行），按"逐帧 1:1 + index 连续"的严格校验不通过。

**这是有意的**：它们与主时钟的对应关系是"1 帧 → 2 行"而非 1:1，若要回退需
定义"每帧多行时如何展开时间轴"（重复同一时刻？还是等分间隔？）——两种都
可能错，且涉及数据语义判断。按本设计 §2 的原则（不得静默、不得猜），
**保持不回退**，并在 `reason` 里如实说明"frame_index 有重复、逐帧 1:1 校验
不通过、这是有意的严格校验"。

如需支持这类流，应单独立项：先确定"每帧多行"的时间轴语义，再放开校验。
