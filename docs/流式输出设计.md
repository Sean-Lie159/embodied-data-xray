## 1. 问题与价值

### 1.1 现状（已核实代码）

全项目搜索 `run_streamed` / `write_stream` / `stream_events` **零命中**——每一轮回答
都是"转圈等到底、然后整段蹦出来"：

```218:296:streamlit_app.py
                with st.chat_message("assistant"):
                    with st.spinner("分析中……"):
                        turn = service.reply(prompt)
                    st.markdown(turn.reply)
                    render_tool_activity(turn)
```

### 1.2 为什么在本项目里代价被放大（实证）

- `docs/行为测试.md` 记录实测：hy3 默认档**思考 token 占总输出 91%~96%**，
  一次 300 字分析问答约烧 900 个不可见思考 token，按 **13 ms/token** 折算，
  绝大部分等待花在思考上；
- SYSTEM_PROMPT 纪律 14/15 明确"批量纪律 / 耗时纪律"，正是因为**单轮可含十余次
  模型往返**（真实事故：检查 24 条流时整轮串行十余次往返触及上游 502）。

即：**单轮十几秒到几十秒是常态**。在这段时间里，用户只看到一个 spinner，
既不知道"在调工具"还是"在写正文"，也无法判断是否卡死。

### 1.3 流式能解决两件事

1. **首字节时间**：正文开始生成即可见，等待体感从"卡住"变为"正在进行"；
2. **过程可见**：工具调用可先播报（"正在检查时间同步……"），与项目一贯的
   "过程可见"理念（工具轨迹、耗时、token 全程可见）一致。

> `ARCHITECTURE.md` 4.5 早已写明方向："需要打字机效果时用 `Runner.run_streamed` +
> `result.stream_events()`；Streamlit 下用 `st.empty()` + `st.markdown` 尾部光标实现"。
> 本设计即该条的落地，并按当前代码结构（多会话、metrics、错误兜底）修订。

## 2. 技术障碍盘点（已核实代码）

| 障碍 | 位置 | 说明 |
|---|---|---|
| 同步包装死事件循环 | `chat_service.py:272` `return asyncio.run(self.areply(...))` | Streamlit 脚本同步，现用 `asyncio.run` 跑 async；流式需在**同一个**事件循环内消费生成器 |
| `run_turn` 返回契约是三元组 | `agent.py:364-494` | 流式返回的是"事件流"而非单一结果，需新增独立入口而非改签名（零回归） |
| 错误兜底要在流中生效 | `agent.py:446-483` | 现有 `try/except BaseException` 把 502 等转友好提示；流式下异常发生在**迭代中途**，兜底位置不同 |
| metrics 需回填 | `agent.py:403-410` | `_finish` 统一回填；流式需在流结束时回填 |
| 历史压缩在送模型前 | `agent.py:412-433` | 流式同样需要，抽公共函数复用 |
| `ChatTurn.findings` 等收尾字段 | `chat_service.py:289-301` | 流结束后才能拿到，需在生成器最后 yield 一个"收尾对象" |

## 3. 设计

### 3.1 分层与接口（核心）

**原则：不改 `run_turn`、不改 `ChatService.reply`**（零回归），新增并行路径。

**第 1 层 `app/agent/agent.py`** 新增：

```python
async def stream_turn(
    agent, context, user_input, history_input=None, max_turns=15, *,
    history_budget_tokens=None, history_keep_recent_turns=None,
    metrics: RunMetrics | None = None,
) -> AsyncIterator[TurnEvent]:
    """流式执行单轮；yield 事件序列，最后一项为收尾事件（含 final/next_input）。

    与 run_turn 共用：历史压缩、错误兜底、metrics 回填（抽公共私有函数）。
    """
```

事件类型（`dataclass`，放 `agent.py` 或新 `app/agent/events.py`）：

```python
@dataclass
class TurnEvent:
    kind: str            # "delta"（正文增量）| "tool"（工具调用播报）| "done"（收尾）
    text: str = ""       # kind=delta 时的正文片段
    tool_name: str = ""  # kind=tool 时的工具名（用于播报"正在检查…"）
    final: str = ""      # kind=done 时的完整正文（与 delta 拼接结果一致）
    next_input: list | None = None   # kind=done：供下一轮
    result: RunResult | None = None  # kind=done：供 ChatTurn 提取 usage/tool_calls
    error: str | None = None         # kind=done：异常兜底提示（复用 _describe_model_error）
```

**第 2 层 `app/services/chat_service.py`** 新增：

```python
def reply_stream(self, user_input: str) -> Iterator[StreamChunk]:
    """同步流式接口：内部 asyncio 事件循环消费 stream_turn，逐块 yield。

    yield 的中间块只含正文增量与工具播报；最后一块含完整 ChatTurn
    （与 reply() 返回的 ChatTurn 同构，UI 侧收尾逻辑可完全复用）。
    """
```

`StreamChunk`：`{kind: "delta"|"tool"|"final", text, turn: ChatTurn | None}`。
**关键**：最后一块携带**完整 `ChatTurn`**（含 findings / usage / metrics），
这样 UI 侧的"累计 token / 写 messages / 渲染工具轨迹"逻辑与现状**逐行一致**。

**第 3 层 `streamlit_app.py`** 消费：

```python
with st.chat_message("assistant"):
    placeholder = st.empty()
    acc = ""
    turn = None
    for chunk in service.reply_stream(prompt):
        if chunk.kind == "tool":
            placeholder.markdown(f"_{chunk.text}_")   # 斜体播报"正在检查…"
        elif chunk.kind == "delta":
            acc += chunk.text
            placeholder.markdown(acc + "▌")           # 尾部光标
        else:
            turn = chunk.turn
    placeholder.markdown(turn.reply)                  # 收尾去掉光标
    render_tool_activity(turn)
```

### 3.2 同步/异步桥接（当前最需要想清楚的一点）

现状 `reply()` 用 `asyncio.run(self.areply(...))` 一次性跑完。

流式的困难：`asyncio.run` 会**开一个新循环并跑到结束**，无法"把生成器交出去
由外部逐个消费"。两种实现方案：

**方案甲（推荐）：自建事件循环 + 队列桥接**

```python
def reply_stream(self, user_input: str) -> Iterator[StreamChunk]:
    import queue, threading, asyncio

    q: queue.Queue = queue.Queue()
    _DONE = object()

    async def _pump() -> None:
        try:
            async for ev in stream_turn(self.agent, self.context, composed,
                                        self.history_input, ...):
                q.put(ev)
        except BaseException as exc:      # 兜底：异常也要送到消费端
            q.put(exc)
        finally:
            q.put(_DONE)

    def _run() -> None:
        loop = asyncio.new_event_loop()
        try:
            loop.run_until_complete(_pump())
        finally:
            loop.close()

    t = threading.Thread(target=_run, daemon=True)
    t.start()
    while True:
        item = q.get()
        if item is _DONE:
            break
        if isinstance(item, BaseException):
            ... # 转友好提示块
        yield _to_chunk(item)
    t.join()
```

- 优点：Streamlit 同步脚本直接消费，**不引入 asyncio 与 Streamlit 的循环冲突**；
  异常经队列送达消费端（不会静默丢失）。
- 代价：多一个后台线程；需保证线程内的 `context` 修改在主线程可见（CPython GIL
  下 dict/list 赋值可见，且现有实现在单线程内修改 `context`，风险低）。

**方案乙：`st.write_stream` + 直接 async**

Streamlit 官方示例在 async 环境下可用 `st.write_stream(async_gen)`。**但**：
Streamlit 脚本是**同步**执行的（`asyncio.run` 的存在即证据），`st.write_stream`
对 async 生成器的支持依赖 Streamlit 内部对事件循环的处理，在"脚本已在同步、
且内部还要 `asyncio.run`"的组合下容易踩到 "event loop already running"。

**决策：采用方案甲**。它把"异步世界"完整封在 `ChatService` 内（符合分层：UI 不碰
asyncio），UI 只面对同步生成器，与现有 `reply()` 的调用风格一致。

### 3.3 工具播报的来源

`stream_turn` 在迭代 `Runner.run_streamed` 的事件流时，遇到工具调用事件
（`RunItemStreamEvent`，item 类型含 `tool_call`）即 yield `kind="tool"` 事件。

播报文案**用功能语言而非工具名**（与 SYSTEM_PROMPT 表述纪律 3 一致）：
- 需要一张 `工具名 → 功能描述` 映射表（放 `app/ui/` 或 `agent.py` 常量）；
- 映射缺失的工具降级为工具名本身（不静默丢弃）；
- **不播报参数**（避免把内部细节暴露给普通用户，与纪律 12"不展示工具名与参数"一致）。

### 3.4 错误兜底（流式下最容易出错的地方）

现状 `run_turn` 在一个 `try` 内 `await Runner.run(...)`，异常时返回友好提示三元组。
`stream_turn` 中异常可能发生在**已 yield 若干 delta 之后**（例：思考完成→开始输出
正文→上游 502）。处理：

1. 异常发生时**不再新 yield delta**，转而 yield `kind="done"`，其
   `error` 字段为 `_describe_model_error(exc)` 的文本，`final` 为空；
2. UI 收到 `error` 非空的 done 块 → **保留已输出的部分正文**，在其后追加一条
   ⚠️ 提示（含"重试本轮"按钮，见第 6 项文档）；
3. `next_input` 仍含本轮用户消息（与 `agent.py:475-478` 现有一致）——
   保证"直接重发"能接上；
4. `metrics.completed=False` 照常回填。

> 为什么不"清空已输出正文再显示错误"：用户已经看到的内容若突然消失，体验更差，
> 且违背"诚实降级"——已生成的部分是真实内容，应保留并明确标注未完成。

### 3.5 零回归保证

- `run_turn` **签名与返回契约完全不动**（本设计不 touch 它，只抽公共私有函数，
  抽的时候保持行为逐字节一致）；
- `ChatService.reply()` 保留（CLI `main.py` 仍在用），内部改为
  "消费 `reply_stream` 并取最后一块"或保持原实现皆可——**建议保留原实现**，
  避免 CLI 路径被流式改造波及；
- UI 侧用一个开关（见 3.6）允许回退到非流式，便于定位问题。

### 3.6 配置开关

新增 `Settings.stream_output_enabled: bool = True`（`.env`: `STREAM_OUTPUT_ENABLED`）。
- 默认开；置 `false` 时 UI 走现有 `service.reply()`（完全旧行为）；
- **为什么需要**：流式涉及线程与事件循环桥接，一旦在某环境下出问题，
  用户可立即用配置回退，而不是等修复 —— 符合"错误可恢复"。

## 5. 测试计划

**单元（不依赖真实模型，用假 agent/替身）**
- `stream_turn` 事件序列：至少一个 `delta`、一个 `done`；`done.final` == 各 delta 拼接；
- 异常中途发生：已 yield 的 delta 仍在，`done.error` 为友好文本，`next_input`
  含本轮用户消息（**回归关键**）；
- `metrics` 在成功/异常两分支都回填且 `completed` 如实；
- `reply_stream` 最后一块 `turn` 与 `reply()` 返回的 ChatTurn 结构同构
  （findings / usage / metrics 字段齐全）。

**UI（AppTest）**
- 流式开启时输入不崩、assistant 消息出现；
- 流式关闭（配置）时走旧路径不崩（**回退路径必须有用例**）。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 线程 + 事件循环桥接引入偶发死锁 | 队列 + daemon 线程；`_DONE` 哨兵；配置开关可一键回退 |
| 流式下 `context` 跨线程可见性 | CPython GIL 下 dict/list 赋值可见；工具本身仍串行执行不并发 |
| Streamlit 重跑导致同一流被消费两次 | 流式消费在 `if prompt:` 分支内（每次重跑 prompt 为空时不进入） |
| 中途异常时 metrics 与 usage 缺失 | `done` 块始终携带 turn；`usage` 取不到为 None（UI 已支持 None） |
| 首字延迟未改善（思考阶段无输出） | **诚实告知**：可在 spinner 阶段显示"模型思考中…"；本设计不承诺思考 token 可见（网关不透传） |

> 最后一条要明确告知 owner：**流式能改善"正文生成阶段"的体感，但思考阶段的
> 等待无法消除**（思考 token 不可见）。若某轮耗时几乎全在思考，用户仍会等——
> 这正是 `reasoning_effort` 配置（可调 low）与"批量纪律"存在的意义，流式是补充而非替代。
