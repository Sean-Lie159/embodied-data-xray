# H5 节点形态接纳设计（帧内标量时间戳被漏登记修复）

> 状态：**已实施**（2026-09-20 用户确认三点取舍后完成，全量测试 1156 passed / 1 skipped）
> 触发问题：真实数据集 `2655849` 的 `record/aligned_joints.h5`（513MB）中
> 每帧都带 `main_timestamp`（0 维标量 uint64）与 `timestamp/camera/<name>`
> （6 路 `shape==(1,)` uint64），但 agent 回答"h5 里没有时间戳"。

## 1. 问题陈述

### 1.1 现象

用户加载 `...\2655849\2655849`（PICO 具身采集目录）后提问三件事：h5 内是否有
时间戳、h5 内各子流对齐如何、h5 时间戳与 `camera/<相机>/<同名>.txt` 的对齐如何。
agent 的结论是"h5 的 27 个子流均无可用时间戳字段"，因此只能按 `frame_index`
（14135 帧）对齐，h5 ↔ txt 无法做时间对齐。

而真实文件里每帧确实都有时间戳（实测第 0/1/14134 帧叶子集合一致）：

```
0/
├── action/…                     （52 个数值组，如 action/joint/position (14,)）
├── main_timestamp               shape=()  dtype=uint64    ← 被漏掉
├── state/…
└── timestamp/camera/            ← 整个组被漏掉
    ├── hand_left_color          shape=(1,) dtype=uint64
    ├── hand_right_color         shape=(1,) dtype=uint64
    ├── head_color               shape=(1,) dtype=uint64
    ├── head_depth               shape=(1,) dtype=uint64
    ├── head_stereo_left         shape=(1,) dtype=uint64
    └── head_stereo_right        shape=(1,) dtype=uint64
```

`main_timestamp` 首值 `1756265284805200809`（ns epoch），中位间隔 33447424 ns
（29.898 Hz），跨度 471.140 s。

### 1.2 根因

`load_dataset._list_hdf5_native_nodes` 的 `_visit` 回调只接纳**三种形态**：

```python
if dtype.names:                              # compound
elif node.ndim == 2:                          # 2D 数值
elif node.ndim == 1 and node.shape[0] > 1:    # 1D 且元素 >1
else:
    return                                    # ← 其余全部静默丢弃
```

`main_timestamp` 的 `ndim == 0`、`timestamp/camera/*` 的 `shape[0] == 1`
（`1 > 1` 为 False），双双落入 `else: return`。

实测 `_list_hdf5_native_nodes` 输出 27 条流，**全部是 action/state 数值节点**，
7 个时间戳节点一条未登记。这 27 条正是 agent 看到的清单。

### 1.3 关键区分（诚实归因）

`is_timestamp_like_field("main_timestamp")` 实际返回 **True**——**字段判据是
正确的**（既有测试 `test_timestamp_field_candidates_exclude_diff_kinds` 已锚定）。
缺陷纯粹在**节点枚举**：时间戳节点根本没进入登记表，轮不到字段判据发挥作用。

因此 agent 的回答在**工具口径内是自洽的**：那 27 条已登记子流确实都没有时间戳
列（它们是数值轨迹）。真正的错误在措辞层面——工具把"我登记到的子流没有时间戳"
表述成"这个容器的子流都没有时间戳"，两者在用户侧几乎无法区分。

### 1.4 代价

| 能力 | 现状 | 修复后应得 |
|---|---|---|
| `align_container_streams` | `error="no_timestamp"` 早退 | 27+7 条子流参与对齐 |
| `inspect_streams` 采样率 | 全部 `present=False` | h5 主时钟 ~29.9Hz |
| h5 ↔ txt 跨容器对齐 | 不可执行 | 可给出时间级残差与尾部截断量 |
| h5 帧数 vs txt 行数差 | 只能"1:1 假设 + 5~7 行对不上" | 起止偏移可精确定量 |

已实测可得的真值（证明损失是实质性的）：`head_depth.txt` 首值与 h5 首帧
`main_timestamp` **逐位相同**（起点对齐）；9 个 txt 末值统一为
`1756265756112163489`，比 h5 末值晚约 **166.7 ms**（差异集中在尾部）。

## 2. 设计目标

1. **不再按"维数枚举"接纳**，改为按**语义规则**接纳：只要叶子是"可表格化的
   数值观测"，就应登记。
2. **不引入噪声**：不得把字符串/object/非数值叶子放进登记表
   （反例：`state/end/errmsg` 是 `dtype=object`、`shape=(1,)` 的字符串字段，
   现有 `dtype == object and node.shape == (1,)` 规则正在正确排除它）。
3. **行数口径一致**：登记表 `rows`、`read_hdf5_nodes_metadata` 的 `shape`、
   `_read_frame_layout_node` 实际读出的行数，三处必须自洽。
4. **零回归**：既有 27 条流的行数/列数与现在完全一致。

## 3. 设计

### 3.1 引入统一的叶子形态判定函数

新增纯函数 `_classify_h5_leaf(shape, dtype, frame_layout) -> dict | None`，
把"这个叶子能不能当表、行多少、列多少、字段名是什么"收敛为**一处**判据。
返回 `None` 表示不接纳（非数值 / 空 / 不可表格化）。

接纳规则（按优先级）：

| 形态 | 判据 | 非帧布局 | 帧布局 |
|---|---|---|---|
| compound | `dtype.names` 非空 | `rows=shape[0]`, `cols=len(names)`, `fields=names` | 同左（每帧含多行） |
| 2D 数值 | `ndim==2` | `rows=shape[0]`, `cols=shape[1]` | `rows=shape[0]`, `cols=shape[1]` |
| 1D 多元素 | `ndim==1 and shape[0]>1` | `rows=shape[0]`, `cols=1` | `rows=1`, `cols=shape[0]` |
| **1D 单元素** | `ndim==1 and shape[0]==1`（**新**） | `rows=1`, `cols=1` | `rows=1`, `cols=1` |
| **0 维标量** | `ndim==0`（**新**） | `rows=1`, `cols=1` | `rows=1`, `cols=1` |

**关键约束**：新增的两类必须同时满足 `_is_numeric_dtype(dtype)`，否则返回
`None`。这保证 `dtype=object`（字符串/嵌套）的叶子仍被排除，
`state/end/errmsg` 不会被误纳入。

`_is_numeric_dtype` 实现用 `np.issubdtype(dtype, np.number) or
np.issubdtype(dtype, np.bool_)`，并显式排除 `object`/`str`/`bytes`。

### 3.2 帧布局下"标量/单元素"的行数语义（核心设计决策）

帧布局（每帧一组）下，每帧贡献的"行数"必须与 `_read_frame_layout_node`
的拼接口径一致。约定：

- 0 维标量与 `shape==(1,)` 在帧布局下，**每帧贡献 1 行 × 1 列**。
- 合并后流 `rows = n_frames`（本例 14135），`cols = 1`。

选择 `1 行` 而非 `0 行`的理由：`main_timestamp` 是"每帧一个时刻"的观测量，
语义上与 `action/joint/position`（每帧 1 行 × 14 列）同级——都是"每帧一条观测"，
只是宽度为 1。这样 `_merge_frame_layout` 的 `rows × n_frames` 折叠规则可以
直接复用，无需为标量加特例。

`_finalize_frame_layout` 采首帧字段清单的逻辑同理适用（每帧都有
`main_timestamp` 与 6 路相机时间戳，实测已验证三帧叶子集合一致）。

### 3.3 同步修改点

**修改点 A**：`_list_hdf5_native_nodes._visit`（`load_dataset.py:552`）
把三分支替换为调用 `_classify_h5_leaf`，自行只负责路径拼接与 append。

**修改点 B**：`read_hdf5_nodes_metadata`（`load_dataset.py:782`）
当前列名推导只区分 `dtype.names` / `ndim==2` / `ndim==1 and shape[0]>1` /
`else`，行数推导只区分 `not frame_layout` / `ndim==2` / `else`。
需为"0 维标量、`shape==(1,)`"补分支：
- 列名：`[field_name]`（不用 `_0` 后缀，因为只有一列且语义就是该字段名本身）
- 帧布局行数：`rows = n_frames`
- 非帧布局行数：`rows = 1`

这样 `main_timestamp` 报为 `shape=(14135, 1)`、`columns=["main_timestamp"]`，
`is_timestamp_like_field("main_timestamp")` 命中 → 参与时间戳链路。

**修改点 C**：`_read_frame_layout_node`（`load_dataset.py:891`）
第 923 行的 `ndim == 1 and shape[0] > 1` 需扩展为"1D 且元素 ≥1"，即
`shape[0] >= 1`（或直接 `ndim == 1`），使 `shape==(1,)` 也被 reshape 为
`1 行 × 1 列`。0 维标量 `leaf[()]` 返回 numpy 标量，`_dataset_to_frame`
的 `pd.DataFrame(scalar)` 会抛错——需先 `np.asarray(x).reshape(1, 1)`。

**修改点 D**：`_classify_h5_node`（`load_dataset.py:607`）
字段清单为空时（2D/1D/标量节点）当前走路径判断。`main_timestamp` 与
`timestamp/camera/*` 的路径特征可用：
- 路径含 `timestamp` 且不含 `action`/`state` → 可新增 `kind="timestamp_index"`，
  `semantic_label="时间戳流"`，避免落进 `unknown` 触发 UI 的"未分类"提示。

此修改点优先级最低（不影响功能正确性，只影响语义标签质量），
但可显著改善用户观感——否则 7 条新流会全部显示"未知（无法分类）"。

### 3.4 性能考量

新增两个分支不改变遍历次数（仍只扫 `_FRAME_SCAN_SAMPLE_FRAMES=3` 帧），
`_classify_h5_leaf` 是纯 CPU 判据，无 I/O 开销。故不引入性能回归。

### 3.5 输出体积考量

新增 7 条流（1 主时间戳 + 6 相机时间戳），登记表条目从 27 增至 34 条，
远低于 `_MAX_STREAMS_PER_CONTAINER = 500` 上限，不触发截断护栏。

## 4. 影响面

| 工具 | 变化 |
|---|---|
| `load_dataset` | 流登记表新增 7 条时间戳流；`main_table` 选择**不变**（`main_timestamp` 行×列 = 14135×1，小于 `action/joint/position` 的 14135×14） |
| `inspect_streams` | 7 条新流的采样率可实测（~29.9Hz）|
| `align_container_streams` | 不再早退；34 条子流参与对齐 |
| `check_temporal_sync` | h5 节点流进入对齐链路 |
| `profile_data` / `plot_chart` | 可按 `table` 参数读取 `aligned_joints::main_timestamp` |
| UI 流清单 | 条目数 27 → 34 |

**主表不变**这一点需要明确：本修复**不会**让 h5 主表从动作流变成时间戳流，
因为排序键是 `rows × cols` 降序，`main_timestamp`（14135×1）远小于
`action/joint/position`（14135×14）。这是期望行为。

## 6. 待用户确认的取舍

> **2026-09-20 用户已确认：三点全部采纳。** 实施情况见下表。

| # | 取舍 | 决定 | 实施情况 |
|---|---|---|---|
| 1 | 标量/单元素在帧布局下登记为 1 行 | **采纳**（1 行 × 1 列） | 已实现：`_classify_h5_leaf` 统一判据，复用既有合并/拼接链路，无需特例 |
| 2 | 做修改点 D（时间戳流语义标签） | **采纳** | 已实现：新增 `kind="timestamp_index"`，主时钟与相机时间戳各有标签 |
| 3 | 如实标注相机路数不对称 | **采纳**（只标注、不补齐） | 已实现：`inspect_streams` 与 `align_container_streams` 均透出 `camera_coverage` |

### 6.1 取舍 1：登记为 1 行 × 1 列

理由是能无缝复用既有链路（`_merge_frame_layout` 的"行数 × 帧数"折叠、
`_read_frame_layout_node` 的按帧拼接），无需为标量开特例。
实测 34 条流的行数口径自洽：7 条时间戳流与 action/state 流同为 14135 行。

### 6.2 取舍 2：`timestamp_index` 语义标签

未做时这 7 条流会全部落到 `unknown` / "未知（无法分类）"，触发 UI 的
"未分类"提示。实现后：

- `main_timestamp` → `kind="timestamp_index"`，`semantic_label="主时钟时间戳（逐帧）"`
- `timestamp/camera/<name>` → `kind="timestamp_index"`，`semantic_label="相机采集时刻（逐帧时间戳）"`

判定要点（两个易错处，均已加测试）：

1. **必须排除 action/state 路径**——`state/*`、`action/*` 下也可能有叫
   `timestamp` 的叶子，靠路径白名单（`action`/`state`/`calibration` 一律不认）防误报。
2. **相机叶子名不含任何时间词根**（`head_color`、`head_stereo_left` 等），
   语义在父级路径 `timestamp/` 上。故 `is_timestamp_like_field` 新增
   "路径上下文形态"分支：父级含 `timestamp`/`stamp`/`clock` 等词根且叶子名
   不含动作/状态语义词时判为时间戳。

### 6.3 取舍 3：相机路数不对称如实标注（只标注、不补齐）

真实数据集实测：h5 内 `timestamp/camera/` 有 **6 路**，`camera/` 目录下有
**9 路**同名 txt，多出的 3 路是 `head_back_fisheye`、`head_left_fisheye`、
`head_right_fisheye`。

实现为 `_camera_coverage_note()`（`inspect_streams.py`）与
`_collect_camera_names()`（`align_container.py`），两者都返回
`camera_coverage = {h5_cameras, dir_cameras, only_in_h5, only_in_dir, note}`，
并把 `note` 同时写进 `user_message`（否则模型看不到——其余字段是给 UI 用的）。

**关键的"不补齐"约束**（写入提示文案，防模型臆造）：只列出"哪侧存在哪些相机"，
不臆造 h5 里不存在的相机时间戳、也不为缺失 txt 造数据。文案中显式声明
"仅如实标注、不补齐缺失侧"，避免模型据此虚构对齐结论。

边界（均已加测试）：两侧一致时 `note=None`（不制造无意义告警）；仅单侧存在时
也不报"不对称"（那是缺一类数据，不是不对称）；非 `camera/` 目录下的 txt
（如 `logs/imu_left.txt`）不得被算作相机路数；反向不对称（h5 有、目录无）
同样要报。
