## 1. 问题

### 1.1 已有基础（做得好的部分）

`app/agent/agent.py` 的 `_describe_model_error()`（`:296-361`）已把模型侧故障
分类为**可操作的中文提示**：502/503/504/429/401/404/上下文超限/网络各有话术，
且 `run_turn` 的异常分支**保留了本轮用户消息**（`:475-478`），使"直接重发"能接上。

`docs/行为测试.md` 有对应终身回归用例（"模型 API 异常不得炸穿界面"）。

### 1.2 缺口

**第一，提示里说"请直接重发这条消息即可"，但用户没有重发入口。**
用户看到：

```
模型服务暂时不可用（502 上游错误）——这不是数据或分析本身的问题，
通常是模型服务侧临时故障或过载。请稍后重试（直接重发这条消息即可）。
```

要"直接重发"，用户得**手动再打一遍**同样的问题（或从对话里复制粘贴）。
在一个"单轮十几秒起"的工具里，这是真实的摩擦。

**第二，失败轮在对话流里没有可识别的标记。** `metrics.completed=False` 已被记录
（`agent.py:409`），`render_tool_activity` 也显示"未正常完成"
（`components.py:61-62`），但那条 assistant 消息**外观上**与正常回答一样，
用户滚动历史时无法一眼看出"这条其实失败了"。

**第三，部分成功的流式轮次（第 1 项引入）需要明确的"未完成"呈现。**
按 `docs/流式输出设计.md` 3.4，中途 502 时保留已输出正文 + 追加提示；
这需要一个统一的"未完成"视觉与操作入口。

**第四，`messages` 与 agent 历史在失败轮的一致性没有 UI 层保障。**
`run_turn` 异常分支返回的 `next_input` **含本轮用户消息**，`ChatService.areply`
把它写回 `self.history_input`（`chat_service.py:281-286`）。所以 agent 侧是
一致的。但 UI 侧 `messages` 里追加的是"用户消息 + 失败的 assistant 消息"
（`streamlit_app.py:284` + `:305`）——**如果重试入口实现成"重新 append 一条
用户消息"，就会出现"同一条问题在 messages 里出现两次"**，历史渲染错乱。
这是本项最需要在设计上想清楚的点（见 2.3）。

## 2. 设计

### 2.1 失败轮的视觉标记

`ChatTurn` **已含** `metrics["completed"]`，无需改 service。UI 侧：

```python
def _is_failed(turn) -> bool:
    """该轮是否未正常完成（模型 API 异常或撞 max_turns）。"""
    m = getattr(turn, "metrics", None) or {}
    return m.get("completed") is False
```

- 失败的 assistant 消息外包一层 `st.warning`-style 边框（或标题前加 `⚠️ 本轮未完成`）；
- 正文保持在下方（流式的部分正文也要保留，见第 1 项文档 3.4）；
- **不改** `tool_activity` 面板（它已显示"未正常完成"）。

### 2.2 重试入口

在失败轮的 assistant 消息**下方**渲染：

```
⚠️ 本轮未完成
<正文或部分正文>
[🔁 重试本轮]   ← 按钮
（展开）查看执行过程
```

**按钮语义**：以**同一份用户输入**重新执行一轮。

### 2.3 重试的正确实现（核心，避免消息重复）

**错误做法**：`messages.append({"role":"user", "content": 上一轮输入})` 再 reply。
→ 同一条问题在 messages 里出现两次；且 agent 历史里本轮用户消息**已经存在**
（`run_turn` 异常分支已补上），再 append 会导致历史里出现两次同样输入。

**正确做法**：重试 = **替换而非追加**。具体：

1. 该失败轮在 `messages` 中的位置：`user_msg_idx`（用户消息）与
   `assistant_msg_idx = user_msg_idx + 1`；
2. 重试时：
   - `messages` 截断到 `user_msg_idx + 1`（丢弃失败的 assistant 消息）；
   - **不追加**新的用户消息（复用已有的那条）；
   - 调 `service.reply(原用户输入文本)`；
   - 成功后把新的 assistant 消息 append（经由 `_record_turn`，见第 5 项文档）；
3. **agent 历史侧**：`run_turn` 异常分支返回的 `next_input` **已含本轮用户消息**，
   直接在其上继续 `reply(原输入)` 会导致该输入在历史中出现两次。
   因此**必须**先调 `service.truncate_history_to_turn(user_msg_idx)`（现有方法，
   编辑重发已在用，`chat_service.py:303-325`）把历史回退到本轮之前，
   再 `reply`。

```python
def _retry_turn(service, messages: list[dict], cumulative: dict, idx: int) -> None:
    """重试第 idx 条用户消息对应的一轮（不新增用户消息）。

    idx 为该用户消息在 messages 中的下标。语义：
    1) agent 历史回退到本轮之前（避免同输入在历史中重复）；
    2) messages 截断到该用户消息之后（丢弃失败的 assistant 消息）；
    3) 用原文本重新执行；成功后经 _record_turn 追加新 assistant 消息。
    """
    user_text = messages[idx]["content"]
    service.truncate_history_to_turn(idx)   # agent 历史回退
    del messages[idx + 1:]                  # 丢弃失败轮及其后（与编辑重发语义一致）
    with st.spinner("重试中……"):
        turn = service.reply(user_text)
    _record_turn(cumulative, turn, messages)
```

> **注意**：`del messages[idx+1:]` 会**丢弃该失败轮之后的所有对话**。
> 但失败轮之后本就不可能有对话（失败轮是最后一轮才有重试按钮）——
> 因此该删除**实际只删掉失败的 assistant 消息**。为稳妥，重试按钮
> **仅在最后一轮失败时显示**（与编辑入口"仅最近一条用户消息显示"的先例一致，
> `streamlit_app.py:269`）。

**为什么复用 `truncate_history_to_turn`**：该方法的语义正是"把 agent 历史截断到
第 n 轮之前"，与编辑重发完全同构；复用它避免新增一套并行逻辑
（也避免第 5 项担心的"漏掉某处累加"类问题）。

### 2.4 与流式（第 1 项）的衔接

第 1 项落地后，`reply_stream` 的 `done` 块含 `error` 字段。重试入口的判定扩展为：

```python
_failed = _is_failed(turn) or bool(stream_error)
```

重试执行路径**统一走 `service.reply()`**（非流式）还是 `reply_stream()`？
- **建议走 `reply_stream()`**（若已启用），保持一致体验；
- 若第 1 项尚未落地（实施顺序为 0→5→2→1→6），本项先基于
  `service.reply()` 实现，第 1 项落地时把 `reply` 换成 `reply_stream`
  —— 因此**本项依赖第 1 项**（总纲第 5 节 C8 依赖 C7）。

### 2.5 其它错误恢复增强（小项，可一并做）

**第一，"压缩历史"的关联提示。** 上下文超限类错误的提示已指向侧栏「压缩历史」
（`agent.py:346-349`），但用户在对话区看不到那个按钮在哪。
可在错误消息下加一个**快捷按钮**"压缩历史并重试"：

```python
if _is_context_overflow(turn):   # 依据提示文本或 error 类型判定
    if st.button("压缩历史并重试"):
        service.compact_now()
        _retry_turn(...)
```

- 判定依据：`_describe_model_error` 的上下文分支是唯一含"上下文超出模型上限"的
  文本；**用类型判定更稳**——建议 `run_turn` 在 metrics 里增一个
  `error_kind` 字段（`None` / `"api"` / `"context"` / `"max_turns"`）。
  这是**新增字段**，不改现有字段（零回归）。

**第二，重试次数不做限制。** 用户自控；不做退避/自动重试（自动重试会掩盖问题，
且服务商配额风险）。

**第三，不做"编辑并重试"。** 编辑重发已存在（`streamlit_app.py:226-263`，
有 ✏️ 编辑入口）；重试不需要编辑能力，保持职责单一。

## 4. 测试计划

**单元（`_retry_turn` 逻辑，用假 service）**
- **不重复用户消息**：重试后 `messages` 中该用户消息**只有一条**（回归关键）；
- **agent 历史不重复**：`truncate_history_to_turn` 被以正确 idx 调用；
- **丢弃失败轮**：重试后原失败 assistant 消息不在 `messages` 中；
- **累加正确**：`_record_turn` 被调用一次，token/rounds 只加一次
  （防"重试导致统计翻倍"）；
- 首轮失败（idx=0）→ `truncate_history_to_turn(0)` 使历史清空，行为正确。

**UI（AppTest）**
- 构造 `metrics.completed=False` 的 turn → 失败标记出现、重试按钮存在；
- 正常轮 → **无**失败标记、**无**重试按钮（防误显示）；
- 重试按钮仅在最后一轮失败时出现。

**行为（`docs/行为测试.md` 追加终身回归）**
- 背景：502 后提示"直接重发"，但无入口；手动重打有摩擦，且历史上会出现重复输入；
- 期望：失败轮有明确标记与一键重试；重试后消息与历史**均不重复**；
  统计不翻倍。

**人工验收**
- 真实触发一次 502（或构造失败）→ 点击重试 → 正常回答；
- 检查侧栏 token 累计与轮数不存在异常增长。
