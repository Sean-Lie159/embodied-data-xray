## 1. 背景与目标

### 1.1 需求来源

用户提出为现有 Agent 新增三项能力：

1. **任务语义标注**——给数据集标注任务描述、语言指令、任务类别；
2. **任务切片标注**——把连续轨迹切成原子动作片段，schema 形如：

```json
{
  "id": 1,
  "start_timestamp": "00:00:00",
  "end_timestamp": "00:00:16",
  "atomic_action": "Place",
  "action_description": "右手用筷子将锅里的蔬菜夹到左手端的碗里",
  "action_description_en": "Right hand uses chopsticks to pick up vegetables from the pan and place them into the bowl held by the left hand",
  "interacting_hand": "right_hand",
  "target_object_class": "vegetables",
  "is_noise": false,
  "cleaning_reason": null
}
```

3. **质检**——基于针对具体数据集的质检标准做质量检查。

### 1.2 目标数据集与用途（用户已确认）

**格式：三类都要支持**——LeRobot v2、多流采集目录、HDF5。
**用途：三类都要**——下游训练真值、数据集发布元数据、内部数据清查。

这两个"都有"是本设计的核心约束，直接决定了第 3 节的架构决策：

- 格式都要 → 标注的**锚点（anchor）必须与格式解耦**，否则会长出三套平行代码；
- 用途都要 → 标注的**精度要求必须分级**，否则要么为训练真值卡死内部清查，要么为清查污染训练数据。

### 1.3 核心设计判断（可行性研究的结论）

| 子能力 | 可行性 | 关键依据 |
|---|---|---|
| 任务语义标注 | **高**，与既有 `propose_stream_semantics` 机制同构 | `app/tools/propose_semantics.py` + `profile_store.py` |
| 质检（动作/任务/标注级） | **高**，统一返回格式与 config 阈值已就绪 | `docs/ARCHITECTURE.md` §6.1、`app/config/settings.py` |
| 切片边界定位 | **高**，本体信号确定性计算，可单测 | 速度突变/夹爪状态变化；RDA 实测接管边界尖峰富集 3.1× |
| 切片动作命名 | **受限**，分层处理 | 见 §5.2 |

**最关键的架构事实**：当前模型 `hy3` **不支持视觉输入**。腾讯云官方文档原文"本文中的混元语言模型不支持图片、视频等多模态输入"，CodeBuddy 配置文档中 `hy3` 标 `"supportsImages": false`。因此 `action_description` / `atomic_action` **在纯文本链路下不得自动生成**——那会直接违反 SYSTEM_PROMPT 纪律 1（不得编造）与纪律 9（假设不得伪装成结论）。

## 2. 设计原则（继承项目既有纪律，不新立）

1. **确定性计算优先，LLM 只做叙述**——时间边界必须由信号算，不得由 LLM 猜。
2. **来源必须可溯源**——每条标注记录其来源（`user_confirmed` / `signal_derived` / `llm_proposed` / `imported`），与 `profile_store.py` 既有的 `label_source` 标记一脉相承。
3. **硬门禁与诊断项分离**——只有确定性错误可判 `fail`；启发式指标只 `warn`，永不自动升级为判定（RDA 的 65% 误报事故是前车之鉴）。
4. **阈值按数据集可配置**——不存在通用阈值；所有阈值集中在 `app/config/settings.py` 并在返回中带 `thresholds` 字段。
5. **诚实降级**——拿不到就说拿不到，字段填 `null` 并附原因，绝不硬猜。
6. **只读不越界**——标注产物只写入 `outputs/`，**绝不写入或修改源数据集**（与 `inspect_video_frame` 的"只读抽取"纪律一致）。
7. **格式无关**——格式分支只允许出现在「锚点解析」一处，其余全链路格式无关（ARCHITECTURE §3.3.1「语义角色优先，不绑定物理形态」）。

## 4. annotation_store：标注存储与规范化层

这是本设计的**核心新增抽象**，也是防止三套平行代码的关键。

### 4.1 为什么需要这一层

三种目标格式的 episode 语义互不相同：

| 格式 | episode 定位方式 | 时间基准 | 现状证据 |
|---|---|---|---|
| **LeRobot v2** | `episode_index` 列；`meta/info.json` 有 fps；`meta/tasks.jsonl` 有任务映射 | 帧号 / fps 推算秒 | README 已验证布局；`tests/fixtures/skeletons/lerobot_v2` |
| **多流采集目录** | `episode` / `ep` / `episode_id` / `traj_id` / `trajectory_id` **列名候选猜测**；可能整段只有一个 episode | 各路流的时间戳列（单位需推断） | `_data_access._EPISODE_COLS`；`timestamp_units` |
| **HDF5** | 容器节点路径（`<file>::<node>`）；帧布局可能按 `frame_0000` 分组 | 节点内时间字段（compound 的 `timestamp` 等） | `_read_h5_node_stream`、`_H5_FRAME_LAYOUT` |

若不做抽象，切片边界检测、命名落盘、质检三处都要写格式分支，共 9 个分支点，且行为必然漂移。抽象后**分支只落在 `resolve_anchors` 一处**。

### 4.2 核心数据结构：标注锚点（Anchor）

```python
@dataclass(frozen=True)
class EpisodeAnchor:
    """一个 episode 的统一锚点（格式无关）。

    为什么用 frozen dataclass：锚点会被多处读取并作为落盘索引键，不可变可避免
    下游无意修改导致"标注对不上数据"。
    """
    episode_key: str          # 稳定标识：LeRobot 用 "ep000123"；h5 用净化后节点路径；
                              # 多流目录用列值 "3"/"traj_003"；无可划分时用 "__all__"
    label: str                # 面向用户的展示名（如 "episode 123" / "容器节点 .../observation"）
    start_s: float | None     # 该 episode 起始秒（相对数据集/该流起点）；不可得为 None
    end_s: float | None       # 结束秒；不可得为 None
    start_frame: int | None   # 起始帧号；不可得为 None
    end_frame: int | None
    n_frames: int             # 帧数（必需，用于质检的时长一致性）
    time_column: str | None   # 该 episode 的时间列名（用于把秒映射回帧）
    anchor_source: str        # "lerobot_index" / "episode_column" / "h5_node" / "whole_dataset"
    evidence: str             # 判定依据（必须可转述，如"列 episode 的唯一值划分"）
```

### 4.3 落盘格式

**任务级标注** `outputs/by_dataset/<净名>/annotations/tasks.jsonl`，每行一个任务级标注：

```json
{"scope":"task","episode_key":"ep000123","task":"pick up the red block and place it in the bowl",
 "task_zh":"把红色方块捡起放进碗里","category":"pick_place","source":"user_confirmed",
 "confidence":"high","evidence":"用户确认","created_at":"2026-09-16T10:00:00Z"}
```

**切片级标注** `outputs/by_dataset/<净名>/annotations/segments.jsonl`，每行一个片段：

```json
{"scope":"segment","episode_key":"ep000123","id":1,
 "start_s":0.0,"end_s":16.0,"start_frame":0,"end_frame":400,
 "atomic_action":"Place","action_description":"右手用筷子将锅里的蔬菜夹到左手端的碗里",
 "action_description_en":"Right hand uses chopsticks to pick up vegetables from the pan and place them into the bowl held by the left hand",
 "interacting_hand":"right_hand","target_object_class":"vegetables",
 "is_noise":false,"cleaning_reason":null,
 "source":"llm_proposed","confidence":"low",
 "boundary_evidence":{"method":"velocity_change_point","peak_ratio":4.2}}
```

**设计决策与理由**：

- **为什么 JSONL 而不是每 episode 一个 JSON**：1000 episode 就是 1000 个文件；JSONL 逐行读写、可追加、项目已有 `read_jsonl_rows` 范式。
- **为什么保留 `start_timestamp` 字符串之外还要存秒与帧**：用户 schema 的 `"00:00:16"` 便于人读、不便于程序对齐。落盘存 `start_s` / `start_frame` 数值，**显示层格式化为 `HH:MM:SS`**，两者都要（训练真值需要精确帧号，元数据发布需要人类可读）。
- **为什么加 `source` / `confidence`**：直接对应用途分级（§4.4），也是 `label_source` 机制的自然延伸。
- **为什么加 `boundary_evidence`**：切片边界必须可解释——质检和人工复核都需要知道"凭什么在这里切"。

### 4.3.1 版本管理（用户已裁决：需要）

**需求**：三种用途并存意味着标注会长期迭代——尤其训练真值用途下，标注会被反复修正。必须能回答"这条标注是谁、什么时候、为什么改的"，以及"上一版是什么"。

**设计**：采用「**当前态 JSONL + 追加式修订日志 + 快照**」三层，避免引入 git 式复杂度：

```
outputs/by_dataset/<净名>/annotations/
├── tasks.jsonl              # 当前态（任务级），每 episode 一行，读时即最新
├── segments.jsonl           # 当前态（切片级），每片段一行
├── revisions/
│   ├── revisions.jsonl      # 追加式修订日志（只增不改，记录每次变更）
│   └── snapshots/           # 关键节点快照（发表/交付前冻结）
│       └── 20260916T103000_segments.jsonl
└── qc/<check>_<ts>.json     # 质检结果
```

**修订日志格式**（`revisions.jsonl`，每行一次变更）：

```json
{"ts":"2026-09-16T10:30:00Z","op":"update","scope":"segment","episode_key":"ep000123",
 "id":1,"actor":"user_confirmed","session_tag":"s-1a2b",
 "before":{"atomic_action":"Place","start_s":15.8},"after":{"atomic_action":"Pick_Up","start_s":16.0},
 "reason":"人工复核修正边界与动作名"}
```

**设计决策与理由**：

- **为什么不做完整版本控制（每次编辑存全量副本）**：标注文件可能很大（1000 episode × 数十片段），全量副本会迅速膨胀。追加修订日志只存增量 diff，体积可控。
- **为什么当前态单独存 `segments.jsonl` 而不从修订日志重放**：重放需要读全量日志、实现复杂且容易出错；当前态直读是 `O(1)` 语义，且**文件本身即人类可读、可手工编辑**（符合项目"画像文件可手改撤销"的既有理念）。
- **为什么需要快照**：训练真值与数据集发布是**冻结语义**——"发给下游的那一版"必须可回溯。快照只在交付前手动/工具触发，不做自动。
- **`actor` 与 `source` 的关系**：`source` 是标注**内容**的可信度分级（§4.4），`actor` 是**这次变更**由谁发起。两者不可混用——一次 `user_confirmed` 的编辑可以把某条的 `source` 从 `llm_proposed` 提升为 `user_confirmed`，这个提升动作本身也记在日志里。
- **配套接口**：

```python
def snapshot_annotations(output_dir, dataset_id, *, label: str) -> dict:
    """把当前态冻结为快照（交付/发布前用）。返回快照路径与记录数。"""

def load_annotation_history(output_dir, dataset_id, *, scope=None,
                            episode_key=None) -> list[dict]:
    """读取修订历史（可按 scope / episode_key 过滤），供 UI 展示"这条改过几次"。"""

def diff_snapshots(path_a, path_b) -> dict:
    """对比两个快照，返回新增/修改/删除三类差异（用于"这版和上版差在哪"）。"""
```

**规模控制**：修订日志做**软上限**（如单文件超过 N 万行时提示归档到 `revisions/archive/`），并在返回中如实报告体积——沿用项目"绝不静默截断"的纪律。

### 4.4 来源分级与用途的对应（关键设计）

| 来源 | 含义 | 下游训练真值 | 数据集发布元数据 | 内部清查 |
|---|---|---|---|---|
| `user_confirmed` | 人工输入或人工复核过 | ✅ 可用 | ✅ 可用 | ✅ 可用 |
| `signal_derived` | 由本体信号确定性算出 | ⚠️ 需人工复核后转 `user_confirmed` | ✅ 可用（须声明 `generated: true`） | ✅ 可用 |
| `llm_proposed` | LLM 生成、未经确认 | ❌ **禁止** | ⚠️ 须显式标注为推测 | ✅ 可用 |
| `imported` | 从外部文件导入 | ⚠️ 依赖外部质量 | ✅ 可用 | ✅ 可用 |

**硬约束**：`save_annotations` 与 `check_annotation_qc` 都必须校验用途合规性——若标注将以 `llm_proposed` 来源进入训练真值路径，**必须拒绝并提示先复核**。这是把"三种用途"落到代码里的具体机制。

## 5. 三项子能力设计

### 5.1 任务语义标注（`annotate_task`）

**形态**：与 `propose_stream_semantics` 同构的三态闸门。

```
候选提取（工具，确定性）→ 用户确认（对话）→ 落盘（confirm=True）
```

**候选来源**（按优先级，全部确定性，不猜）：

1. LeRobot 的 `meta/tasks.jsonl`（已有任务映射，直接读）；
2. 数据表中含语言/任务描述列（列名候选：`task` / `instruction` / `language` / `task_name` / `language_instruction`）→ 取其唯一值；
3. 文件名与目录结构中的任务线索（仅作**候选**，标注为待确认）；
4. 以上都无 → 返回 `no_task_signal`，**请用户提供**，不由模型编造。

**工具签名**：

```python
class TaskAnnotation(BaseModel):
    episode_key: str = Field(description="episode 标识（取自 resolve_anchors 的返回）")
    task: str = Field(description="任务描述（英文原文或用户给定原文）")
    task_zh: str = Field(default="", description="中文描述（可选）")
    category: str = Field(default="", description="任务类别（自由文本，建议取自配置的动词表）")

@tool
def annotate_task(
    wrapper: RunContextWrapper[RunContext],
    annotations: list[TaskAnnotation],
    confirm: bool = False,
) -> dict:
    """登记/落盘任务级语义标注（整段任务描述）。

    使用纪律（闸门）：confirm=False 只登记返回、不落盘；**必须在用户明确
    同意后**才可传 confirm=True。落盘来源标 user_confirmed。

    Args:
        annotations: 任务级标注清单，每条含 episode_key（取自锚点清单）、

        confirm: 是否落盘。

    Returns:
        dict，含 results（逐条，含 anchor 匹配结果与冲突提示）、validated

    """
```

**动词表配置**：不硬编码。`category` 的推荐取值来自可配置词表，初始骨架为 RT-1 的 9 类技能 + BridgeData V2 的 13 个 skill（见附录 A），存于 `app/config/` 或数据集画像，允许按数据集覆盖。

### 5.2 任务切片标注——分层处理（本设计的核心判断）

#### 5.2.1 问题拆解

切片标注 = **边界定位** + **动作命名**，二者可行性差距极大：

| | 边界定位（第几秒切） | 动作命名（这段叫什么） |
|---|---|---|
| 数据来源 | 机器人本体信号（关节/末端速度、夹爪状态） | 需要看懂画面 |
| 能否确定性计算 | ✅ 能 | ❌ 不能 |
| 当前链路是否可行 | ✅ 可行 | ❌ **hy3 无视觉输入** |
| 方案 | `segment_actions` 工具 | 人工 / 视觉模型（分层） |

#### 5.2.2 `segment_actions`：确定性边界检测

**输入信号**（按可得性降级）：

1. **末端执行器/关节速度曲线**——变化点检测；
2. **夹爪开合状态变化**——抓取与释放的物理标志（`gripper` / `gripper_position` 列）；
3. **加速度突波**——HF GIGO 公式：`θ > 15 × median(|a|)`，加速度代理 `a_t = (q_{t+1} - 2q_t + q_{t-1}) / (t_{t+1} - t_t)²`；
4. **低速段（停顿）**——速度低于阈值（GIGO 用 0.1）的连续段。

以上皆不可得时，返回 `no_motion_signal` + **明确说明缺少哪些列**，建议用户提供，**不做等分兜底**（等分基线在公开基准上 F1 仅 0.070，等价于无信息，且会诱导用户误信）。

**工具签名**：

```python
@tool
def segment_actions(
    wrapper: RunContextWrapper[RunContext],
    episode_key: str | None = None,
    table: str | None = None,
    method: str = "auto",
    min_segment_s: float | None = None,
    max_segment_s: float | None = None,
) -> dict:
    """用机器人本体信号做确定性动作切片，输出**候选边界**（不含动作名称）。

    只给边界，不给名字——命名需要视觉理解，当前模型不支持；请用户在
    对话中命名，或接入视觉模型后另行生成（见设计文档 §5.2.3）。

    Args:
        episode_key: 指定 episode（缺省对全部锚点执行）。
        table: 可选，指定状态/动作表名（缺省自动定位）。
        method: auto / velocity / gripper / combined（缺省 auto 按可得信号选）。
        min_segment_s: 最小片段时长（秒），短于此的相邻片段合并；缺省取配置值。
        max_segment_s: 最大片段时长（秒），超过则按最低信号谷值再切；缺省取配置值。

    Returns:
        dict，含 episodes（逐 episode 的候选片段列表，每段含 start_s/end_s/
        start_frame/end_frame/boundary_evidence）、method_used、signals_used、
        signals_missing（诚实列出欠缺的信号）、thresholds、n_segments。
    """
```

**粒度设计**：原子动作的合理时长**无公认标准**（DROID 5–20s 指整段轨迹、AgiBot 30–60s、OXE 多 <5s，均非原子片段粒度）。因此 `min_segment_s` / `max_segment_s` **必须可配置**，默认值仅为占位建议值，并在返回中标注"阈值为默认值，未经该数据集验证"。

#### 5.2.5 实施中确认的信号可靠性分级（重要结论）

阶段三实现与实测改变了本设计对四类信号的**信任排序**。结论如下：

**① 夹爪开合状态变化——可靠（应作为首选信号）。**
夹爪开合是**物理事件**，不受运动强度影响。实测在 4 段合成轨迹上**精确命中
全部真实边界**（100/200/300，误差 ≤1 帧）。建议用户在数据含夹爪通道时优先
依赖此信号。

**② 速度变化点——仅为候选，不可靠（实测确认的局限）。**
这一点经过**三轮修正**才认清，值得完整记录：

- *初版*（瞬时梯度判据 `|gradient| > ratio × median`）：在正弦轨迹上产出
  **120 个**候选（正弦过零处梯度本就大）——完全失效；
- *修正版*（先平滑、再取"连续变化带"每带一点）：仍产出 **49 个**——高频段
  内部的周期性波动本身就是大梯度；
- *本版*（**水平跃迁判据**：比较窗口前后的速度**窗口均值**）：改善为 12 个，
  但**仍含误报**。

**根本原因（这是通用信号判据的固有上限，不是实现缺陷）**：相邻动作段
若频率不同，高频段的窗口均速**天然更高**，判据无法区分"动作切换"与
"运动强度变化"。**仅凭关节速度无法判定语义上是否换了动作。**

因此本工具的定位调整为：**产出"值得人工查看的候选位置"**，而非"检测到的
动作边界"。该局限已在 `boundary_evidence.note` 与 `user_message` 中如实标注，
并有专门的回归测试守护这一表述（`test_velocity_signal_documented_as_candidate_only`）。

**③ 加速度突波——可靠但稀疏。** 对应碰撞/人工干预（HF GIGO 公式），
在无此类事件时不会触发（属正常，非缺陷）。

**④ 低速段边界——可靠但仅覆盖停顿。** 只能识别"停下来的地方"，
对连续动作之间的切换无能为力。

**对方案的影响**：原设计 §5.2.2 曾把四类信号并列。实测后明确为
**"夹爪优先、速度仅作补充候选、必须人工复核"**。这也从另一个角度强化了
§5.2.4 的结论——自动切片的质量上限不高，人工复核不是可选项而是必需环节。

#### 5.2.3 动作命名的两条路线（分层，不做二选一）

**路线 1（默认，当前链路即可行）：人工命名。**
`segment_actions` 输出候选边界 → `check_annotation_qc` 校验边界合理性 → 用户在对话或 UI 中命名 → `save_annotations` 落盘，来源 `user_confirmed`。

**路线 2（可选增强，需换模型）：视觉模型生成草稿。**
前置条件是先把 `DEFAULT_MODEL` 从 `hy3` 换为支持视觉的模型。**成本是本项目的核心约束**（当前 hy3 免费），完整选型与成本核算见 §5.2.4。

**必须实测验证的前置项**：CodeBuddy/CloudBase 网关可能对模型做了白名单裁剪——**模型本身支持视觉 ≠ 网关放行**。动工前须先用 `curl` 直连确认目标视觉模型能否返回图片描述。

#### 5.2.4 视觉模型选型与成本核算（用户重点关注项）

**前提澄清**：当前 `hy3` 是免费模型（用户最在意的成本优势）。切换到任何视觉模型都意味着**开始产生费用**，因此本节的结论是"按需启用、不做默认切换"。

**图片 token 换算是成本的主因**，各家规则不同：

| 厂商 | 图片 token 规则 |
|---|---|
| 腾讯混元 | 1024×1024 ≈ **1058 token**；768×768 ≈ **602 token**（实测 hy-vision-2.0 单图 total 340、双图 800） |
| OpenAI | 按 tile 计费（低/高细节模式不同） |
| Qwen-VL / GLM / Gemini | 各有独立换算规则 |

**关键成本杠杆**：图片 token 与分辨率近似平方关系。**从 1280×960 降到 640×480 可省约 75% 的图片 token**。对"判断手在做什么"这类任务，640×480 通常已足够——这是最有效的降本手段。

**成本实算（场景：60 秒 / 30fps 机器人操作视频，需生成约 10 个动作片段描述）**

方案 A（抽帧）：每 2 秒抽 1 帧 = 30 张图。按 640×480 档估算，单张约 265 token（1024×1024 的 1/4），30 张 ≈ 8,000 token 输入。

| **零成本验证** | 阿里百炼 `qwen3-vl-flash`（100 万免费额度） | 0（额度内） | 需换 base_url 与模型名；验证自动命名可行性 |
| **低成本生产** | `qwen3-vl-flash` 或 `混元 HY-Vision-2.0` | ≈0.07–3.6 元/小时视频 | 混元同厂商同网关，切换最平滑 |
| **效果优先** | `Kimi K3` / `GLM-5V-Turbo` | ≈2.4–9.6 元/小时 | 支持视频直接输入，但成本高两个量级 |

**决策建议**：**默认保持 `hy3` + 人工命名（零成本）**，把视觉模型作为**可选配置项**（如 `.env` 新增 `VISION_MODEL` / `VISION_BASE_URL`，与主模型解耦）。这样既守住"当前免费"的成本底线，又为将来启用留好接口。**不要在阶段五之前改动默认链路。**

**关于视频输入的额外约束**：混元 video 模型与部分厂商**仅接受公网 URL、不支持 base64**（混元已确认），这与项目"本地运行、不发起网络请求"的定位有张力。GLM 文档另有"不支持同时理解文件、视频和图像"的限制。**建议先以单帧方案验证，不急于引入上传链路。**

**若走路线 2，两条硬约束不得放宽**：

1. 生成的标注来源**只能**是 `llm_proposed`，`confidence` 只能是 `low`，且**禁止**在 `user_confirmed` 之前用于训练真值；
2. 公开基准实测显示，最佳自动子任务分割 Segment F1 仅 **0.306**（IoU ≥ 0.75 严格匹配）、端到端 F1 仅 **0.168**（WGO-Bench，743 个人工标注片段）。**该精度不支持无复核入库**——所有视觉生成结果必须经人在回路校验。

**关于视频 vs 单帧**：动作描述本质是时序任务，单帧信息量有限。若走路线 2，优先评估 `hunyuan-turbos-vision-video` 传整段视频；但其只接受公网 URL，与项目"本地运行、不发起网络请求"的定位存在张力（需先上传至公网可访问位置）。**建议先以单帧方案验证可行性，不急于引入上传链路。**

### 5.3 质检（`check_dataset_quality`）

#### 5.3.1 设计依据

**重要定性结论**：具身智能领域**没有单一权威的公开质检标准**。可依据的四类资源：

1. 论文中的定性 QC 流程（DROID 的成功/失败过滤与多标注冗余；AgiBot 的三阶段 + 人机回环；RoboMIND 的 **8 项质量保证标准**）；
2. 格式规范硬约束（LeRobot 的 `fps > 0`、版本兼容、`finalize()`）；
3. 量化质量指标与公式（HF GIGO 的过暗/模糊/碰撞/饱和/空闲/路径效率）；
4. 社区工具源码（**RDA 的四层框架**最值得借鉴）。

**照搬 RDA 的核心设计哲学**：只有 L1 硬完整性检查能触发 `EXCLUDE`/`fail`；L2/L3 诊断项**永不自动升级为判定**。作者披露早期版本因让 `idle_ratio` 自动升级，在 libero_10 上产生 **65% 误报**，改架构后误报减少 97–100%。

#### 5.3.2 规则包设计（照搬既有统一返回格式）

复用 `check_temporal_sync` 的返回模板，新增**分层 `result` 语义**：

```python
{
  "success": True,
  "dataset": "<dataset_id>",
  "check": "check_dataset_quality",
  "result": "pass" | "warn" | "fail",      # 由硬门禁决定；诊断项只能影响 warn
  "gate": {                                 # L1 硬门禁（可 fail）
    "result": "pass",
    "checks": {
      "timestamp_monotonic": {"result": "pass", "detail": "..."},
      "nan_inf":             {"result": "fail", "detail": "...", "affected": [...]},
      "frame_loss":          {"result": "warn", "detail": "..."},
      "schema_consistency":  {"result": "pass"}
    }
  },
  "diagnostics": {                          # L2/L3 诊断（仅 warn，永不 fail）
    "result": "warn",
    "checks": {
      "idle_ratio":        {"value": 0.72, "threshold": 0.60, "result": "warn",
                            "note": "阈值按数据集配置；高空闲比对 push 类任务可能正常"},
      "action_spike":      {"value": 33,   "threshold": 15, "result": "warn"},
      "velocity_smoothness":{"value": 0.83,"result": "info"},
      "path_efficiency":   {"value": 0.61, "result": "info"}
    }
  },
  "measurements": { ... },                  # 实际计算出的指标（与 thresholds 分离）
  "thresholds": { ... },                    # 判定所用阈值（来自 config / 数据集配置）
  "threshold_source": "default" | "dataset_override",
  "affected_episodes": [ ... ],
  "not_audited": [ "video_freeze", "..." ], # 明确标注"未检查"，不得报为 pass
  "user_message": "..."
}
```

**规则清单（分两层）**：

**L1 硬门禁（确定性错误，可判 `fail`）**——所有工具/论文的"最小公分母"：

| 规则 | 判据 | 参照 |
|---|---|---|
| `invalid_values` | NaN / Inf 占比 > 阈值 | RDA 盲测 10/10 检出 |
| `timestamp_monotonic` | `diff(timestamp) < 0` | RDA `temporal_validity` |
| `frame_loss` | 帧计数与时间戳行数/预期不符，缺口检测 | `check_temporal_sync.locale_gaps` 已有能力 |
| `schema_consistency` | 跨 episode feature/dtype 不一致 | LeRobot 规范 |
| `fps_positive` | fps ≤ 0 或缺失 | LeRobot 源码硬校验 |
| `episode_bounds` | 标注的 `end_s` 超出 episode 实际时长 | **本设计新增，见 5.4** |

**L2/L3 诊断（启发式，仅 `warn`）**：

| 规则 | 判据 | 阈值来源 | 参照 |
|---|---|---|---|
| `idle_ratio` | 速度 < 0.1 的步数占比 | 可配置，默认 0.6 | HF GIGO |
| `action_spike` | `θ > 15 × median(\|a\|)`，`a_t=(q_{t+1}-2q_t+q_{t-1})/(t_{t+1}-t_t)²` | 15（公开公式） | HF GIGO |
| `actuator_saturation` | `\|a_t - q_{t+1}\| > 7°` | 7° | HF GIGO |
| `visual_dark` | `max(0, (50 - μ)/50)`，μ 为灰度均值 | 50/255 | HF GIGO（**只罚过暗不罚过曝**） |
| `visual_blur` | 拉普拉斯方差 `Var(ΔI)`，核 `[0,1,0;1,-4,1;0,1,0]` | 可配置 | HF GIGO |
| `path_efficiency` | `clip(D/L, 0, 1)` | 可配置 | HF GIGO |
| `episode_duration_outlier` | IQR 法（已有 `stats_outlier_k`） | 已有配置 | `compute_stats` 已有 |
| `robot_induced_pause` | 动作开始处长时间停顿 | RoboMIND 标准 #2 | RoboMIND |
| `arm_shaking` | 高频振动能量 | 可配置 | RoboMIND 标准 #4 |
| `collision_before_grasp` | 抓取前加速度突波 | 可配置 | RoboMIND 标准 #5 |

**阈值来源诚实标注**：附录 B 列出「有公开出处」与「未找到公开出处」两类阈值。后者（时间戳容差 ms、缺口百分比、jitter 绝对阈值、多相机同步偏移容差、episode 时长合理区间）**必须作为可配置默认值并在返回中标注默认来源**，且不得被模型当作物理事实转述。

### 5.3.3 实施中修正的三处判据缺陷（重要，实现记录）

阶段二实现与测试过程中发现了三处**判据本身不可靠**的缺陷。它们都不是编码错误，而是"公式选错了"——记录下来以免将来重犯：

**缺陷 1：丢帧判据自我掩饰。**
初版按「时间戳跨度 / 中位采样间隔」推算应有行数。但隔行抽掉一半数据时，**中位间隔会翻倍**，"应有行数"随之减半，丢帧被自洽地掩盖（实测：抽掉 50% 后算出的丢帧率是 0.0）。
**修正**：改为两级判据——① 有声明 fps（`fps` 列或 LeRobot `meta/info.json`）时以其为**权威参照**，这能发现均匀丢帧（实测可正确算出 49.5%）；② 无 fps 时退化为「间隔一致性」（中位间隔 5 倍以上的缺口），能发现大段缺失但**无法发现均匀丢帧**，此时必须在 `evidence.note` 中**如实说明该局限**。

**缺陷 2：检查顺序导致判据失效。**
`fps_valid` 原本排在 `frame_loss` 之后，导致丢帧判据永远拿不到 `declared_fps`，静态地退化为那个自我掩饰的版本。
**修正**：把 `fps_valid` 前移到丢帧之前（代码中已加注释说明依赖关系）。

**缺陷 3：抖动判据对"平滑高频运动"完全失效。**
初版用 jerk 的 P95/median 比值。但一个**平滑的 8Hz 正弦**其 jerk 处处均匀，P95/median ≈ 1.2——比值判据无法发现平滑的高频运动，而那恰恰是抖动的典型形态（实测：构造 8Hz 正弦时该规则未报警）。
**修正**：改为「低频趋势（5 点滑动均值）+ 高频残差」分解，用**高频残差能量占总能量的比例**衡量（实测 8Hz 正弦 → 高比例报警；0.3Hz 低频平滑 → 通过）。仍保持无量纲、只 warn，符合 "Consistency Matters" 反对绝对阈值的立场。

**另有两条规则因"输入前提不成立"而改为诚实跳过**（宁可不检，不产出错误结论）：

- **致动器饱和**：HF GIGO 公式 `|a_t − q_{t+1}|` 要求**动作列与状态列成对**。初版在通道内自比，数值无物理意义。修正为按 `action_*` ↔ `observation.state.*` 归一化后缀配对；配对不到时返回 `skip` 并说明原因（列入 `not_audited`）。
- **视频逐帧质量**（过暗/模糊）：需额外视频解码依赖，当前版本只做**元信息级**检查（分辨率/时长），逐帧项如实列入 `not_audited`——**绝不报为 pass**。

### 5.4 标注自身质检（`check_annotation_qc`）

这是质检与标注的**闭环**，也是确定性最高、几乎零误报的一组规则。内部函数形态（不单独注册 @tool，由 `save_annotations` 与 `check_dataset_quality` 调用）：

| 规则 | 判据 | 严重度 |
|---|---|---|
| `time_overlap` | 同 episode 内相邻片段 `end_s > 下一段 start_s` | **fail** |
| `time_gap` | 相邻片段之间存在未覆盖空隙 | **fail**（若空隙 > 阈值，可能是漏标） |
| `bounds_exceeded` | `end_s` 超出 episode 实际时长 | **fail** |
| `non_monotonic_ids` | 同 episode 内 `id` 不递增或重复 | **fail** |
| `segment_too_short` | 片段时长 < `min_segment_s` | warn |
| `segment_too_long` | 片段时长 > `max_segment_s` | warn |
| `missing_hand` | 有 `target_object_class` 但 `interacting_hand` 为 `none` | warn（语义可能矛盾） |
| `noise_reason_empty` | `is_noise=true` 但 `cleaning_reason` 为空 | **fail**（规则不一致） |
| `action_vocab_offlist` | `atomic_action` 不在词表内 | warn（提示可能需扩词表） |
| `category_imbalance` | 某 `atomic_action` 占比极端（如 > 80%） | warn |
| `source_for_training` | 用途为训练真值但 `source != user_confirmed` | **fail**（§4.4 硬约束） |
| `action_language_mismatch` | 标注的动作与数据集已有语言指令明显不符 | warn（**仅提示，需人工判断**） |

## 8. 分阶段实施计划

严格遵循 AGENTS.md §3.5「小步交付，一次一个模块」，每阶段独立验收。

### 阶段一：`annotation_store`（锚点抽象 + 读写 + 版本管理）+ 既有缺陷修复

- **交付**：
  1. 锚点解析（三格式适配，§4.2/4.5）；
  2. JSONL 读写、来源分级校验、时间格式化；
  3. **版本管理三件套**（修订日志 / 快照 / diff，§4.3.1）；
  4. **修复 `main.py` 的 `_build_main_agent` 漏注册 `unpack_mcap` 的既有缺陷**（用户已确认顺手修掉）。
- **前置**：无。
- **验收**：三种格式骨架各自解析出正确锚点；JSONL 追加/去重/删除正确；并发写入不产生半截文件（复用 `_atomic_write` + `_file_lock`）；修订日志正确记录 `before`/`after`/`reason`；快照可冻结、可 diff。
- **测试**：`tests/test_annotation_store.py`；同时在 `tests/fixtures/skeletons/` 新增「带标注文件」骨架；**补一条 CLI 工具数与 UI 工具数一致性的断言**（防该缺陷复发）。
- **为何先做**：它是其余全部功能的地基，且是纯 Python、零外部依赖，风险最低。

### 阶段二：质检规则扩展（`check_dataset_quality`）

- **交付**：L1 硬门禁 6 条 + L2/L3 诊断 10 条 + 分层返回结构 + config 阈值。
- **前置**：无（不依赖标注）。
- **验收**：合成数据注入已知缺陷后能检出（参照 RDA 的盲测做法：注入 N 个缺陷 episode + 等量正常 episode，断言检出与零误报）。
- **测试**：`tests/test_check_dataset_quality.py`（含"诊断项不得升级为 fail"的守护用例——这是防 65% 误报事故的回归）。

### 阶段三：切片边界检测（`segment_actions`）

- **交付**：速度变化点、夹爪状态变化、突波、低速段四类信号；候选边界输出；`signals_missing` 诚实降级。
- **前置**：阶段一（锚点）。
- **验收**：合成信号（已知切分点）能正确定位；无动作列时返回 `no_motion_signal` 而非等分兜底。
- **测试**：`tests/test_segment_actions.py`；用合成轨迹（明确构造 3 段不同速度）断言边界误差在容差内。

### 阶段四：任务语义标注 + 标注落盘 + 标注质检

- **交付**：`annotate_task`、`save_annotations`、`check_annotation_qc`。
- **前置**：阶段一、二。
- **验收**：确认后重载数据集，标注正确回读；`source` 标记正确；用途合规校验生效（`llm_proposed` 进训练真值被拒）。
- **测试**：`tests/test_annotate_task.py`、`tests/test_annotation_qc.py`。

### 阶段五（可选，**默认不启用**）：视觉模型接入与 UI 标注编辑

- **交付**：
  1. 视觉草稿能力（`VISION_MODEL` 配置驱动，默认关闭）；
  2. 时间轴标注审阅/编辑界面（`app/ui/`，含修订历史展示与快照操作）。
- **前置**：阶段一至四全部完成；**且必须先用 `curl` 验证目标网关放行视觉模型**（模型本身支持 ≠ 网关放行）。
- **成本纪律**（用户决策 4）：本阶段**不得改动默认链路**——`DEFAULT_MODEL` 仍为 `hy3`。视觉能力仅经 `VISION_MODEL` 显式启用，未配置时全部走人工命名（零成本）。优先用免费额度验证（阿里百炼 100 万 token/模型，90 天）。
- **风险**：
  - 需修改 LLM 层与工具返回通道设计（`RunContext` 不序列化给模型的约定需重新审视）；
  - 公开基准 F1 0.306 意味着产出必须标 `llm_proposed` 并强制复核；
  - 视频输入方案（若有）多要求公网 URL，与"本地运行、不发起网络请求"定位冲突，**建议先只做单帧方案**。

### 阶段六（可选）：导入/导出与外部格式对接

- **交付**：LeRobot `meta/tasks.jsonl` 的任务标注导入/导出；`imported` 来源支持。
- **前置**：阶段四。
- **说明**：如果数据集本身已有任务标注（LeRobot v2），导入比重新标注更经济；导出则服务于"数据集发布元数据"用途。

## 9. 风险与边界

| 风险 | 后果 | 缓解 |
|---|---|---|
| 模型编造 `action_description` | 违反纪律 1/9，污染标注 | 模型无视觉时**禁止**自动生成描述；`llm_proposed` 禁止进训练真值 |
| 视觉模型引入后成本失控 | 意外产生 API 费用（当前为 0） | 视觉能力**默认关闭**，仅经 `VISION_MODEL` 显式启用；降分辨率优先于降帧率；优先用免费额度验证 |
| 阈值误报 | 用户对质检失去信任（RDA 曾 65% 误报） | 硬门禁与诊断项分离；诊断项只 warn；阈值按数据集配置 |
| 标注与数据对不上 | 标注失效，训练用到错误真值 | 锚点不可变；`bounds_exceeded` 硬检；锚点解析结果可复现 |
| 标注文件规模失控 | 1000 episode 产生 1000 文件 | JSONL 聚合落盘，非每 episode 一文件 |
| 修订日志无限膨胀 | 目录体积失控 | 追加式 diff（非全量副本）+ 软上限提示归档；绝不静默截断 |
| 工具返回膨胀撑爆上下文 | 触发 400 | 登记 `_TOOL_DROPPABLE`；逐片段明细列为可丢字段并保留完整计数 |
| 破坏既有零回归契约 | 影响现有 285 项测试 | 新模块独立；对既有函数的改动保持签名不变；补 CLI/UI 工具一致性断言 |
| 私有网关裁剪视觉能力 | 阶段五无法落地 | 阶段五动工前必须 `curl` 实测；失败则退回人工命名（不影响前四阶段） |

## 附录 B：质检阈值来源诚实标注

### 有公开出处的阈值（可直接采用并注明来源）

| 指标 | 数值/公式 | 出处 |
|---|---|---|
| 动作突波/碰撞 | `θ > 15 × median(\|a\|)`，`a_t=(q_{t+1}-2q_t+q_{t-1})/(t_{t+1}-t_t)²` | HF GIGO |
| 致动器饱和 | `\|a_t - q_{t+1}\| > 7°` | HF GIGO |
| 过暗惩罚 | `max(0, (50 - μ)/50)`，μ 为灰度均值 | HF GIGO |
| 模糊度 | 拉普拉斯方差，核 `[0,1,0;1,-4,1;0,1,0]` | HF GIGO |
| 空闲判定 | 速度阈值 0.1；空闲比 = 低速步数比例 | HF GIGO |
| 路径效率 | `clip(D/L, 0, 1)`，D 直线距离、L 实际路径长度 | HF GIGO |
| 人工接管边界 | 动作不连续尖峰富集 **3.1×** | RDA 实测 |
| 样本量阈值 | AgiBot 每原子技能至少 100 条轨迹 | AgiBot World |
| 验证收益 | 528 条验证轨迹 vs 482 条未验证，完成分数提升 **0.18** | AgiBot World "Wipe Table" |
| fps 硬校验 | `fps <= 0` 抛 ValueError | LeRobot 源码 |

### 未找到公开出处的阈值（必须标为可配置默认值，不得当权威标准）

- 时间戳容差的统一毫秒值
- 采样率不稳 / 数据缺口的百分比阈值
- 动作 jitter 的**绝对数值**阈值（"Consistency Matters" 明确反对用绝对值，主张 K-means 聚类分组）
- 多相机同步偏移的毫秒容差
- episode 时长的合理区间硬阈值（仅有经验性描述，见 §5.2.2）
- 标注类别不平衡的量化阈值

## 附录 C：自动切片精度的公开实测（用于设定预期）

来源：Macrodata WGO-Bench（100 个片段、743 个人工标注片段、62 个任务、71.5 分钟；评分要求 Segment F1 的 IoU ≥ 0.75）：

| 方法 | Segment F1 |
|---|---|
| 固定长度基线（5.77s 均分） | 0.070 |
| 字幕嵌入相似度分割 | 0.081 |
| 逐帧时间戳图像 | 0.193 |
| 视觉时间戳 + 接触表 | 0.263 |
| **最佳（Gemini 3.5 Flash）** | **0.306** |
| 最佳端到端 F1 | 0.168 |

**结论**：自动切分（含视觉方案）只能产出草稿。这直接支撑了本设计"边界用信号算、命名靠人工/视觉、来源分级、复核闸门"的方案选择。
