# 文件内容查看能力设计

> 版本：v0.1（草案，待用户确认）
> 关联文件：`AGENTS.md`（行为准则）、`docs/ARCHITECTURE.md`（总纲，

> `docs/表访问与跨表运算改造设计.md`
> 状态：**设计评审中，未经确认不得动工**（AGENTS.md §3.4「先文档后代码」）
>
> 触发背景（真实场景，2026-09-22）：分析 `origin-data-fullmodal-sample-dataset`
> 时，用户问"这个数据集里有没有数采设备信息（相机型号 / 手环型号）"。
> agent 的回答是"够不到，建议你重新加载单文件来读"——**但这既不必要，
> 且其中一条路径实际走不通**（`.md` 是 `unsupported_format`）。

## 1. 问题陈述

### 1.1 复现结果（确定性，非推测）

构造同构目录并加载，得到：

| 文件 | 分组 | 在流登记表？ | 内容可读？ |
|---|---|---|---|
| `file-007.parquet`（数据表） | tables | ✅ | ✅ 正常 |
| `video_layout.json`（配置型） | tables→config | ✅ | ❌ `table_read_failed` |
| `camera_calibration.json`（标定） | cals | ❌ | ❌ 仅键名（来自指纹探测） |
| `lerobot/meta/info.json`（元数据） | cals | ❌ | ❌ 不可读 |
| `README.md`（文档） | **others** | ❌ | ❌ **完全不可读** |
| `leRobotv3DatasetDoc.md` | **others** | ❌ | ❌ **完全不可读** |

`.md` 尝试单文件加载的结果：

```
success: False | error: unsupported_format
user_message: 暂不支持 .md 格式，目前支持：.csv、.json、.jsonl、
             .parquet、.h5、.mcap、.txt、.info、.log
```

### 1.2 根因：**"文件角色"与"内容可读性"被混为一谈**

`_sniffing.probe_directory` 按扩展名把文件分六组：
`tables` / `videos` / `audios` / `images` / `cals` / `others`。

而 `build_streams_registry` **只登记** `table_info`（表格）、视频、音频、图片。
于是：

- **`others` 组（.md / .yaml / .json 之外的文档）被完全丢弃**——
  普查阶段"看得到文件名"，但没有任何读取路径；
- **`cals` 组（标定 / 元数据 JSON）刻意不进流登记表**——这本身是**正确的**
  （`docs/ARCHITECTURE.md` §3.3.1：防止标定 JSON 被当数据表参与对齐），
  但副作用是**它们的"内容"也变得不可读**，只剩下指纹探测给出的键名。

**关键区分（本设计的立足点）**：

> **"不参与数据分析" ≠ "内容不可查看"。**
>
> 标定文件确实不该进表清单（防误用），但用户完全有理由查看它的内容
> （如相机内参、`P_left_from_joints` 变换矩阵）。当前的实现把
> "语义角色隔离" 错误地扩大成了 "内容访问封锁"。

### 1.3 为什么这件事重要（不只是"少读一个文件"）

数据集的**设备信息、采集协议、字段语义、使用边界**通常写在文档与配置里。
真实案例（origin-data）：

- README 写明"synchronously capturing sEMG, first-person-view video, IMU"；
- 文档写明"**Force is an estimate inferred from EMG, not ground truth from a
  hardware force sensor**"——**这条直接决定 `force_values` 能否当作物理真值
  用于训练**，是比通道统计更重要的质量结论；
- `lerobot/meta/info.json` 定义字段 schema 与是否启用可选字段；
- `camera_calibration.json` 含投影矩阵（做 overlay 必需）。

**这些都在"不可读"的一侧。** 结果是：agent 能精确算出 16 张表的行数分布，
却读不到"这批数据是干什么的、能不能当力真值用"。

## 2. 设计目标与非目标

**目标**：

1. **任何文本类文件都有只读查看路径**（文档 / 配置 / 标定 / 元数据）；
2. 查看能力**不改变数据语义**——不参与对齐、不进统计、不替换主表；
3. **限长返回**，长文档不撑爆上下文（沿用既有预算纪律）；
4. 内容来源**可溯源**（路径、行号范围、被截断量）；
5. 模型**能自己发现并使用**该能力（不需用户提示"重新加载"）。

**非目标**（明确不做）：

- 不做**文档语义解析**（不解析 Markdown 结构、不抽取"设备型号"字段）——
  那是 LLM 的活，工具只提供**原文**；工具替模型"理解"内容必然引入幻觉；
- 不做**二进制内容读取**（图片/视频走既有专用工具）；
- 不做**文件写入**（本能力严格只读）；
- 不把文档内容**并入 `context.df` 或能力标签**（避免污染确定性分析）。

## 3. 设计

### 3.1 新增工具：`read_file_content`

一个工具、三种模式（按文件角色自动分派），**只读**：

```python
@tool
def read_file_content(
    wrapper: RunContextWrapper[RunContext],
    path: str,
    max_chars: int = 4000,
    start_line: int | None = None,
    keyword: str | None = None,
) -> dict:
    """查看数据集内任意文本文件的内容（只读；文档 / 配置 / 标定 / 元数据通用）。

    用于回答"这个数据集是干什么的""设备是什么""字段怎么定义""标定参数是多少"
    这类问题——这些信息通常在 README、文档、meta/info.json、标定 JSON 里，
    而它们不属于可分析的"数据表"。

    **不做内容理解**：本工具只返回原文（或键值摘要），不解析、不总结、
    不抽取语义——含义由你阅读后判断，避免工具层替模型"理解"而产生幻觉。

    Args:
        path: 文件路径，或流登记表中的文件名（大小写不敏感）。
        max_chars: 返回的最大字符数（默认 4000，防长文档撑爆上下文）。
        start_line: 可选，从第几行开始读（1-based；用于分段读取长文件）。
        keyword: 可选，只返回包含该关键词的行（大小写不敏感，带行号）。
            用于在长文档中定位设备型号、字段定义等——**逐行匹配，
            不猜语义**。

    Returns:
        dict，含 success、path、kind（document / config / calibration /
        metadata）、content（文本或键值摘要）、n_lines_total、
        n_lines_returned、truncated、content_basis（来源说明，如"第 1-120 行"）；
        失败时含结构化 error 与 user_message。
    """
```

### 3.2 三种模式（按角色自动分派）

| 模式 | 触发 | 返回 | 依据 |
|---|---|---|---|
| **文本模式** | `.md` / `.txt` / `.yaml` / `.log` / `.info` 等纯文本 | 原文（按行切片 / 关键词过滤） | 直接读取 |
| **配置模式** | 单对象 JSON（含 `config` / `metadata` / `calibration` 角色） | **键值摘要**（复用 `_compact_config`：标量原样、长值截断、嵌套报规模） | 配置语义在"键→值"，展成表反丢失信息 |
| **表格模式** | 逐行数据表 | **引导用 `profile_data`**（返回结构化提示） | 职责分离，避免两个工具做同一件事 |

**为什么配置模式返回"键值摘要"而非原文**：JSON 原文可能很长且嵌套深，
直接灌进上下文性价比低；而配置的价值恰恰是**顶层键值**（`nominal_hz: 120`）。
`_compact_config` 已在"配置型 JSON"修复中实现（见 `docs/ARCHITECTURE.md`
§3.3.0），此处复用，**不重写**。

**为什么表格模式要"引导"而不是直接读**：若本工具也能读表，就与
`profile_data` / `compute_stats` 职责重叠——而"工具集臃肿、功能重叠导致
模型不知该用哪个"是明确的反模式（`AGENTS.md` §5「工具即壁垒」）。
故表格请求返回**结构化引导**（含建议工具名），而不是再实现一遍。

### 3.3 文件解析顺序（沿用既有容错）

```
输入 path
  ├─ 直接是存在的文件路径 → 用
  ├─ 是流登记表中的文件名（大小写不敏感）→ 用其完整路径
  ├─ 在 file_survey 的**任意组**（tables/cals/others/videos…）中按名匹配 → 用
  └─ 都不匹配 → 结构化错误 + available_documents（可选文件清单）
```

**关键**：第三级（遍历 `file_survey` 全部组）是本设计的**核心修复点**——
此前 `others` 组的路径**只在 `file_survey` 里可见**，没有任何工具能按它取文件；
现在 `read_file_content` 能在此定位。

### 3.4 安全与预算约束（硬性）

1. **只读**：绝不写入、绝不修改源文件（与 `inspect_video_frame` 同纪律）；
2. **限长**：单次返回 ≤ `max_chars`（默认 4000，可配），超出**如实标注**
   `truncated: true` 与 `n_lines_total`，并提示用 `start_line` 续读；
3. **不进主表语义**：读取结果**不写入** `context.df`、不进 `findings`、
   不参与对齐（避免污染确定性分析）；
4. **不做内容理解**：不解析、不总结、不抽字段——**原文交付**；
5. **路径约束**：仅允许读**当前数据集目录内**的文件（防止越权读系统文件）。

### 3.5 与既有能力的关系

| 既有能力 | 关系 |
|---|---|
| `load_dataset` 的 `file_survey` | 提供**可读清单**（含 others 组），本工具据它定位 |
| `_compact_config` | **复用**（配置模式的值摘要） |
| `profile_data` / `compute_stats` | 表格分析仍归它们；本工具遇表格时**引导**过去 |
| `inspect_streams` | `config_files` 已列出配置文件名；本工具是**读内容**的补充 |
| `_output_guard` | 复用返回体积护栏（本工具返回天然小，仍登记 droppable） |

**无需改动** `probe_directory` / `build_streams_registry`——
本设计**不改文件分组逻辑**（那会影响既有回归），而是**新增读取通道**。

## 5. 验收标准

1. 能读到 `README.md` 内容，且 `keyword="emg"` 能定位到相关行（带行号）；
2. 能读到 `camera_calibration.json` 的键值摘要（含 `intrinsics`）；
3. 能读到 `lerobot/meta/info.json` 的 schema 信息；
4. 表格请求返回**引导**而非重复实现（不出现"两个工具都能读表"）；
5. 超长文件被截断且**如实标注**，`start_line` 可续读；
6. 越权路径（数据集目录之外）被拒绝；
7. 全量既有测试不回退。

## 6. 明确不做（防止范围蔓延）

| 方案 | 否决理由 |
|---|---|
| 让模型"重新加载单文件"绕行 | **替换当前数据集**（单数据集语义），代价与风险都不合理；且 `.md` 本就不支持（`unsupported_format`），此路实际不通 |
| 把文档内容并入 `context.meta` / 能力标签 | 污染确定性分析；文档是"人读的原文"，不是"机器用的事实" |
| 工具自动抽取"设备型号"等字段返回 | **替模型理解内容**必然引入幻觉；项目原则是"工具给原文，LLM 做解读" |
| 支持二进制（图片/视频）内容读取 | 已有专用工具（`inspect_video_frame`）；职责不重叠 |
| 改 `probe_directory` 把 `others` 并入 tables | 会破坏"others 不参与分析"的既有语义与回归测试；且 `.md` 不是表格 |

## 7. 待用户裁决的决策点

1. **工具命名**：`read_file_content` / `view_file` / `read_document`？
   （设计倾向 `read_file_content`：明确"读内容"而非"读表"）
2. **默认 `max_chars`**：4000（约 1.5 页）是否合适？依据：既要覆盖典型
   README 的关键段落，又不能挤占单工具返回预算（预算的比例由
   `tool_output_budget_ratio` 决定）。
3. **是否支持通配/多文件**：如 `path="*.md"` 一次读多个？
   设计倾向**不支持**（保持单文件语义清晰；多文件应分次读）。
4. **关键词模式是否返回上下文行**：如命中行前后各 1 行（便于理解上下文）？
   设计倾向**返回命中行 + 前后各 1 行**并标注行号——单行常缺上下文。
