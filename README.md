# 🩻 Embodied-data-Xray

**X-ray your robot datasets** — structural profiling & analysis agent for embodied-AI collection data.

一个**本地运行、面向具身智能（Embodied AI）领域**的数据分析 Agent：像 X 光一样透视机器人采集数据的**结构**——文件构成、时间戳伴随表、骨骼位姿块、元数据角色——再通过自然语言对话完成统计分析、可视化与解读报告。

> 为什么叫 x-ray？它看的是数据的**结构骨架**，而不是内容本身。所有已支持格式的结构骨架都固化为回归测试（`tests/fixtures/skeletons/`），保证"新格式来了不再崩"。

## 它能做什么

- **目录透视**：递归普查 + 语义角色识别（时间戳伴随表 / 元数据文件 / 骨骼位姿块 / 索引列），生成能力标签与推测类型
- **确定性分析**：数据概况、任务级统计、骨骼位姿范围（按数据集声明的 N×M 块分解）、时间同步与漂移检查、传感器合理性检查——全部由 pandas 确定性计算，LLM 只负责解读
- **数据集质检**：分层判定——硬门禁（NaN/丢帧/时间戳单调/schema/fps/episode 边界）可判 fail，诊断项（空闲比/突波/饱和/抖动/停顿/振动/路径效率/视频）仅提示，不自动升级为判定
- **标注支持**：切片边界检测（本体信号确定性计算）、任务语义标注、标注落盘与标注自身质检——含来源分级、版本管理与用途合规闸门（详见「标注与质检」一节）
- **对话式操作**：自然语言驱动（openai-agents SDK），CLI 与 Streamlit 双入口；工具调用轨迹、token 消耗全程可见
- **诚实降级**：识别不了就如实标注 unknown 并附证据，绝不硬猜；数值计算不交给 LLM

## 标注与质检

面向"给机器人数据打上任务语义与动作切片"的工作流。质检是对数据集本身的分析延伸，
标注则会把结果落到 `outputs/` 下供后续使用。

### 数据集画像确认（`confirm_dataset_profile`）

把**只有你知道的事实**固化下来，跨会话生效（写入 `outputs/by_dataset/<净名>/profile.json`）。
典型场景有两个：

**固定数据集类型**：报告里显示「推测类型 unknown」而你知道它是什么时，确认后
报告会改显示「数据集类型：xxx（来源：用户确认）」，并保留自动识别的结果供对照。

**标注预期缺失**：设备的某组信号**本来就没有**（如手套不含前臂传感器）时，
把这些列登记为"预期缺失"。质检此后会把它们标为「预期缺失」而非「错误」——
**不隐藏，只是与「意外缺失」区分开**，避免已知的正常情况每轮都被报成问题。

### 数据集质检（`check_dataset_quality`）

每次调用返回全部检查项，结果**分两层**，含义不同、必须分开看：

| 层 | 包含 | 能判 fail？ | 怎么理解 |
|---|---|---|---|
| 必须处理的问题（`gate`） | 缺失值与异常值、时间戳顺序、丢帧、跨段结构一致性、采样率声明、片段边界 | ✅ 只有这层能 | 确定性错误，出现即为真问题 |
| 参考提示（`diagnostics`） | 静止占比、动作突跳、执行器饱和、动作抖动、中途停顿、异常振动、路径效率、视频质量 | ❌ 只提示 | 统计性观察，**超阈不等于数据有问题** |

分层是刻意的：**阈值与任务强相关**，不存在通用阈值——静止占比高对放置、按压类
任务完全正常，对连续抓取类才可疑。若让提示项自动升级为判定，会产生大面积误报
（同类工具曾因此误报 65%）。所以提示项只是参考，需结合任务类型判断。

**输出是可读的**：结果用中文分层表述（【必须处理的问题】/【参考提示】/【本次未检查】），
每条规则都带中文名与白话说明。需要给界面用时可取 `readable_summary`（全中文键），
需要查术语可取 `glossary`。此外，`nan_inf` 会同时给出整体比例与最差字段——
判定依据是**逐字段**，所以你可能会看到"整体缺失率 2% 低于阈值 5% 却判不通过"
（某个字段 100% 为空，整体被摊薄稀释），详情里会解释这一点。

返回中还带 `not_audited`（**未检查**的项，不等于通过）、`thresholds` 与
`threshold_source`（阈值来源，默认值均未针对具体数据集验证）。

### 动作切片（`segment_actions`）

用机器人**本体信号**做确定性切分，四类信号按可得性自动降级：

| 信号 | 可靠度 | 说明 |
|---|---|---|
| 夹爪开合状态变化 | **高** | 抓取/释放是物理事件，实测能精确命中真实边界 |
| 加速度突波 | 中 | 对应碰撞/人工干预，无此类事件时不触发（正常） |
| 停顿段边界 | 中 | 只能识别"停下来的地方" |
| 速度变化点 | **低（仅候选）** | 无法区分"动作切换"与"运动强度变化"，**会有误报** |

**重要：该工具只产出时间边界，不产出动作名称。** 命名需要看懂画面，而当前默认
模型 `hy3` **不支持图片/视频输入**（官方文档明确说明），因此无法自动生成
`atomic_action` / `action_description`——这是当前能力的**明确边界**，不是待修的
缺陷。请人工命名，或先换用支持视觉的模型（该能力尚在规划中，未实现）。

信号全部不可得时返回 `no_motion_signal` 并列出欠缺的信号，**不做等分兜底**
（按固定时长等分产生的边界没有物理依据，会给下游引入噪声）。

### 标注落盘与来源分级（`annotate_task` / `save_annotations`）

任务描述同样不由模型编造：优先从数据中确定性提取（LeRobot 的 `meta/tasks.jsonl`、
`meta/episodes.jsonl`、数据表语言列），找不到就请用户提供。

落盘的每条标注都带**来源标记**，它决定这条标注能用于什么用途：

| 来源 | 含义 | 训练真值 | 发布元数据 | 内部清查 |
|---|---|---|---|---|
| `user_confirmed` | 用户输入或已确认 | ✅ | ✅ | ✅ |
| `signal_derived` | 本体信号确定性算出 | ⚠️ 需复核 | ✅ 须声明自动生成 | ✅ |
| `llm_proposed` | 模型提出、未经确认 | ❌ **拒绝** | ⚠️ 须声明为推测 | ✅ |
| `imported` | 从外部文件导入 | ⚠️ 取决于外部质量 | ✅ | ✅ |

这不是建议而是**代码里的硬闸门**：以 `use="training"` 落盘 `llm_proposed` 或
`signal_derived` 来源时会被**整批拒绝**，并提示先用 `confirmed_by_user=True`
复核。落盘前须经用户明确同意（`confirm=False` 只登记不写盘）。

### 标注自身质检（`check_annotation_qc`）

检查的是**标注**而非数据。可判 fail 的确定性问题：片段重叠、超出 episode 时长、
片段序号重复/错乱、标了噪声却无原因、来源与声明用途不兼容。仅提示的项：片段间
存在空隙（可能确实不属于任何动作）、粒度离群、有目标物体却未标交互手、动作名
不在词表内、单一动作占比过高。落盘后会**自动跑一次**，问题当场暴露。

### 标注产物与版本管理

```
outputs/by_dataset/<数据集名-短哈希>/annotations/
├── tasks.jsonl              # 任务级标注（每 episode 一行）
├── segments.jsonl           # 切片标注（每片段一行，读时即最新）
├── revisions/
│   ├── revisions.jsonl      # 追加式修订日志（记录了谁在何时改了什么、为什么）
│   └── snapshots/           # 交付前手动冻结的快照
└── qc/                      # 质检结果
```

当前态单独存 JSONL 便于直读与手工编辑；修订日志只追加增量差异（不是全量副本），
可回溯"这条标注改过几次、改成什么"；快照用于交付/发布溯源，**只手动触发**——
训练真值与数据集发布是冻结语义，不该被自动行为影响。

### 推荐工作流

1. `check_dataset_quality` 看数据质量（重点看硬门禁）；
2. `segment_actions` 产出候选边界（**优先信夹爪信号**，速度边界须人工复核）；
3. 人工命名与修正边界，或接入视觉模型生成待确认的名称；
4. `save_annotations` 落盘（如实标记来源；用于训练真值须先经确认）；
5. `check_annotation_qc` 校验（落盘时已自动执行一次），按提示修正后重存。

```bash

.venv\Scripts\activate          # Windows
pip install -r requirements.txt

# 2) 配置模型：复制 .env.example 为 .env，填入密钥与端点

# 3) 没有数据？用内置结构骨架生成一个示例目录（零数据体验全流程）
python -c "from tests.fixtures.make_skeleton import build_skeleton; \

python main.py                      # CLI

### 产物在哪里

Agent 生成的图表与报告都在项目根目录的 `outputs/` 下，**按数据集分子目录**便于
查找与清理：

```
outputs/

    ├── reports/     # Markdown 报告

`outputs/` 已被 `.gitignore` 排除（不进仓库），可随时整个删除。子目录名的

`s-xxxx_` 前缀是会话标识——多个对话分析同一数据集时靠它避免产物互相覆盖。
详见 `outputs/README.md`。

> 早期版本把产物平铺在 `outputs/` 根目录、确认画像集中在单个
> `.dataset_profile.json`；升级后旧画像会在首次读取时自动迁移到新位置。

图表配色），**无需改代码**：

- **切换浅色 / 深色**：点右上角菜单 → Settings → Theme，可选 Light / Dark /

- **改品牌主色**：改 `[theme]` 的 `primaryColor`。若同时要改图表配色，请同步
  修改 `chartCategoricalColors`（必须**正好 10 个**颜色）与
  `app/visual_theme.py` 的 `CHART_COLORS`——两处必须一致（有测试断言）。
- **图表为何是透明底**：图表以 png 落盘，透明背景使其在浅色与深色页面上都能
  自然融入（否则深色下会出现刺眼的白色贴片）。图表文字用中间明度的中性灰，
  以便同一张图在两种主题下都可读。

## 支持的数据布局清单

当前**已验证**的数据布局（每种布局的结构骨架已固化为回归测试）：

| 布局 | 特征 | 状态 |
|---|---|---|
| 单文件 | CSV / JSON / JSONL / Parquet / HDF5 单表 | ✅ 支持 |
| 多流采集目录 | CSV 传感器流 + 每路视频的时间戳伴随表 + 相机标定 JSON + 媒体文件 | ✅ 支持 |
| 帧索引 + 视频目录 | 每路视频的帧索引表（`.index.parquet`）+ 多分辨率/预览视频变体 + 同名 sidecar JSON | ✅ 支持 |
| LeRobot v2 | `meta/info.json` + `data/chunk-*` + `videos/chunk-*` | ✅ 支持 |

**清单外格式**：agent 仍会尝试加载（普查/嗅探尽力而为），但识别可能受限——未知语义
角色会被如实标注为 `unknown`，而不是硬猜。新布局建议先把结构骨架加入测试套件，
再进入分析流程。

## 数据识别如何工作

识别规则绑定**语义角色**，不绑定物理形态（后缀/目录名/固定列名）：

- **时间戳伴随表**：与媒体同 stem 的表格 + 帧级时间戳列（`frame_*`/`exposure_*`/`pts`），行数与视频帧数相符——无论它是 `*_metainfo.csv` 还是 `camera-x.index.parquet`
- **元数据文件**：小尺寸 JSON + 配置型键（fps/features 等）→ 不进流清单、不参与对齐
- **配置文件（与空流不同）**：单个 JSON 对象（无逐行数据，如 `session.json`）会被标为
  `status="config"` 并在 `config_files` 中单列，**其字段值会被解析出来透出**（如手套数据
  的 `nominal_hz`=120、`hand_mode`=both）。注意这与"空流"语义相反：空流没有内容，
  配置文件有内容但不是逐行格式——两者分开呈现，不会再把有内容的配置报成"空"。
  含空数据键的 JSON（如 `{"data": []}`）仍按空流处理，因为文件本身在声明没有数据
- **骨骼位姿块**：数据集声明 `names=xxx_NxM` 且 N×M==shape → 按块分解统计位姿范围与四元数范数
- **时间戳列**：词表命中优先，未命中回退内容指纹（单调递增 + 量级符合时间单位）；单位推断带自我纠正（采样率超物理区间自动换单位重算）
- **JSONL vs JSON**：`.jsonl` 每行一个 JSON 对象（`lines=True`），`.json` 整体一个 JSON 值——两者分别读取、不混用；JSONL 的嵌套列表/对象值保留为 object 列，可被概况统计（非空计数/样例值）与合理性检查（全零/恒定）覆盖
- **多时钟与嵌套信封**：MCAP 导出的信封流（顶层容器时间 + `data` 内嵌数值与传感器时间）会自动发现嵌套时间候选与信号字段（`data.header.timestamp_us`、四元数/加速度向量等）；同一流多个时间口径的形态矛盾（容器时间判"突发"、传感器时间判"周期"）会显式告警（`clock_artifact_suspected`），可用 `time_column=嵌套路径` 重算。`profile_data` / `check_sensor_sanity` 传 `expand=True` 可把嵌套数值展开为扁平列后分析（只读视图，不改主表）。流的语义分组可由 agent 批量提交假设（`propose_stream_semantics`：先工具验证 → 用户确认 → 持久生效）

## 上下文管理（防 input length too long）

多轮对话中，历史会不断累积——每轮都会把此前所有轮次的工具返回重发给模型，
数据集较大时可能撞上模型上下文上限（表现为 `input length too long`）。本工具
采用三层防御：

1. **工具返回护栏**：单次工具返回超出预算时**渐进降级**（先省略次要字段 →
   截断长列表 → 压缩为结论摘要），且**保留完整计数**、必带 `truncated` 与
   `truncation_note`，绝不静默抽样；
2. **兜底硬截断**：即使某个工具漏做降级，也保证单条返回不超预算；
3. **历史压缩**：历史超出阈值时（**在送给模型之前**拦截），把较早轮次的
   工具返回原文压缩为结论摘要——**用户提问与助手结论一条不丢**，且数据仍在
   本地进程内，需要明细时重新调用工具即可取回。

触发方式为"自动为主、手动兜底"：超阈值自动压缩（默认开启，可在 `.env` 用
`HISTORY_COMPACTION_ENABLED=false` 关闭），也可随时手动压缩——CLI 输入
`/compact`（`/history` 查看历史体积），Streamlit 在侧栏点「压缩历史」。

预算按 `模型上下文窗口 × 0.6` 派生。窗口来源优先级：`.env` 的
`CONTEXT_WINDOW_TOKENS` > 内置模型表（已核证：hy3=256K、deepseek-v4=1M、
deepseek-v3/chat=128K）> 256K 兜底。**换模型时建议显式配置
`CONTEXT_WINDOW_TOKENS`**——内置表可能过时，兜底值对小上下文模型不安全。
token 数为保守估算而非精确计数（不引入分词器依赖），偏差方向是安全的：
估高只会提前压缩，不会估低撑爆。

> 工具返回被截断时，agent 会主动告知"本次结果未能完整展示"并建议分批查看，
> 不会把截断后的部分结果当作完整结论陈述。

## ffmpeg / ffprobe（可选）

加载含视频的目录时，会用 `ffprobe` 读取视频元数据（帧率/分辨率/帧数/时长/编码）。
未安装不影响其余功能，视频元数据会以结构化降级提示呈现。

Windows 推荐 `winget install Gyan.FFmpeg`；安装后用 `where ffprobe` 确认在 PATH 中
（winget 的实际安装目录在 `%LOCALAPPDATA%\Microsoft\WinGet\Packages\Gyan.FFmpeg_...`，
与常见的 `C:\ffmpeg\bin` 约定不同）。macOS / Linux：`brew install ffmpeg` 或
`apt install ffmpeg`。验证：`ffprobe -version`。
